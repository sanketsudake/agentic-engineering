# Chapter 5 — Memory & State

## Why this chapter

The model is stateless: every API call starts from the context alone.
So "the agent remembers" always means that the harness stored something and injected it again later.
This chapter zooms into steps 2 and 9 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) — recall at context assembly, and the memory write at post-processing.
The mental model: memory is a read at turn start and a write at session end.
Everything between those two moments is session state.
An engineer who holds that model can debug every "it forgot" and "it remembers wrong" report.

## Concepts

**Short-term vs long-term memory.** Short-term memory is what the harness holds for the current session: the context window plus session state.
It ends when the session ends.
Long-term memory is anything that the harness stores and can inject into a later session.
The model itself holds neither one ([Trace 1](ch01.md#trace-1-what-happens-when-you-send-one-message-to-a-model)).

**Session state.** Session state is the harness-side record of the run: the transcript, the tool results, the current plan, and scratch data.
It is complete, and it covers one session only.
Memory is the opposite: it is distilled, and it crosses sessions.
If you confuse the two, the store fills with transcripts, and recall returns noise.

**Files as memory.** The simplest long-term store is a file.
The harness puts an instruction file (project conventions, environment facts) at the front of the context at session start.
The agent then edits that file with the ordinary file tools.
You can read, diff, and version a file, and the read and write paths are plain tool calls.
The limit: the harness injects the whole file and cannot rank the parts by relevance, so the file must stay small.

**Recall.** At context assembly ([Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task), step 2), the harness queries the memory store and injects the matching entries into the system segment.

Two signals rank the candidates:

- **Relevance:** does the entry apply to this request?
  Relevance selects the candidates.
- **Recency:** is the entry still true?
  Recency orders the versions of one fact and marks the stale ones.

Trace 12 shows this read.

**Memory write and consolidation.** At post-processing ([Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task), step 9), the harness extracts candidate memories from the transcript.
It then consolidates them.
Consolidation compares each candidate against the existing entries and chooses one of three actions: update the entry, skip the duplicate, or delete the obsolete one.
Without consolidation, the store collects entries that contradict each other.
Trace 13 shows this write.

**Persist vs recompute.** Persist the facts that are stable and expensive to find again: environment quirks, user preferences, and decisions with their reasons.
Recompute anything that is cheap to derive or quick to change: file contents, test results, branch state.
A stale entry looks exactly like a correct one, so any fact that is dangerous when stale defaults to recompute.

**State stores across runtimes.** Framework runtimes use one common pattern: a state store keyed by a session or thread identifier.
The runtime saves the state at defined points and loads it again on resume.
So crash recovery and multi-day tasks need stored data, not more loop code.

### In other stacks

- **OpenAI Agents SDK:** a session stores the conversation history across runs, so short-term memory can survive a process restart.
- **OpenAI Agents SDK:** each run still starts stateless; a session replays the transcript, not distilled memory.
- **LangGraph:** a checkpointer saves the graph state at every superstep, and a `thread_id` in the invocation config loads that state again.
- **LangGraph:** persistence belongs to the graph, not to the chat — the session state is the graph state (Lab 7 exercises this).
- **Both stacks:** you still build extraction, consolidation, and long-term recall yourself (Traces 12 and 13).

## Traces

### Trace 12: What happens when an agent recalls a fact from memory

You open a new session and ask the agent to deploy; a session last month learned the staging URL.

1. **User** sends a request in a new session.
2. **Harness** starts context assembly ([Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task), step 2) with an empty transcript.
3. **Harness** derives a retrieval query from the request and from the user or project identity.
4. **Mem** searches the stored entries and returns candidates with scores and timestamps.
5. **Harness** ranks the candidates by relevance first, then by recency.
   - Recency also marks an entry as stale when a newer version of the same fact exists.
6. **Harness** cuts the ranked list to fit a token budget.
7. **Harness** injects the remaining entries into the system segment, labeled as recalled memory.
   - The label is necessary: the model must read a memory as a harness statement, not as user words.
8. **LLM** generates the answer from the assembled context, memory included.
9. **User** sees an answer that uses the stored fact, with no new question from the agent.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant Mem
  participant LLM
  User->>Harness: new session request
  Harness->>Mem: retrieval query
  Mem-->>Harness: scored entries
  Harness->>Harness: rank and budget
  Harness->>LLM: context plus memory
  LLM-->>Harness: answer using fact
  Harness-->>User: answer
```

*Figure 5.1 — recall is a read at assembly time: the model sees a memory only because the harness injected it.*

**Where this can fail**

- **Symptom:** the agent states a fact that is no longer true.
    - **Cause:** recency never marks stale entries, so old entries rank on relevance alone.
    - **Where to look:** the timestamps of the recalled entries in the store.
- **Symptom:** a stored fact is never used.
    - **Cause:** the retrieval query misses the entry, or the token budget cut it.
    - **Where to look:** the retrieval scores, and the assembled system segment in the transcript.
- **Symptom:** the first turn grows larger every week.
    - **Cause:** no injection budget, so recall returns more entries as the store grows.
    - **Where to look:** the token counts of the first turn across sessions.
- **Symptom:** the model quotes a "memory" that nobody wrote.
    - **Cause:** the model invented it, or it rephrased an injection that carried no label.
    - **Where to look:** compare the system segment with the store's entries.

### Trace 13: What happens when a session ends and memory is written

The [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) session ends; the harness runs post-processing (step 9) before it closes the session.

1. **User** ends the session, or a stop condition ends it.
2. **Harness** starts post-processing with the full transcript.
3. **Harness** sends the transcript to the LLM with an extraction prompt.
4. **LLM** returns candidate memories: facts, preferences, and corrections.
5. **Harness** drops every candidate that is true for this session only.
6. **Harness** asks Mem for the existing entries that are similar to each remaining candidate.
7. **Mem** returns the matches with their timestamps and provenance.
8. **Harness** resolves each conflict: update the entry, skip the duplicate, or delete the obsolete one.
   - A contradiction becomes an update, never a second entry; two versions of one fact make later recall return both.
9. **Mem** commits the writes with timestamps and provenance.
10. **Harness** records the telemetry and closes the session.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  participant Mem
  User->>Harness: end session
  Harness->>LLM: transcript and extraction prompt
  LLM-->>Harness: candidate memories
  Harness->>Mem: find similar entries
  Mem-->>Harness: matches with timestamps
  Harness->>Harness: update skip or delete
  Harness->>Mem: commit writes
  Mem-->>Harness: ack
```

*Figure 5.2 — consolidation runs before commit: every candidate is checked against what the store already holds.*

**Where this can fail**

- **Symptom:** the store grows without limit and fills with near-duplicates.
    - **Cause:** no similarity check before commit.
    - **Where to look:** the entry counts, and the overlap between entries over time.
- **Symptom:** recall later returns two facts that contradict each other.
    - **Cause:** the harness stored a contradiction as a new entry instead of an update.
    - **Where to look:** the matching entries and their timestamps.
- **Symptom:** the store keeps session-local detail, such as "the test failed today".
    - **Cause:** the extraction prompt does not filter for durable facts.
    - **Where to look:** the candidate list, compared with the committed entries.
- **Symptom:** a secret appears in memory.
    - **Cause:** extraction copied a tool result word for word into an entry.
    - **Where to look:** the entry contents and their provenance.
- **Symptom:** a session that crashed loses everything it learned.
    - **Cause:** the harness writes memory only at a clean session end.
    - **Where to look:** the telemetry for the crashed run: did the write step run?

## Questions

### Tier 1 — Explain

**Q 5.1 — What is the difference between short-term and long-term memory in an agent?**

**Answer.** Short-term memory is the context window plus session state, and it ends with the session.
Long-term memory is whatever the harness stores and injects into later sessions.
The model holds neither one: every call starts from the context that the harness assembled.
The boundary is the session end.
Anything that must survive it needs an explicit write (Trace 13).
The two layers also fail in different ways: short-term memory overflows, and long-term memory goes stale.

*Strong answers also mention:* session state is complete and covers one session; memory is distilled and crosses sessions.

**Q 5.2 — Why is memory a harness feature and not a model feature?**

**Answer.** The API is stateless for each call, so the model cannot write anything that outlives its response.
Persistence needs storage, and the harness owns everything that holds state ([Chapter 1](ch01.md)).
The harness also owns the two moments when memory happens: assembly at step 2, and post-processing at step 9.
"The agent remembered" always means that the harness wrote at step 9 and injected at step 2.
So memory bugs are harness bugs: you debug the store and the injection, not the model.

*Strong answers also mention:* a provider-hosted "built-in memory" is still a harness, and the provider runs it for you.

**Q 5.3 — What does "files as memory" mean, and why is it so common?**

**Answer.** The harness loads an instruction file into the context at session start, and the agent edits it with the normal file tools.
You can read, diff, and version a file, and it needs no extra infrastructure.
The read and write paths are ordinary tool calls, so no new mechanism can fail.
The cost: the harness injects the whole file and cannot rank the parts, so the file must stay small.
Many coding-agent harnesses ship this pattern: one project instruction file that the harness loads at session start.

*Strong answers also mention:* file memory uses the repository review process, so every memory change appears in a diff.

### Tier 2 — Reason

**Q 5.4 — During recall, when does relevance win and when does recency win?**

**Answer.** Relevance decides which entries enter the shortlist.
Recency then orders that shortlist and marks stale entries.
A highly relevant entry from last year ranks above an unrelated entry from yesterday.
But between two versions of the same fact, the newer version wins and must replace the older one.
Trace 12, step 5 shows the division: relevance builds the shortlist, and recency judges inside it.
If recency is the primary rank, recall returns the entries of the last session and little else.

*Strong answers also mention:* a timestamp marks an entry as stale, not only sorts it; some classes of entry need a TTL.

**Q 5.5 — How do you decide what to persist versus what to recompute?**

**Answer.** Persist what is stable and expensive to find again: environment quirks, preferences, and decisions with their reasons.
Recompute what is cheap to derive or quick to change: file contents, test results, branch state.
The deciding factor is the cost of a stale entry.
A stale entry looks exactly like a correct one, and the model uses it; a recomputed fact costs one tool call.
Every persisted fact also needs a consolidation path (Trace 13), and a recomputed fact needs none.
If you are not sure, recompute.

*Strong answers also mention:* persisting the pointer ("tests live under tests/") instead of the volatile value.

**Q 5.6 — Why consolidate memory at session end instead of writing every turn?**

**Answer.** A write at session end can use everything the session learned.
A fact that the session later disproved never reaches the store.
One pass can also remove duplicates and resolve conflicts together (Trace 13, steps 6–8).
A write on every turn commits unverified facts and creates more conflicts.
Extraction also works better on the full transcript: the fix that ended the session matters more than the attempts that failed.
The cost is crash loss, so long sessions save periodic state checkpoints, which are a separate mechanism from memory.

*Strong answers also mention:* a checkpoint saves the complete session state for resume; a memory write saves distilled facts for reuse.

### Tier 3 — Design & Debug

**Q 5.7 — After an API migration, the agent keeps calling the old endpoint in every new session. Walk your diagnosis.**

**Answer.** First read the first turn's assembled context: does the harness inject the old endpoint from memory?
If it does, examine the store.
You find two entries that contradict each other, or one stale entry that no session replaced.
Two entries point at the write path: the harness stored the contradiction as a new entry instead of an update (Trace 13, step 8).
One stale entry points at extraction: no session judged the migration durable enough to write.
Correct the entry, then check the first turn of the next session, not the store alone.

*Strong answers also mention:* the durable fix is a conflict policy, plus a recall eval that replays facts you know are superseded.

**Q 5.8 — Design the memory write policy for a coding agent shared by a whole team.**

**Answer.** Split the stores by scope:

- **Personal preferences:** for each user.
- **Project facts:** shared.
- **Org policy:** read-only.

Then apply these rules:

- Give every entry provenance (the session and the evidence), a timestamp, and a class that sets its TTL.
- Send every write to a shared store through a gate, so a human reviewer approves it before commit.
- Resolve every contradiction with an update, and make deletes soft so the history stays.
- At recall, give each scope its own token budget, so no store takes the space of the others.

*Strong answers also mention:* a shared store is an injection surface, because one harmful entry reaches the context of every teammate.

## Common mistakes & red flags

- **"The agent remembers our last conversation."** Only if the harness wrote at session end and injected at assembly. Check both halves (Traces 12 and 13).
- **"Store everything — storage is cheap."** Recall carries the cost: more entries give worse ranking, more stale facts, and a larger first turn (Trace 12).
- **"Rank memories by recency."** Relevance selects; recency orders the versions and marks stale entries. A recency-first rank replays the last session for every user (Trace 12, step 5).
- **"Just append the new fact."** If the harness stores a contradiction as a new entry, recall later returns both versions. Consolidation must update or delete (Trace 13, step 8).
- **"We persist the transcript as memory."** That is session state, not memory. Without extraction and consolidation, recall returns transcript text instead of facts (Trace 13).
- **"Memory needs a vector database."** Files and key-value stores carry most production memory. A retrieval index earns its place only at corpus scale; retrieval comes later in this book.
