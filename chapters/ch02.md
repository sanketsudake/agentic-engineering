# Chapter 2 — Models & the API Surface

## Why this chapter

Every agent turn ends in one API call: the harness sends the full context, and the model returns sampled tokens.
This chapter zooms into step 3 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) — the model call itself.
The mental model has two parts: the API is stateless, and the stop reason is the control signal that the loop branches on.
Structured output, tool calls, streaming, and prompt caching are all behaviors of this one call.
An engineer who can read a raw request and a raw response can separate a model problem from a harness problem.

## Concepts

**Tokens.** A token is the model's unit of text: a subword chunk of a few characters.
The tokenizer is the fixed mapping between text and tokens.
It belongs to the model, and it differs across model generations.
The API measures everything in tokens: the cost, the context limits, and the output limits.
`POST /v1/messages/count_tokens` returns the exact count for a given model.
Never estimate the count when the number matters.

**Sampling.** The model computes a probability distribution over the next token, picks one token, and repeats.
Temperature is the main control: a low setting concentrates the choice on likely tokens, and a high setting spreads it.
No setting guarantees bit-level determinism.
The same prompt can produce different outputs from run to run.
Treat this variance as a property of the system, and measure it over many runs.

**The Messages API shape.** One endpoint carries everything: `POST /v1/messages`.
Each call is stateless, because the provider keeps no conversation between calls.
A request carries the model name, `max_tokens`, an optional system prompt, the `messages` list, and optional `tools`.
A conversation is the harness resending the entire message list every turn, one turn longer each time.
That is why the input tokens grow every turn, and why prompt caching pays (Trace 6).
Tool use and structured output are features of this endpoint, not separate APIs.

**Stop reasons are control signals.** Every response says why generation ended.
The loop must branch on `stop_reason`.
It must never branch on whether the output looks finished.

| `stop_reason` | Meaning | What the harness does |
|---|---|---|
| `end_turn` | the model finished | return the answer |
| `tool_use` | the model requests tool calls | execute, append results, resend (Trace 4) |
| `max_tokens` | the output limit hit | treat as truncated; never parse as complete |
| `stop_sequence` | a caller-defined string appeared | apply the caller's protocol |
| `pause_turn` | a server-tool turn paused | resend to resume |
| `refusal` | the model declined | read `stop_details`; surface, do not blind-retry |
| `model_context_window_exceeded` | the window is full | trim or compact context, then retry |

**Output limits.** `max_tokens` is a hard cap on everything the model emits in one response: thinking tokens plus visible text.
Thinking tokens are the model's internal reasoning tokens.
The model cannot see the cap, and it does not pace against it.
Generation just stops, mid-sentence or mid-JSON.
[Appendix A](appendices.md#appendix-a--quick-reference-tables) lists the output limit for each model.
The SDKs require streaming for large `max_tokens` values, because a long silent request hits HTTP timeouts (Trace 5).

**System prompts versus user turns.** The system prompt is a separate request field.
The harness sets it, and it stays stable across turns.
It carries the standing frame: the role, the rules, the environment, and the output conventions.
User turns carry the task of the moment and the data that the task needs.
Keep the split clean: a stable prefix caches well (Trace 6), and per-turn data belongs in the user messages after that prefix.

**Model selection is a routing decision.** Providers ship tiers: small, fast, cheap models and large, capable, expensive models.
Which model serves a call is a decision for each call, not one decision for the whole product.

- **Route mechanical steps** to a cheap tier: classification, extraction, and summaries of tool results.
- **Route planning and judgment** to a capable tier.

`GET /v1/models` reports the limits and the capabilities of each model, so a harness can discover these facts instead of hardcoding them.

For volume that no user waits on, the Batch API trades latency for cost: half price, and results within 24 hours.
Each item carries a `custom_id`, because the results can arrive in any order.
[Appendix A](appendices.md#appendix-a--quick-reference-tables) holds the dated model snapshot.

### In other stacks

- **OpenAI:** the chat-completions and the responses endpoints use different field names and roles. Each call still resends the full conversation, so the stateless model is universal.
- **OpenAI:** `finish_reason` carries the stop reason. A production loop branches on it the same way.
- **OpenAI Agents SDK:** `Runner.run()` hides the resend loop. The calls on the wire keep the same shape, and the SDK enforces a `max_turns` limit.
- **LangGraph:** a model node sends the message list from the graph state on every call, which is the full context. Checkpointers store that state in your own infrastructure, never at the provider.
- **All stacks:** several providers support structured output through constrained decoding, where the sampler blocks the tokens that would break the schema. Treat "schema in, valid JSON out" as a pattern, not as one vendor's feature.

## Traces

### Trace 3: What happens when you demand output matching a schema

You ask the model to extract invoice fields, and you demand JSON that matches a schema.

1. **Harness** puts the JSON Schema in the request: `output_config.format` with `type: "json_schema"`.
2. **LLM** compiles the schema into a grammar that the sampler can enforce.
   - The first request with a new schema pays the compilation latency. The provider then caches the compiled grammar for reuse.
3. **LLM** samples under constrained decoding: at each step it masks out the tokens that would break the schema.
4. **LLM** finishes; on a clean stop (`end_turn`) the output is guaranteed to be schema-valid JSON.
5. **Harness** checks the stop reason before it parses the output.
   - `max_tokens` means a truncated prefix, which is invalid. `refusal` means no JSON at all; read `stop_details`.
6. **Harness** parses the output and continues, because validation effort now goes to meaning, not to shape.

The portable alternative is validate-and-retry: the harness instructs the model, parses the reply, and resends with the error text after a failure.
It works on any provider, but it costs retry turns, and it never converges by guarantee.

- **Use constrained decoding** where the provider supports it.
- **Keep validate-and-retry** for the schemas that the constraint engine rejects.

```mermaid
flowchart TD
  A[Schema in request] --> B{Grammar cached}
  B -->|no| C[Compile schema]
  B -->|yes| D[Mask invalid tokens]
  C --> D
  D --> E[Sample constrained output]
  E --> F{Stop reason}
  F -->|end_turn| G[Valid JSON]
  F -->|max_tokens| H[Truncated JSON]
  F -->|refusal| I[No JSON]
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef resource fill:#BE123C,stroke:#9F1239,color:#fff
  class A,G,H,I resource
  class B,F lease
  class C,D,E process
```

*Figure 2.1 — constrained decoding guarantees shape only on a clean stop; two stop reasons escape the schema.*

**Where this can fail**

- **Symptom:** invalid JSON despite structured output.
    - **Cause:** the output hit `max_tokens`, so a valid prefix was cut.
    - **Where to look:** the stop reason and the output token count.
- **Symptom:** prose instead of JSON.
    - **Cause:** a refusal escapes the schema.
    - **Where to look:** `stop_reason: "refusal"` and `stop_details`.
- **Symptom:** the first call with a new schema is slow, and the rest are fast.
    - **Cause:** the provider compiles the schema on first use.
    - **Where to look:** the latency of each request against the schema changes.
- **Symptom:** the API rejects the request.
    - **Cause:** the schema uses features that the constraint engine does not support.
    - **Where to look:** the API error message.

### Trace 4: What happens when the model decides to call a tool

The context carries a `run_tests` tool, and the model needs the test output before it can answer.

1. **Harness** sends the request with the tool definitions in the `tools` field.
2. **LLM** reads the definitions as ordinary input tokens; a schema is a prompt.
3. **LLM** decides during generation that it needs the tool; nothing switches modes.
4. **LLM** samples a `tool_use` content block token by token: an id, the tool name, and the input.
   - The input is model-generated text in the shape of JSON. The API did not build an object for you.
5. **LLM** stops with `stop_reason: "tool_use"`, which is a request to the harness, not an action.
6. **Harness** parses the input as JSON.
   - Field order, whitespace, and escaping vary from run to run, so string matching is never safe.
7. **Harness** executes the tool and answers with a `tool_result` block in the next request.

```mermaid
sequenceDiagram
  autonumber
  participant Harness
  participant LLM
  Harness->>LLM: context plus tool definitions
  LLM->>LLM: reads schemas as tokens
  LLM->>LLM: samples tool_use block
  LLM-->>Harness: name and input JSON
  LLM-->>Harness: stop_reason tool_use
  Harness->>Harness: parse input as JSON
  Harness->>LLM: tool_result in next request
```

*Figure 2.2 — the tool call is sampled text plus a stop reason; everything after arrow 5 is harness work.*

**Where this can fail**

- **Symptom:** the tool input does not parse.
    - **Cause:** free generation drifted from the schema.
    - **Where to look:** the raw block; `strict: true` on the definition makes the input schema-guaranteed through constrained decoding.
- **Symptom:** the loop returns text while a tool call sits unhandled.
    - **Cause:** the harness branched on the presence of text instead of on `stop_reason`.
    - **Where to look:** the branch condition of the loop against the response blocks.
- **Symptom:** extraction breaks after a model upgrade.
    - **Cause:** the code runs regexes over generated text, and the formatting shifted.
    - **Where to look:** the parsing code; replace the string matching with JSON parsing.
- **Symptom:** several `tool_use` blocks in one response.
    - **Cause:** this is not a failure; the model requests parallel tool calls.
    - **Where to look:** the next request, which must carry all the results in one user message.

### Trace 5: What happens when a response streams

The harness streams the response, so the user sees the text while the model generates it.

1. **Harness** sends the request with `stream: true`; the connection stays open for server-sent events.
2. **LLM** sends `message_start` with the message id, the model, and the input-token usage.
3. **LLM** opens a content block with `content_block_start`.
4. **LLM** sends `content_block_delta` events; the content of the block arrives in fragments.
   - The input of a tool call arrives as partial JSON fragments. It parses only when it is complete.
5. **Harness** renders the text deltas immediately. It buffers the tool-input deltas until the block closes.
6. **LLM** closes the block with `content_block_stop`; more blocks can follow.
7. **LLM** sends `message_delta`, which carries the stop reason and the final usage counts.
8. **LLM** sends `message_stop`; the harness now assembles the same message that a non-streaming call returns.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  Harness->>LLM: POST with stream true
  LLM-->>Harness: message_start
  LLM-->>Harness: content_block_start
  LLM-->>Harness: content_block_delta
  Note over Harness,LLM: deltas repeat per block
  Harness-->>User: render text live
  LLM-->>Harness: content_block_stop
  LLM-->>Harness: message_delta with stop reason
  LLM-->>Harness: message_stop
  Harness-->>User: complete message
```

*Figure 2.3 — the stop reason and usage arrive in message_delta, near the end; a loop that reads only deltas misses its control signal.*

**Where this can fail**

- **Symptom:** the stream dies during an answer.
    - **Cause:** an error event arrived mid-stream, after the HTTP 200.
    - **Where to look:** the last event received; discard or retry the partial content, and never show it as complete.
- **Symptom:** JSON parse errors during tool calls.
    - **Cause:** the harness parsed the input deltas before `content_block_stop`.
    - **Where to look:** the point where the accumulator hands the input to the parser.
- **Symptom:** the loop never sees a stop reason.
    - **Cause:** the handler consumed the text deltas and ignored `message_delta`.
    - **Where to look:** the events that the handler covers.
- **Symptom:** long generations fail with timeouts.
    - **Cause:** a non-streaming call held one HTTP request open too long; the SDKs require streaming for large `max_tokens`.
    - **Where to look:** the stream flag of the request and the SDK error.

### Trace 6: What happens when a prompt cache hits — and misses

The harness marks its long, stable prompt prefix for caching, and it runs a session of two turns.

1. **Harness** adds `cache_control: {type: "ephemeral"}` to the last stable block; a request allows up to 4 breakpoints.
2. **LLM** renders the request in a fixed order: the tools, then the system prompt, then the messages.
3. **LLM** looks for the longest cached prefix that ends at a breakpoint; turn one misses.
4. **LLM** processes the full prefix and writes the cache entries at the breakpoints.
   - A write costs more than plain input: 1.25× for the default lifetime of 5 minutes, and 2× for the option of 1 hour.
5. **Harness** sends turn two: the same prefix, plus the new messages appended at the end.
6. **LLM** hits the cache and reads the prefix at roughly 0.1× the input price. It processes only the new suffix in full.
7. **LLM** reports the split in `usage`; a nonzero `cache_read_input_tokens` proves that a hit happened.
8. **Harness** watches the prefix, because any byte that changes inside it invalidates everything after that byte.

```mermaid
flowchart TD
  A[Request arrives] --> B[Render tools system messages]
  B --> C{Cached prefix found}
  C -->|miss| D[Process full prefix]
  C -->|hit| E[Read prefix from cache]
  D --> F[Write cache at breakpoints]
  F --> G[Process new suffix]
  E --> G
  G --> H[Usage shows the split]
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef resource fill:#BE123C,stroke:#9F1239,color:#fff
  class A,B,D,G,H process
  class C lease
  class E,F resource
```

*Figure 2.4 — the cache is a prefix match over the rendered request; append-only prompts hit, edited ones miss.*

**Where this can fail**

- **Symptom:** `cache_read_input_tokens` is zero on every repeat.
    - **Cause:** something early in the prefix changes on each call — a timestamp in the system prompt, a reordered tool list, or a per-request id.
    - **Where to look:** two rendered requests, diffed byte by byte.
- **Symptom:** caching does nothing for a short prompt.
    - **Cause:** the prefix is below the minimum cacheable size, which is 512–4096 tokens and depends on the model; the provider then caches nothing and reports no error.
    - **Where to look:** the token count of the prefix against the minimum for the model.
- **Symptom:** the hits stop after a pause.
    - **Cause:** the cache entry expired; the default lifetime is 5 minutes.
    - **Where to look:** the gap between the requests; consider `ttl: "1h"`.
- **Symptom:** the bill went up after you enabled caching.
    - **Cause:** the prefix changes on each call, so every call pays the write premium and no call earns the read discount.
    - **Where to look:** the write and read fields of `usage` over a day of traffic.

## Questions

### Tier 1 — Explain

**Q 2.1 — What is a token, and why can the same prompt produce different outputs?**

**Answer.** A token is the model's unit of text: a subword chunk that the model-specific tokenizer maps.
The model generates by sampling from a probability distribution over the next token, one token at a time.
Sampling is random by design, and temperature scales how far the choice spreads from the most likely token.
No setting guarantees bit-level determinism, so identical prompts can produce different outputs.

*Strong answers also mention:* token counts differ across model generations; use the count-tokens endpoint, not an estimate.

**Q 2.2 — Name the stop reasons a production loop must handle, and what each one signals.**

**Answer.** A production loop must handle seven stop reasons:

- `end_turn` — the model finished; return the answer.
- `tool_use` — execute the tools and resend.
- `max_tokens` — the output is truncated; never parse it as complete.
- `stop_sequence` — a caller-defined string appeared; apply the caller's protocol.
- `pause_turn` — resend the request to resume a server-tool turn.
- `refusal` — read `stop_details` and surface the refusal.
- `model_context_window_exceeded` — trim or compact the context, then retry.

The loop branches on this field, never on whether the text looks finished.
A loop that handles only `end_turn` and `tool_use` fails quietly on truncation and on refusals.

*Strong answers also mention:* in streaming, the stop reason arrives in `message_delta`, near the end of the event sequence.

**Q 2.3 — What does `max_tokens` cap, and what happens when generation hits it?**

**Answer.** It is a hard cap on everything the model emits in one response: the thinking tokens plus the visible text.
The model cannot see the cap and does not pace against it; the output just stops, mid-sentence or mid-JSON.
The response reports `stop_reason: "max_tokens"`, and the harness must treat the content as truncated.
Schema-constrained output becomes invalid the same way, because a valid prefix is not valid JSON.

*Strong answers also mention:* large caps require streaming in the SDKs, because a long silent request hits HTTP timeouts.

**Q 2.4 — What belongs in the system prompt, and what belongs in user turns?**

**Answer.** The system prompt carries the standing frame: the role, the rules, the environment, and the output conventions.
It is a separate request field that the harness owns, and it stays stable across turns.
User turns carry the task of the moment and the data of that task.
The split matters twice.
The model reads the system frame as standing policy, and a stable prefix is what makes the cache hit (Trace 6).

*Strong answers also mention:* user-turn content is untrusted input; standing rules do not belong where task data can rewrite them.

### Tier 2 — Reason

**Q 2.5 — When do you choose constrained decoding, and when validate-and-retry?**

**Answer.** Choose constrained decoding wherever the provider supports your schema: shape errors go to zero, and it costs no retry turns.
Validate-and-retry remains for the schemas that the constraint engine rejects, and it is the portable pattern across providers.
Neither method removes semantic validation, because a schema-valid field can still hold a wrong value.
Constrained decoding also still needs a check of the stop reason, because truncation and refusal both escape the schema (Trace 3).

*Strong answers also mention:* schema compilation makes the first request slower; keep the schemas stable so the compiled grammar is reused.

**Q 2.6 — Why must the harness parse tool input as JSON instead of matching strings?**

**Answer.** The input is model-generated text, because the model sampled it token by token.
Field order, whitespace, escaping, and formatting can all vary from run to run and across model versions.
A regex that works today depends on formatting that the provider never promised.
Parse the JSON, validate it against the schema, and use `strict: true` where constrained decoding must guarantee the shape.

*Strong answers also mention:* `strict: true` needs `additionalProperties: false` and a `required` list, and it removes syntactic failures, not semantic ones.

**Q 2.7 — In a streaming handler, why buffer tool-call input until the block stops, and which event carries the stop reason?**

**Answer.** The input of a tool call arrives as partial JSON fragments spread across delta events.
Any prefix of a JSON document is invalid JSON, so an early parse fails — or half-succeeds, which is worse.
Buffer the fragments until `content_block_stop`, then parse once.
The stop reason and the final usage arrive in `message_delta`, just before `message_stop`.
A handler that reads only the content deltas misses the control signal of the loop.

*Strong answers also mention:* mid-stream error events can arrive after HTTP 200; never show partial content as complete.

**Q 2.8 — Your prompt has tools, a system prompt, and history. What breaks the cache, and how do you order content?**

**Answer.** The cache is a prefix match over the rendered request, in a fixed order: the tools, then the system prompt, then the messages.
Any changed byte invalidates everything after it, so an edit to the tool list invalidates the system prompt and all the history behind it.
Order the content by stability: the tool definitions and the system prompt stay stable, and the harness appends the dynamic content at the end of the messages.
Never put a timestamp, a request id, or a per-user value early in the prefix.
Verify the result with `usage.cache_read_input_tokens`; zero across repeats means that something in the prefix changes on each call.

*Strong answers also mention:* writes cost 1.25–2× input; a prefix that changes on every call makes caching a net loss.

### Tier 3 — Design & Debug

**Q 2.9 — A team enabled prompt caching and the bill went up. Walk your diagnosis.**

**Answer.** Pull the `usage` fields for a day of traffic first, and compare the cache reads against the writes.
This failure has one signature: a write on every call, and reads near zero.
The team pays the 1.25–2× write premium and earns none of the 0.1× reads.

Then find what changes the prefix: render two identical requests and diff them byte by byte.
The usual causes are a timestamp or a session id in the system prompt, and a tool list built from an unordered set.
Per-request content placed before the history does the same.
Also check the size, because a prefix under the minimum cacheable size of the model caches nothing.
Fix the prefix, then verify again that `cache_read_input_tokens` is nonzero on repeats.

*Strong answers also mention:* alert on the cache-read ratio in production, so a regression surfaces as a metric, not as a bill.

**Q 2.10 — Design model selection for an agent that triages support tickets and drafts replies.**

**Answer.** Split the pipeline by the weight of each decision, and route for each call.

- **Classification and field extraction** are mechanical: a cheap tier handles them, and structured output makes the results checkable.
- **Drafting a reply and deciding on an escalation** need judgment, so a capable tier earns its cost there.
- **Volume that no user waits on** — nightly re-triage and eval runs — goes through the Batch API at half price, keyed by `custom_id`.

Wire the routing as a harness decision with a model name for each call, and hold the quality with an eval suite for each tier.

*Strong answers also mention:* if a wrong answer from a cheap tier is easy to detect, route cheap and verify; if it fails silently, pay for the stronger model first.

## Common mistakes & red flags

- **"The API remembers our conversation."** Each call is stateless, and the harness resends everything. "The model forgot" almost always means that the harness dropped it.
- **"Structured output means we can skip validation."** Truncation (`max_tokens`) and refusals escape the schema. Check the stop reason before you parse, and validate the meaning after.
- **"We extract tool calls with a regex."** The tool input is model-generated JSON, and the formatting varies from run to run. Parse it; `strict: true` guarantees the shape, and a regex never does.
- **"`max_tokens` caps the visible text."** It caps the thinking tokens plus the text, and the model can neither see it nor pace against it. A truncated response says so only in the stop reason.
- **"We enabled caching, so we save money."** The cache is a prefix match, and one early byte change invalidates everything after it. Verify the hits in `usage.cache_read_input_tokens`.
- **"Streaming is cosmetic."** The SDKs require streaming for large outputs. Streaming is also where the harness must handle partial tool inputs and mid-stream errors.
- **"We standardized on one model."** Model choice is a routing decision for each call. Route the mechanical steps to a cheap tier, and the judgment to a capable tier.
