# Chapter 8 — Operating Coding Agents: Workflows

## Why this chapter

[Chapter 7](ch07.md) opened the harness; this chapter operates it.
You are the operator: the [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop becomes a process with gates.
The mental model: treat the agent as a capable contractor.
The spec is the contract, the checkpoints sit where a mistake is still cheap to correct, and the PR is the deliverable.
Gates placed early correct a wrong direction after one reading; a review of the final diff pays for the whole run first.

## Concepts

### Spec-driven development

Spec-driven development starts a run with a document, not with code.
The spec states the intended behavior, the boundaries, and how to verify the result.
The agent turns the spec into a plan:
which files change, in what order, and what test proves each step.
The plan is the contract for the run.

Review the plan, not just the diff.
A diff shows what changed; only the plan shows what should have changed.
Rejecting a wrong plan costs one reading;
rejecting a wrong diff costs the whole run and the review that found it.
Trace 21 walks a feature from the spec to the merge.

A complete spec also fixes how the run may end:

- **Objective and non-goals:** the outcome required, and what must not change.
- **Acceptance criteria:** observable behavior, with the edge cases.
- **Checks:** the exact tests, linters, and builds that the agent must run.
- **Terminal states:** complete, retry, no-op, or escalate to a human.
- **Evidence:** the changed artifacts, plus every check that passed, failed, or was skipped.
- **Rollback:** the smallest safe way to undo the change.

Make "no-op" and "escalate" legitimate outcomes.
An agent that may not stop or ask reports plausible work instead of reporting that it is stuck.
A vague spec is not neutral: the run automates the ambiguity.

### Plan-then-execute and decomposition

Decompose a task when one review cannot check all of it at once,
or when its parts are independent enough to verify separately.
Split along review boundaries, not code boundaries.
Each part must end at a checkpoint —
a state that a human can verify cheaply and roll back to safely.
Examples: a passing test, a compiling module, a small PR.

Small tasks do not earn decomposition:
the briefs and the merges cost more than the review that they save.
The test: if the whole diff fits in one honest review, keep it whole.

### Subagent delegation

A subagent is a second agent that the harness starts to run its own [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop.
In Claude Code a file at `.claude/agents/<name>.md` defines it, and its frontmatter names the tools, the model, and the permission mode.

Three events start it:

- The model matches its description.
- The user names it.
- The model calls the agent tool.

The important property is the isolated context.
The subagent starts empty:
it receives the task brief and its own instructions, and nothing else.
It cannot read the parent conversation, and the parent reads only its final report.
So the brief's quality decides the output's quality:
what the brief does not say does not exist for the subagent.

Delegate work that is self-contained and needs a lot of context:
broad searches, mechanical batches, independent subtasks.
Keep work inline when it needs the conversation context or touches one file.
Trace 22 walks one delegation.

### Draw the orchestration, then have the agent build it

When one delegation is not enough, the shape of the work becomes the thing you author.
Draw it first, then give the drawing to the coding agent and have it write the runner script.
A drawing is a specification, so the drawing decides the quality of the result.

Put five things on it, because each missing one is a defect that appears at run time.

1. **The role and model of each node.** Give the expensive model to the nodes that judge, and a cheap one to the mechanical nodes.
2. **The data contract on each edge.** Write the schema that crosses it, never a description of the schema.
3. **The acceptance criteria inside each gate.** A gate labelled "Pass?" with no written criteria passes everything.
4. **A retry cap on every feedback edge.** Three attempts is a usual limit; an uncapped retry edge is an endless loop with extra steps.
5. **What each node records.** Tokens and elapsed time for each node, or you cannot find the expensive one later.

Bound the fan-out width in the drawing.
A width that grows with the input is the common cost defect, because the bill grows with it and no step reports the growth.

### Parallel work in worktrees

A git worktree gives one branch its own working directory in the same repository.
Give each agent its own worktree, always.
Two agents in one checkout overwrite each other's edits, and each one reads the other's half-finished state as the true state of the code.

Parallel runs change the operator's job: you stop watching one loop and start merging several.

Three rules keep the merges safe.

- Keep each commit small, scoped, and limited to one logical change.
- Rebase onto the mainline before you merge.
- Give one person ownership of the merge order.

Two parallel agents that own the same files are a planning defect, not a merge problem.

### CI agents and review loops

An agent can also run with no human present.
In the CI pattern a trigger fires on an event:
a failing check, a review request, or a label.
A job then starts the harness with a fixed prompt.
The run is trigger → checkout → diagnose → fix → push → report.
The setup gives the job the least privilege that works:
each needed call has an explicit allow rule, and the harness denies the rest ([Chapter 7](ch07.md)).
The credentials reach one repository and one branch.

The review loop closes the workflow.
An agent's output is a PR like any other: same review bar, same CI, same ownership.
Review threads work in both directions:
an automated reviewer comments on an agent PR,
and an agent can read those comments, fix each issue, and resolve the thread.
One human decision remains: the merge.

### Steer vs let-run

Two modes exist.

- **Interactive operation:** you watch the transcript and interrupt.
- **Autonomous operation:** you set the gates before the run and read the report at the end.

The line between them is the difference between a decision and its execution.

- Steer while the agent decides: which approach, which files, which interface.
  A wrong direction costs more with every turn that follows it.
- Let the agent run when the direction is fixed and only the labor remains.
  An early interrupt is the cheapest correction in the workflow.

Every step toward autonomy trades live attention now for review work later,
so more autonomy needs stronger verify steps and tighter gates.

### In other stacks

- **Claude Agent SDK:** the same harness as an in-process library — it fits the CI automation in Trace 23.
- **OpenAI Agents SDK:** it ships no coding harness; you build the operator loop yourself from `Runner.run()`, `max_turns`, and guardrails.
- **OpenAI Agents SDK:** handoffs make the delegation in Trace 22 a built-in operation between agents.
- **LangGraph:** plan-then-execute becomes an explicit graph — the plan gate is a node, and conditional edges encode the review loop.
- **LangGraph:** checkpointers store the state at every superstep, so any step can become a checkpoint that a human reviews.
- The other half of operating many agents — orchestrators, handoffs, shared artifacts — comes later in this book.

## Traces

### Trace 21: What happens when a feature ships spec-first

You ask the agent to add rate limiting to an API; the session starts with a document, not a diff.

1. **User** states the goal and its constraints, not the implementation.
2. **LLM** reads the codebase read-only, then drafts the spec and the plan: behavior, files to change, risks, and tests.
   - In Claude Code this is plan mode ([Chapter 7](ch07.md)): a read-only stance until the plan is approved.
3. **User** reviews the plan and corrects the direction — the cheapest gate in the workflow.
4. **LLM** implements the approved plan step by step, in small commits.
5. **Harness** gates each write and command exactly as in [Trace 18](ch07.md#trace-18-what-happens-when-the-harness-gates-a-dangerous-action).
6. **LLM** runs the verify step of the plan: tests, lints, a build.
7. **Harness** loops steps 4–6 until the verify step passes.
8. **User** reads the PR diff against the plan, not against memory.
9. **User** sends review comments; the loop resumes at step 4 with the comments in context.
10. **User** merges once the plan, the diff, and the checks agree.

```mermaid
flowchart TD
  SPEC[Write the spec] --> PLAN[Draft the plan]
  PLAN --> GATE[Plan review]
  GATE -->|revise| PLAN
  GATE -->|approve| IMPL[Implement a step]
  IMPL --> VER[Verify tests]
  VER -->|fail| IMPL
  VER -->|pass| PR[Open the PR]
  PR --> REV[Code review]
  REV -->|comments| IMPL
  REV -->|approve| MERGE[Merge]
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef resource fill:#BE123C,stroke:#9F1239,color:#fff
  class SPEC,PLAN,IMPL,MERGE process
  class GATE,VER,REV lease
  class PR resource
```

*Figure 8.1 — two gates, not one: the plan review catches direction, the code review catches execution.*

**Where this can fail**

- **Symptom:** the implementation departs from the approved plan.
    - **Cause:** a long session compacted the plan out of the context.
    - **Where to look:** the token counts per turn, and whether the plan persists as a file.
- **Symptom:** plan reviews approve everything, and the diffs still come back wrong.
    - **Cause:** the plans are too vague to falsify — no file list, no test plan.
    - **Where to look:** the plan text; a reviewable plan names files and proofs.
- **Symptom:** the agent declares the task done, then CI fails.
    - **Cause:** the run skipped the verify step, or its failure never reached the context.
    - **Where to look:** the transcript, for the test command and its raw output.
- **Symptom:** one large PR that nobody can review.
    - **Cause:** no decomposition; the whole feature shipped as one checkpoint.
    - **Where to look:** the step sizes in the plan against the final diff size.

### Trace 22: What happens when work is delegated to a subagent

During a task, the parent agent needs a broad search that would fill its own context with file contents.

1. **LLM** identifies a self-contained subtask and decides to delegate it.
2. **LLM** assembles the brief: the goal, the constraints, and the report shape that it wants back.
3. **Harness** selects the subagent definition: by a description match, by name, or by the agent tool.
4. **Harness** starts the subagent with a fresh context: the brief plus its own instructions and tools.
   - No part of the parent conversation goes across; the brief is the entire interface.
5. **Sub** runs its own [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop: it reads, searches, and iterates inside its own context window.
6. **Sub** ends and returns one final report; its intermediate tool results stay in its own context.
7. **Harness** appends only the report to the parent context, as a tool result.
   - The parent pays the tokens of one report for dozens of file reads.
8. **LLM** integrates the conclusion and continues the parent task.

```mermaid
sequenceDiagram
  autonumber
  participant LLM
  participant Harness
  participant Sub
  participant Env
  LLM-->>Harness: agent call with brief
  Harness->>Sub: spawn with fresh context
  Sub->>Env: read and search
  Env-->>Sub: raw results
  Sub->>Sub: loop until done
  Sub-->>Harness: one final report
  Harness->>LLM: report as tool result
  LLM-->>Harness: continue parent task
```

*Figure 8.2 — the raw results stop at the Sub lane; the parent pays one report for a whole search.*

**Where this can fail**

- **Symptom:** the subagent returns confident but irrelevant work.
    - **Cause:** a constraint lived only in the parent conversation and never entered the brief.
    - **Where to look:** the brief text against the conversation that produced it.
- **Symptom:** the parent redoes the search itself.
    - **Cause:** the brief never specified the report shape, so the answer came back unusable.
    - **Where to look:** the report format that the brief requested.
- **Symptom:** no context savings appear.
    - **Cause:** the subagent returned the raw results instead of a conclusion.
    - **Where to look:** the report's token count in the parent transcript.
- **Symptom:** the delegation costs more than the same work inline.
    - **Cause:** an open-ended brief and no turn cap on the subagent.
    - **Where to look:** the subagent's turn count and its `maxTurns` setting.

### Trace 23: What happens when a CI agent handles a pull request

The tests on a PR fail at night, and a CI job starts an agent to fix them with no human present.

1. **CI** triggers on the failing check and starts the harness with a fixed prompt and the PR reference.
2. **Harness** starts in a non-interactive mode: each needed call has an allow rule, and the harness denies the rest.
3. **Harness** checks out the PR branch in a clean runner, with credentials scoped to this repository and branch.
4. **LLM** reads the failure: the CI log, the failing test, and the diff that introduced it.
5. **LLM** proposes a fix; the harness gates each call against the allow rules.
6. **LLM** runs the test suite and reads the real result, not a claim of success.
7. **Harness** pushes the fix commit to the PR branch — the one write that the credential permits.
8. **CI** re-runs the checks on the new commit.
9. **Harness** reports as a PR comment: what it found, what it changed, what it could not fix.
10. **User** still owns the merge; the push of the agent is a proposal, not a decision.

```mermaid
sequenceDiagram
  autonumber
  participant CI
  participant Harness
  participant LLM
  participant Env
  CI->>Harness: trigger with prompt
  Harness->>Env: checkout PR branch
  Harness->>LLM: failure log context
  LLM-->>Harness: fix tool calls
  Harness->>Env: apply and test
  Env-->>Harness: real test result
  Harness->>Env: push fix commit
  CI->>CI: rerun checks
  Harness-->>CI: report as comment
```

*Figure 8.3 — no human lane exists: the permission boundary and the report have to do the human's job.*

**Where this can fail**

- **Symptom:** the run hangs, then times out.
    - **Cause:** an unmatched call waits for an answer that no human is there to give.
    - **Where to look:** the last pending call in the transcript, and the session's permission mode.
- **Symptom:** CI goes green because the agent weakened the test.
    - **Cause:** the prompt stated the goal as "make checks pass", not "preserve behavior".
    - **Where to look:** the diff to the test files, and the prompt's goal wording.
- **Symptom:** the agent and another bot push commits to each other without end.
    - **Cause:** the trigger fires on the agent's own pushes.
    - **Where to look:** the trigger filters, and the commit author on each run.
- **Symptom:** the job's token could have done far more than push.
    - **Cause:** a broad credential where a branch-scoped one was needed.
    - **Where to look:** the token's scopes and the runner's egress rules.

## Questions

### Tier 1 — Explain

**Q 8.1 — What does "review the plan, not just the diff" mean, and why is it cheaper?**

**Answer.** The plan states which files change, in what order, and what test proves each step.
Reviewing it catches a wrong direction before any code exists, at the cost of one reading.
A diff review catches the same wrong direction only after the run has spent the tokens.
Both gates stay: the plan review checks direction, the code review checks execution.

*Strong answers also mention:* a plan is only reviewable if it is falsifiable — it must name files and proofs.

**Q 8.2 — What context does a subagent receive, and what does it never see?**

**Answer.** It receives the task brief plus its own definition: instructions, tools, model, permission mode.
It never reads the parent conversation, and the parent never reads its intermediate tool results.
Only the final report crosses back.
So the brief is the entire interface, and its quality decides the output's quality.

*Strong answers also mention:* this isolation is the purpose — it keeps the parent's context clean ([Chapter 3](ch03.md)).

**Q 8.3 — Why one agent per git worktree?**

**Answer.** A worktree gives each branch its own working directory in the same repository.
Two agents that share one checkout overwrite each other's edits,
and each one reads the other's half-finished state as a fact about the code.
Separate worktrees keep each agent's files consistent, and the merge becomes an explicit, ordered step.

*Strong answers also mention:* parallel agents should also own separate file areas, or the merge inherits the conflict.

**Q 8.4 — Why must a CI agent's setup never rely on ask rules?**

**Answer.** An ask rule prompts a human, and in CI no human is there to answer.
The run hangs until it times out, and the failure looks like slowness, not policy.
Unattended runs need an explicit allow for every required call and automatic denial for the rest.
Each denial should fail the run loudly, with the transcript attached.

*Strong answers also mention:* [Trace 18](ch07.md#trace-18-what-happens-when-the-harness-gates-a-dangerous-action) shows why deny and ask still apply in every mode — CI only removes the person who answers.

### Tier 2 — Reason

**Q 8.5 — When do you delegate a subtask to a subagent, and when do you keep it inline?**

**Answer.** Delegate when the subtask is self-contained and needs a lot of context:
broad searches, mechanical batches, work whose intermediate output would fill the parent context window.
Keep it inline when it depends on the conversation context, touches one file, or is faster to do than to specify.
Delegating costs a complete brief; inline work costs extra content in the parent context.
Pick whichever cost is smaller for this subtask.

*Strong answers also mention:* if a correct brief takes longer to write than the task takes to do, delegation has negative value.

**Q 8.6 — A subagent did exactly what its brief said and the result is still wrong. Whose failure is that?**

**Answer.** The parent's.
The subagent's world is the brief; a constraint that never entered it was never given.
The fix is not a better subagent but a better brief:
goal, constraints, exclusions, and the exact report shape.
Treat a brief as a reviewed artifact, in the same way as a tool schema.

*Strong answers also mention:* recurring brief omissions belong in the subagent's own instruction file, so every future brief inherits them.

**Q 8.7 — How do you decide between steering a session and letting it run?**

**Answer.** Split the task into decisions and execution.
Steer at the decisions — approach, interfaces, file layout — because a wrong choice costs more with every turn after it.
Let it run during the execution, when the direction is fixed and only the labor remains.
More autonomy is a trade: less live attention now, more verification and review work at the end.

*Strong answers also mention:* an early interrupt is the cheapest correction available; waiting because the run already cost you time is the expensive habit.

**Q 8.8 — Why should agent-written code go through the same PR review as human code?**

**Answer.** The review bar protects the codebase, and the risk in a change does not depend on who wrote it.
A separate, softer path for agent PRs turns high agent output into unreviewed risk.
The same bar also closes the loop:
review comments and bot threads are inputs that the agent can read, fix, and resolve.
The human decision then sits where it belongs — at the merge.

*Strong answers also mention:* higher agent volume argues for stronger automated review, not weaker human review.

### Tier 3 — Design & Debug

**Q 8.9 — Your team's spec-first workflow keeps producing correct plans and wrong code. Walk your diagnosis.**

**Answer.** First check whether the plan survives the run: in a long session, compaction can drop it from the context.
Persist the plan as a file and instruct the agent to re-read it at each step.
Then check the verify step: does the transcript show the tests running, with real output, at each step?
A verify step that never runs proves nothing.
Then find the first point where the diff departs from the plan.
That point usually shows where the context was lost, or where a step was too big.

*Strong answers also mention:* a hook ([Trace 19](ch07.md#trace-19-what-happens-when-a-hook-fires)) can enforce the verify step deterministically, instead of trusting the model to run it.

**Q 8.10 — Design the permission and credential boundary for a CI agent that fixes failing PRs.**

**Answer.** Start from what the job must do: read the repository, run tests, edit files, push one branch, comment on the PR.

- Allow exactly those calls; deny everything else, and fail the run loudly on any denial.
- Scope the credential to the single repository, with write access limited to the PR branch and the comments, never the default branch.
- Run in a disposable container, with egress limited to the hosts that the build needs.
- Filter the trigger so the agent's own pushes never start it again, and keep the merge human.

*Strong answers also mention:* the prompt is part of the boundary — "preserve behavior" prevents the test-weakening fix that permissions cannot catch.

## Common mistakes & red flags

- **"The diff looked fine, so we shipped it."** A clean diff can execute a wrong plan perfectly. Review the plan for direction, the diff for execution.
- **"The subagent knows what we discussed."** It receives the brief and its own instructions, and nothing else. A missing constraint is the parent's defect.
- **"Run all three agents in the same checkout."** They overwrite each other's edits and read half-finished state as fact. One worktree per agent.
- **"The CI agent can ask if it's unsure."** Nobody answers in CI. Use explicit allows, deny the rest, and fail loudly on a denial.
- **"It's agent code, so it needs a special review process."** It is a PR like any other: same bar, same checks, same ownership.
- **"Don't interrupt it, the run is almost done."** If the direction is wrong, the rest of the run adds more waste. Steer at the decisions, early.
- **"Delegate everything, context is precious."** Delegation costs a full brief and loses the conversation context. Small edits that depend on context are cheaper inline.
