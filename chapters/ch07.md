# Chapter 7 — Inside a Coding-Agent Harness

## Why this chapter

The harness decides most of a coding agent's behavior before the model generates one token.
Settings, instruction files, permission rules, hooks, and skills shape every turn.
An engineer who knows where each one lives can change the agent's behavior without editing a prompt.
This chapter zooms into steps 1, 4, and 9 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task).
It shows what the harness builds at session start, how it gates a tool call, and what it fires after one.
The mental model: the harness is a policy engine around the loop.
Configuration goes in, and gated actions come out.
Claude Code is the worked example throughout, and the mechanisms are general.
Level emphasis: [L1]–[L2]; no (L3) sections in this chapter.

## Concepts

### The session startup surface

Two kinds of files configure a coding agent, and the harness merges them differently.
**Settings** are machine-readable policy: permissions, hooks, and environment values.
They resolve by *precedence*: a higher layer overrides a lower layer, key by key.
In Claude Code the order is
managed policy → CLI arguments → `.claude/settings.local.json` → `.claude/settings.json` → `~/.claude/settings.json`.
The same pattern applies elsewhere: org policy overrides the invocation, the invocation overrides the project, and the project overrides the user.

**Instruction files** are the natural-language memory that the model reads.
They *concatenate*: one file never replaces another.
Claude Code loads CLAUDE.md files broadest-first:
managed → user `~/.claude/CLAUDE.md` → project `./CLAUDE.md` → `./CLAUDE.local.md`.
All of them enter the context together.
A project file cannot delete a user instruction; it can only add to it.

`@path` imports pull in other files, to a maximum depth of 4.
A subdirectory CLAUDE.md file loads on demand, when the agent works in that directory.

The difference matters for debugging.
A wrong permission means a settings layer that you forgot.
A contradictory behavior means two instruction files that both apply.
Trace 17 walks through the full startup sequence.

### The permission model

The harness decides which tool calls run.
It evaluates three inputs in a fixed order: the hooks, the rules, and the permission mode.

**Rules** name a tool, or a tool with a specifier, such as `Bash(rm *)`.
They live in three lists: `deny`, `ask`, and `allow`.
The harness checks the lists in that order, and the first match decides.
Specificity has no effect.
A broad deny rule overrides a precise allow rule, because the harness checks the deny list first.

**Modes** supply the default when no rule matches.
Claude Code ships six modes:

- `default` — reads run, and everything else asks.
- `acceptEdits` — file edits approve automatically.
- `plan` — the agent reads and plans, but changes nothing.
- `auto` — a classifier gates each call.
- `dontAsk` — the harness denies an unmatched call instead of prompting for it.
- `bypassPermissions` — everything that no rule denies runs.

Deny rules and explicit ask rules apply in every mode, including `bypassPermissions`.
A mode is a stance for one session; rules are policy that outlives the session.

**Hooks** run *before* the harness evaluates the rules.
A PreToolUse hook that exits 2 blocks the call, even when an allow rule matches.
A hook that answers "allow" cannot override a deny rule or an ask rule.
The full order is therefore: hook, then deny, then ask, then allow, then the mode default.

### Hooks: the extension seam

A hook runs your own code at a fixed point in the session.
The handler is a shell command, an HTTP call, or an MCP tool.
Settings bind the handler to a lifecycle event, and a matcher selects which occurrences of that event fire it.
Claude Code exposes about thirty events.
The core set to know is
`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `PreCompact`, and `SessionEnd`.
Learn the shape, not the list: an action is about to happen or has just happened, and your handler can inspect it or block it.

The handler's exit code carries the decision.
Exit 0 means success.
On exit 0, stdout enters the context only for prompt events and session events.
Exit 2 means block: the action stops, and this block overrides every rule, including an allow rule.
A handler can also return JSON:
`permissionDecision: allow|deny|escalate` on PreToolUse, or `continue: false` to end the turn.

A hook is your own code, and it behaves the same way every time inside a loop where the model's output varies.
Typical handlers format a file after an edit, audit a command before it runs, or send a notification on stop.

### Skills and slash commands

A skill is an instruction file that the harness loads on demand.
In Claude Code it is `<dir>/skills/<name>/SKILL.md` with YAML frontmatter:
`name`, `description`, `when_to_use`, optional `allowed-tools`, and more.
The harness finds skills in layers: enterprise, then personal `~/.claude/skills`, then project `.claude/skills`.

The key mechanism is **progressive disclosure**.
Only each skill's name and description stay in the context at all times.
The body loads when the user types a slash command, or when the model matches the task against a description.
The body then stays in the context for the rest of the session.
Sidecar files load later still, and only when the instructions direct the model to read them.
A skill that nobody invokes costs only its description, so hundreds of skills stay affordable.

Slash commands (`.claude/commands/<name>.md`) use the same mechanism as skills.
The `$ARGUMENTS` and `$N` placeholders substitute the text that the user typed.
A `` !`cmd` `` line injects shell output into the loaded body.

### Sandbox boundaries

The permission gate controls *which* calls run.
It cannot control what a running process does.
An approved script can still read any file that the operating system permits.
The second boundary belongs to the operating system: containers, restricted filesystems, network egress rules, or a dedicated sandbox around the shell.

The two layers answer different questions.
The harness gate answers "should this intent proceed?", and it can ask a human.
The operating-system sandbox answers "what can this process touch?", and it asks no one.
A safe setup uses both layers.
Rules and hooks stop a bad intent at low cost.
The sandbox limits the damage that a process can do when the rules miss it.

An attacker can also steer the model through the content that the model reads.
That problem comes later in this book.

### In other stacks

- **Claude Agent SDK:** Claude Code's loop as an in-process library — the same context management, hooks, subagents, MCP, permissions, and skills, which you embed in your own service.
- **OpenAI Agents SDK:** it ships no full coding harness; guardrails, which validate input and output, do part of the work that rules and PreToolUse hooks do here.
- **LangGraph:** it ships no harness either; you build the gates and the lifecycle logic yourself, as graph nodes and conditional edges around the node that runs the tool.
- **LangGraph:** session startup is graph re-entry — a checkpointer plus a `thread_id` restores the state, where a harness re-reads the settings and the instruction files.

## Traces

### Trace 17: What happens when a coding-agent session starts

You start the agent CLI in a project directory, and the harness assembles its configuration before you type anything.

1. **User** starts the harness in the project directory.
2. **Harness** resolves the settings by precedence: managed policy, CLI arguments, local project settings, project settings, user settings.
   - Each key takes its value from the highest layer that sets it.
3. **Harness** concatenates the instruction files broadest-first: managed, user, project, then local.
   - `@path` imports resolve to a maximum depth of 4; subdirectory files wait until the agent needs them.
4. **Harness** loads only each skill's name and description from the skill directories.
5. **Harness** connects the configured MCP servers to get their tool definitions ([Trace 11](ch04.md#trace-11-what-happens-when-the-agent-calls-an-mcp-server)).
   - A project-scope `.mcp.json` needs interactive approval before its servers run.
6. **Harness** fires the `SessionStart` hooks; their stdout can enter the context.
7. **Harness** assembles the system prompt: base instructions, concatenated instruction files, tool definitions, skill descriptions.
8. **User** sends the first message, and [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) starts with all of this in place.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant Env
  participant MCP
  User->>Harness: launch in project
  Harness->>Env: read settings layers
  Env-->>Harness: merged settings
  Harness->>Env: read memory files
  Env-->>Harness: concatenated instructions
  Harness->>Env: scan skills
  Env-->>Harness: descriptions only
  Harness->>MCP: connect and list tools
  MCP-->>Harness: tool definitions
  Harness-->>User: session ready
```

*Figure 7.1 — everything the model will "know" at turn one is gathered here, before any request.*

**Where this can fail**

- **Symptom:** a permission works on your machine and not on a teammate's. **Cause:** the rule lives in `settings.local.json` or in user settings, not in the committed project file. **Where to look:** each settings layer, highest precedence first.
- **Symptom:** the agent follows an instruction that nobody remembers writing. **Cause:** instruction files concatenate, so a user-level or imported file still applies. **Where to look:** every CLAUDE.md on the path, plus its imports.
- **Symptom:** MCP tools are missing from the session. **Cause:** nobody approved the project `.mcp.json`, or a server with the same name at another scope hides it. **Where to look:** the MCP config scopes and the approval state.
- **Symptom:** the session starts slowly. **Cause:** many MCP servers connect, or the import chains are deep. **Where to look:** the startup time for each server and the import tree.

### Trace 18: What happens when the harness gates a dangerous action

The model proposes `rm -rf` on a build directory, and the harness decides whether the command runs.

1. **LLM** emits a tool call: a shell command that deletes files.
2. **Harness** runs any matching PreToolUse hook first, before any rule.
   - A hook that exits 2 blocks the call here, even if an allow rule would match later.
3. **Guard** (the hook) exits 0, so the call continues to the rule lists.
4. **Harness** checks the deny list; a match blocks the call.
5. **Harness** checks the ask list; a match forces a prompt to the human.
6. **Harness** checks the allow list; a match lets the call run.
7. **Harness** uses the permission mode's default when no rule matches — in `default` mode, a write prompts.
8. **User** approves or rejects the prompted call.
9. **Harness** runs the approved call inside the sandbox, which limits what the process can touch.
10. **Harness** appends the result — or the denial text — to the context, so the model reads what happened.

```mermaid
flowchart TD
  TC[Tool call] --> HK[PreToolUse hook]
  HK -->|exit 2| BLK[Blocked]
  HK -->|passes| DENY[Deny rules]
  DENY -->|match| BLK
  DENY -->|no match| ASK[Ask rules]
  ASK -->|match| HUM[Prompt the human]
  ASK -->|no match| ALLOW[Allow rules]
  ALLOW -->|match| RUN[Run in sandbox]
  ALLOW -->|no match| MODE[Mode default]
  MODE -->|permits| RUN
  MODE -->|prompts| HUM
  HUM -->|approve| RUN
  HUM -->|reject| BLK
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef external fill:#57534E,stroke:#44403C,color:#fff
  class TC,BLK process
  class HK,DENY,ASK,ALLOW,MODE,HUM lease
  class RUN external
```

*Figure 7.2 — the gate order: hook, deny, ask, allow, mode default; first match wins, and the sandbox backstops whatever runs.*

**Where this can fail**

- **Symptom:** a precise allow rule never fires. **Cause:** a broader deny rule or ask rule matches first, because the order of the lists decides. **Where to look:** all three rule lists in every settings layer.
- **Symptom:** a command that you thought was blocked still ran. **Cause:** no deny rule matched it, so `bypassPermissions` mode ran it, or the model got the same effect through another tool. **Where to look:** the deny patterns, the session mode, and the full tool-call transcript.
- **Symptom:** the agent prompts constantly, and users approve without reading. **Cause:** there are no allow rules for routine safe calls, so the mode default prompts for everything. **Where to look:** the prompt count for each rule pattern; add allow rules for the common safe calls.
- **Symptom:** an approved script sent a file out of the machine. **Cause:** the gate checks intent, not what the process does, and no sandbox limited the process. **Where to look:** the sandbox configuration and the network egress rules.

### Trace 19: What happens when a hook fires

The agent edits a Python file, and a PostToolUse hook formats the file.

1. **Harness** completes a file-edit tool call and reaches the `PostToolUse` lifecycle event.
2. **Harness** tests the configured matchers against the tool name; one matcher matches the edit tool.
3. **Harness** starts the handler as a process and writes the event payload — tool name, inputs, result — as JSON to its stdin.
4. **Guard** (the handler) runs the formatter and a lint pass over the edited file.
5. **Guard** exits: 0 for success, 2 to block the outcome of the action.
   - On exit 0, stdout enters the context only for prompt events and session events; tool events stay silent.
6. **Harness** reads any JSON that the handler printed — a `permissionDecision` on PreToolUse, or `continue: false` to stop the turn.
7. **Harness** appends the blocking feedback to the context on exit 2, so the model reads the reason and can adjust.
8. **LLM** reads the outcome on the next turn; a handler that exits 0 changes nothing that the model reads.

```mermaid
sequenceDiagram
  autonumber
  participant Harness
  participant Guard
  participant LLM
  Harness->>Harness: lifecycle event fires
  Harness->>Guard: spawn handler with JSON
  Guard->>Guard: run format and lint
  Guard-->>Harness: exit code plus JSON
  alt exit 2 blocks
    Harness->>LLM: feedback in context
  else exit 0 succeeds
    Harness->>Harness: continue silently
  end
```

*Figure 7.3 — a hook is your process inside the loop: the exit code decides block versus advisory.*

**Where this can fail**

- **Symptom:** the hook does nothing. **Cause:** the matcher never matches the tool name, or the settings file that holds the hook is not on this machine. **Where to look:** the merged settings and the hook execution log.
- **Symptom:** every tool call fails for no clear reason. **Cause:** the handler crashes with exit 2 on all inputs, so a bug in the handler blocks everything. **Where to look:** the handler's stderr for the failing event payload.
- **Symptom:** the hook output never reaches the model. **Cause:** on exit 0, stdout enters the context only for prompt events and session events, not for tool events. **Where to look:** the event that the hook binds to; use exit 2 or JSON when the model must read the output.
- **Symptom:** the session runs slowly after edits. **Cause:** the handler runs an expensive check on every edit, and the harness waits for it. **Where to look:** the handler's run time for each event.

### Trace 20: What happens when a skill or slash command is invoked

You type `/review-pr 412`, and the harness loads an instruction file that then steers the turn.

1. **Harness** has carried every skill's name and description in the context since session start (Trace 17).
2. **User** types the slash command — or, on a plain request, the **LLM** matches the task against a skill description.
3. **Harness** resolves the name through the discovery layers: enterprise, then personal, then project.
4. **Harness** loads the SKILL.md body from disk into the context.
   - `$ARGUMENTS` substitutes "412"; any `` !`cmd` `` line injects shell output into the body.
5. **LLM** reads the body and follows its instructions: which files to fetch, which checklist to apply, and which format to answer in.
6. **Harness** loads the sidecar files only if the instructions direct the model to read them.
7. **Harness** keeps the loaded body in the context for the rest of the session, so later turns reuse it at no extra cost.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant Env
  participant LLM
  alt user trigger
    User->>Harness: slash command
  else model trigger
    LLM-->>Harness: matches description
  end
  Harness->>Env: read skill body
  Env-->>Harness: SKILL.md content
  Harness->>LLM: context plus body
  LLM-->>Harness: instruction-steered turn
  Harness-->>User: result
```

*Figure 7.4 — progressive disclosure: only the description costs tokens until the body is actually needed.*

**Where this can fail**

- **Symptom:** the model never selects the skill on its own. **Cause:** the description does not name the words that users really say. **Where to look:** the description text against real requests.
- **Symptom:** the wrong skill loads for a name. **Cause:** a skill with the same name at a higher discovery layer hides the project skill. **Where to look:** the enterprise and personal skill directories for that name.
- **Symptom:** the context grows through the session. **Cause:** every invoked skill body stays in the context, and several large bodies add up. **Where to look:** the token count for each turn after each invocation ([Chapter 3](ch03.md)).
- **Symptom:** the skill behaves differently on two machines. **Cause:** a `` !`cmd` `` injection depends on a local tool or on local state. **Where to look:** the output of the injected command on each machine.

## Questions

### Tier 1 — Explain

**Q 7.1 — Settings and instruction files both configure the harness. How do they merge differently?**

**Answer.** Settings resolve by precedence: for each key, the value comes from the highest layer that sets it.
Instruction files concatenate broadest-first: every file that applies enters the context together.
So a project setting can override a user setting.
A project CLAUDE.md cannot cancel a user CLAUDE.md; it can only add to it.

*Strong answers also mention:* this is why contradictory agent behavior usually means two instruction files, not a bug.

**Q 7.2 — In what order are permission rules evaluated, and why does specificity not matter?**

**Answer.** Deny, then ask, then allow; the first match decides.
Specificity has no effect, because the harness checks the lists in order and never compares one rule with another.
A broad deny rule overrides the most precise allow rule, because the harness checks the deny list first.

*Strong answers also mention:* the mode default applies only when no rule in any list matches.

**Q 7.3 — What is progressive disclosure in the skills mechanism?**

**Answer.** Only each skill's name and description stay in the context at all times.
The body loads on invocation — a slash command, or a model match on the description.
The body then stays in the context for the rest of the session.
Sidecar files load later still, and only on demand.
So a skill that nobody invokes costs about one sentence.

*Strong answers also mention:* the description is itself a prompt; the model finds the skill only if the description names the words that users really say.

**Q 7.4 — What do hook exit codes 0 and 2 mean, and where does stdout go?**

**Answer.** Exit 0 is success. Exit 2 blocks the action, and that block overrides every rule, including an allow rule.
On exit 0, stdout enters the context only for prompt events and session events; tool events stay silent.
A handler can also emit JSON: a `permissionDecision` on PreToolUse, or `continue: false` to end the turn.

*Strong answers also mention:* on a block, the harness appends the feedback to the context, so the model can adjust instead of only failing.

### Tier 2 — Reason

**Q 7.5 — A PreToolUse hook returns an "allow" decision, but the harness still prompts the user. Why?**

**Answer.** An "allow" from a hook cannot override a deny rule or an ask rule.
Hooks run first and can block any call, but their permissive answers rank below the rule lists.
Here an ask rule, or a deny rule, matches the call, so the prompt fires whatever the hook answered.
The asymmetry is deliberate: an extension can make the policy stricter, never weaker.

*Strong answers also mention:* the full order — hook, deny, ask, allow, mode default — and that exit 2 is the hook's strong decision, not "allow".

**Q 7.6 — Why load a skill body on demand instead of keeping every skill fully in context?**

**Answer.** The context is a budget ([Chapter 3](ch03.md)).
Full bodies for dozens of skills would take space away from the task.
Unused instructions also change where the model puts its attention.
The descriptions alone give the model enough signal to select a skill, and the body arrives only after that.
The body then stays in the context, so later turns do not load it again.

*Strong answers also mention:* the same pattern appears elsewhere — tool search, subdirectory instruction files — because loading on demand scales and loading everything at once does not.

**Q 7.7 — Where does the harness's permission gate stop, and what must the OS sandbox cover?**

**Answer.** The gate evaluates intent: it reads a proposed call and decides run, ask, or deny.
After the process starts, the gate cannot see what it does, and the process gets whatever the operating system grants.
The sandbox must therefore limit the behavior: filesystem scope, network egress, and resource limits.
A gate without a sandbox lets one approved script do anything.
A sandbox without a gate permits silent damage inside the sandbox.

*Strong answers also mention:* the two layers fail differently — an injected instruction can steer the model past the gate, but nobody can prompt a sandbox.

**Q 7.8 — A team commits an allow rule to the project settings, but one developer's agent still prompts for those calls. What layers do you check?**

**Answer.** Rules from every settings layer apply, so look for a match in a higher layer.
Check the managed policy and the CLI arguments first, because an org-level ask rule or deny rule overrides the project allow rule.
Then check the developer's `settings.local.json` and user settings for a rule that hides the project one.
Also confirm that the rule matches the call as the model issued it.
Different arguments, or a different tool, do not match the specifier.

*Strong answers also mention:* reproduce the problem with the merged settings, not by reading the files one at a time.

### Tier 3 — Design & Debug

**Q 7.9 — A deny rule protects a secrets file, yet a transcript shows the agent read it. Walk your diagnosis.**

**Answer.** Start from the transcript and find the exact call that returned the file contents.
Then check which tool made that call.
A deny rule on one tool does not cover another path to the same file.
The agent can use a shell `cat`, an MCP file server, or a script that it wrote.
Deny rules apply in every mode, so a read that ran means the rule never matched, or the rule never loaded.
Check the settings layer that holds the deny rule, because a rule in a local file protects only that one machine.
Fix it at the strongest layer: deny every read path, and add a control in the operating system, because rules gate only intent.

*Strong answers also mention:* a PreToolUse hook that inspects the arguments of every tool catches the path variants that pattern rules miss.

**Q 7.10 — Design the gating setup for an unattended agent run in CI, where nobody can answer prompts.**

**Answer.** No human can answer a prompt, so an ask must never fire.
Give every call that the job needs an explicit allow rule, and deny the rest.
The `dontAsk` mode denies an unmatched call instead of waiting for an answer that never comes.
Keep the allow list narrow: only the build, test, and version-control commands that the job needs.
Add PreToolUse hooks for audit logging and argument checks, because exit 2 blocks a call without a prompt.
Run the whole job in a container that holds no credentials beyond the task, and limit egress to the required hosts.
Report every denial, because in CI a denied call is a signal, not an interruption.

*Strong answers also mention:* a denial should fail the run and attach the transcript; a silent auto-deny hides a broken policy.

## Common mistakes & red flags

- **"Our project CLAUDE.md overrides the user's."** Instruction files concatenate, so both apply. Only settings override by precedence.
- **"The allow rule is more specific, so it wins."** The order decides: deny, then ask, then allow. The harness never compares specificity.
- **"The hook approved it, so it runs."** An "allow" from a hook cannot override a deny rule or an ask rule; only its exit 2 overrides every rule.
- **"The permission gate makes the agent safe."** The gate checks intent before a process starts. What the process does after that belongs to the operating-system sandbox.
- **"Add all our skills to the system prompt."** That defeats progressive disclosure. Descriptions stay in the context, and bodies load on demand, to keep the context small.
- **"The hook printed a warning, so the model read it."** On exit 0, stdout reaches the context only for prompt events and session events. For tool events, use exit 2 or JSON.
- **"bypassPermissions is fine on my machine."** It approves every call that your deny and ask rules do not name. You lose every prompt that would have caught a mistake.
