# Chapter 6 — Retrieval & RAG

## Why this chapter

An agent knows only what the harness puts in the context window this turn.
Retrieval moves content from outside the window into it.
This chapter zooms into steps 2 and 5 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): retrieved content enters context assembly, and search tools run.
The mental model: retrieval is a supply chain.
Every ingest choice — chunking, embedding, indexing — sets a cost that you pay at query time.
Engineers who trace a wrong answer back to the stage that failed can fix retrieval; the others only change the prompt again.
Level emphasis: [L1]–[L2]; no (L3) sections in this chapter.

## Concepts

**Retrieval.** Retrieval brings relevant external content into the context window at the moment the agent needs it.
It exists for two reasons: a corpus is larger than the context window, and every token that you add costs money and attention.

**RAG.** In retrieval-augmented generation (RAG), the harness searches an index and injects the top results into the context.
The model then writes its answer from those results.
The model never queries the index; the harness does, before or between model calls.
This is step 2 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): the retrieved content is part of context assembly.

**The ingest pipeline.** The ingest pipeline makes content searchable before any query arrives.
It runs offline, in four stages: extract, chunk, embed, index.
Each choice here is cheap to make now and expensive to change later.

- *Chunking* splits a document into pieces small enough to embed and to inject.
  A small chunk matches a query precisely, but it loses the meaning around it.
  A large chunk keeps that meaning, but it blurs the embedding and uses more of the token budget at injection.
  A split that cuts a thought in half makes both halves impossible to find.
- *Embedding* maps each chunk to a vector, so that similar meanings land near each other.
  The embedding model becomes part of the index.
  A query must use the same model, so a change of model forces a full reindex.
- *Indexing* stores the vectors in a structure built for approximate nearest-neighbor search.
  It stores the chunk text and the metadata — source, section, timestamp — next to each vector.
  That metadata makes filtering and citations possible later.
  If you skip it at ingest, no work at query time can recover it.

Ingest is not a one-time build.
Documents change, so the pipeline needs re-ingest triggers and deletes.
Without them, the index serves old content and gives no warning.

**Query-time RAG.** At query time the harness runs four steps: embed the query, search the index, rerank the candidates, inject the top chunks.
Search is tuned for recall: it returns a broad candidate set fast.
Reranking is tuned for precision: a stronger scorer, a cross-encoder or an LLM, orders the candidates against the query.
Injection then puts the top chunks into the context, each with a source label.
The model sees only what survives all four steps.

**Hybrid search.** Hybrid search runs vector search and keyword search together, because each one is blind where the other is strong.
Vector search matches meaning.
It is weak on exact strings such as error codes, SKUs, and function names, because embeddings blur rare tokens.
Keyword search (BM25, a ranking function over exact terms) is strong on identifiers and blind to paraphrase.
Hybrid search fuses the two ranked lists, often with reciprocal rank fusion.
Production systems use hybrid search by default, because real query mixes contain both kinds.

**Agentic search.** Agentic search gives the model search tools and lets the model drive, instead of using an index built in advance.
The model emits grep, list, and read calls, reads the results, and issues a sharper query each round.
This is step 5 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): search tools run inside the loop.
It needs no ingest pipeline, it always reads live data, and it can change the query during a search.
It pays for this with turns: every round is a full model call, so latency and token cost grow with search depth.
Coding agents use agentic search, because code is already greppable and changes constantly.

**When long context beats retrieval.** Long context beats retrieval when the whole corpus fits in the context window with room to work.
You put the whole corpus in the prompt, so recall failures disappear and the model sees every passage.
Prompt caching makes this affordable when you query the same corpus many times.
The cached prefix costs a fraction of the input price ([Chapter 2](ch02.md)).
Retrieval is worth its complexity when the corpus outgrows the window, or when only a small part is relevant for each query.
It is also worth it when the token cost for each turn dominates.

| Approach | Freshness | Cost per query | Best when |
|---|---|---|---|
| One-shot RAG | as fresh as the index | low, one model call | large corpus, known query shape |
| Agentic search | live | high, many turns | greppable data, exploratory questions |
| Long context | as fresh as the prompt | high without caching | corpus fits, repeated queries |

**Retrieval quality.** Retrieval quality sets the ceiling on answer quality, so measure it directly.
The first metric is recall@k: of the chunks that should be found for a query, how many appear in the top k?
Low recall@k means the answer never reaches the model, and no prompt change fixes that.
The second metric is precision: how much of what you inject is relevant, because irrelevant chunks dilute attention.
To measure both you need gold query sets, graded retrievals, and drift tracking; that method comes later in this book.
Hold this rule here: when a RAG answer is wrong, first ask whether the right chunk was in the top k at all.

### In other stacks

- **LangChain:** every vector store exposes `as_retriever()`, so retrieval sits behind one common interface, and chains inject the returned documents as context.
- **LangGraph:** retrieval is an explicit graph node, and agentic-RAG patterns (grade the results, rewrite the query, retrieve again) are conditional edges that you own.
- **OpenAI Agents SDK:** file search is a hosted tool over provider-managed vector stores; chunking and embedding run on the server, so you give up control and run no pipeline.
- **Framework-neutral:** many stacks expose an index through a plain search tool, so the surface that the model sees is the same as agentic search; only the backend differs.

## Traces

### Trace 14: What happens when a document becomes searchable

You add a product manual to the agent's knowledge base.

1. **User** adds the manual to the knowledge base.
2. **Harness** extracts the plain text plus the structure: title, headings, timestamps.
3. **Harness** splits the text into chunks along semantic boundaries.
   - Chunk size sets the trade between precision and meaning. It is fixed here, at ingest.
4. **Harness** attaches metadata to every chunk: source ID, section, position.
5. **Harness** sends each chunk to the embedding model and receives one vector for each chunk.
6. **Idx** stores each vector next to its chunk text and its metadata.
7. **Idx** updates the keyword index over the same chunks for hybrid search.
8. **Idx** commits the index; the manual is now searchable by meaning and by exact term.

```mermaid

  D[New document] -->|parse| X[Extract text]
  X -->|split| C[Chunks]
  C -->|tag| M[Chunks with metadata]
  M -->|embed| E[Embedding model]
  M -->|tokenize| K[Keyword index]
  E -->|vectors| V[Vector index]
  V -->|serve| S[Searchable store]
  K -->|serve| S
  classDef resource fill:#fb7185,stroke:#be123c,color:#fff
  classDef process fill:#38bdf8,stroke:#0369a1,color:#fff
  classDef external fill:#64748b,stroke:#334155,color:#fff

  class X,C,M process

```

*Figure 6.1 — every downstream search quality is decided here: chunk boundaries, embedding model, and metadata are fixed at ingest.*

**Where this can fail**

- **Symptom:** a passage in the document never comes back in search. **Cause:** the chunker split it mid-thought, so neither half matches the query. **Where to look:** the stored chunk text around that passage.
- **Symptom:** search finds the right document but cites the wrong section. **Cause:** extraction lost the headings, so the chunks carry no section metadata. **Where to look:** the metadata fields on the returned chunks.
- **Symptom:** results become much worse after an upgrade. **Cause:** the queries use a new embedding model while the corpus keeps the old vectors. **Where to look:** the embedding model in the index build against the one in the query path.
- **Symptom:** last week's edits never appear in answers. **Cause:** there is no re-ingest trigger, so the index serves the old version. **Where to look:** the index commit timestamps against the source timestamps.

### Trace 15: What happens when a RAG query runs

The user asks the agent a question that the product manual answers.

1. **User** sends the question.
2. **Harness** embeds the query with the same embedding model that ingest used.
3. **Harness** sends the query vector and the query text to the index.
4. **Idx** runs vector search and keyword search, then returns one fused candidate list.
5. **Harness** reranks the candidates against the query with a stronger scorer.
6. **Harness** injects the top chunks into the context, each with a source label.
7. **LLM** writes an answer grounded in the injected chunks.
8. **Harness** returns the answer with citations built from the chunk metadata.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant Idx
  participant LLM
  User->>Harness: question
  Harness->>Harness: embed query
  Harness->>Idx: vector plus keyword search
  Idx-->>Harness: fused candidate chunks
  Harness->>Harness: rerank candidates
  Harness->>LLM: context plus top chunks
  LLM-->>Harness: grounded answer
  Harness-->>User: answer with citations
```

*Figure 6.2 — the model appears once, at the end; every retrieval decision is the harness's, made before the model sees anything.*

**Where this can fail**

- **Symptom:** a confident answer with wrong facts. **Cause:** retrieval missed, so the model answered from its weights. **Where to look:** the injected chunks in the transcript — is the needed fact there at all?
- **Symptom:** the right chunk was retrieved, but the answer ignores it. **Cause:** it ranked low, so weaker chunks sat above it at injection. **Where to look:** the chunk order and count in the assembled context.
- **Symptom:** queries with exact identifiers fail while paraphrase queries work. **Cause:** the keyword search is missing from the fusion, and embeddings blur rare tokens. **Where to look:** the candidate list before the rerank.
- **Symptom:** answer latency rises sharply under load. **Cause:** the reranker scores hundreds of candidates for each query. **Where to look:** the trace spans for the rerank step.

### Trace 16: What happens when the agent searches instead

You ask a coding agent where the retry logic lives; there is no index, only search tools.

1. **User** asks where the retry logic lives.
2. **Harness** assembles the context with the search tools defined: grep, list, read.
3. **LLM** emits a grep call for a likely term.
4. **Tools** run the search against the live files in the environment.
5. **Harness** appends the hit list to the context.
6. **LLM** reads the hits, then emits a read call for the strongest match.
7. **Tools** return the file contents, and the harness appends them.
8. **LLM** repeats steps 3 to 7, with a sharper query each round.
   - Trace 15 differs: there the harness searches once. Here the model steers the search, one full turn for each round.
9. **LLM** answers with file paths and line references.
10. **Harness** returns the answer.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  participant Tools
  participant Env
  User->>Harness: question
  Harness->>LLM: context plus search tools
  LLM-->>Harness: grep call
  Harness->>Tools: run search
  Tools->>Env: scan live files
  Env-->>Tools: matching lines
  Tools-->>Harness: hit list
  Harness->>LLM: context plus hits
  Note over LLM,Tools: search rounds repeat
  LLM-->>Harness: paths and lines
  Harness-->>User: answer
```

*Figure 6.3 — each search round is a full model turn: adaptive and always fresh, paid for in latency and tokens.*

**Where this can fail**

- **Symptom:** a correct answer, but slow and expensive. **Cause:** the first queries were broad, and every round is a full model call. **Where to look:** the transcript turn count and the token totals for each turn.
- **Symptom:** the agent loses the goal during the search. **Cause:** one grep returned thousands of lines and filled the context. **Where to look:** the tool result sizes for each turn.
- **Symptom:** the agent concludes that the code does not exist. **Cause:** query drift — it searched for literal strings, but the code names the concept differently. **Where to look:** the sequence of search strings across the turns.
- **Symptom:** the agent read the right file, but the answer misses the point. **Cause:** the read used a window, and the relevant lines fell outside it. **Where to look:** the offset and the limit on the read call.

## Questions

### Tier 1 — Explain

**Q 6.1 — Name the stages of the ingest pipeline and what each one fixes for later.**

**Answer.** Extract, chunk, embed, index.
Extraction fixes what text and structure exist at all; lost headings never come back.
Chunking fixes the granularity of retrieval: what a hit can be.
Embedding fixes the similarity space and locks the choice of model into the index.
Indexing fixes what you can filter and cite, through the metadata stored with each chunk.
Every behavior at query time is downstream of these choices.

*Strong answers also mention:* ingest is an operated pipeline with re-ingest and deletes, not a one-time build.

**Q 6.2 — Walk the four query-time steps of RAG.**

**Answer.** Embed the query with the same model that ingest used.
Search the index for a broad candidate set; this step is tuned for recall.
Rerank the candidates with a stronger scorer; this step is tuned for precision.
Inject the top chunks into the context with source labels, and the model writes its answer from them.
The model sees only what survives all four steps, and it never touches the index.

*Strong answers also mention:* the recall-then-precision split exists because the precise scorer is too slow to run over the whole corpus.

**Q 6.3 — Why do vector-only systems miss exact identifiers, and what is the fix?**

**Answer.** Embeddings compress meaning, and rare tokens such as error codes and SKUs carry little shared meaning, so they blur.
Two different codes can land near each other in the vector space.
Keyword search (BM25) matches exact terms and has the opposite blind spot: paraphrase.
The fix is hybrid search: run both, fuse the two ranked lists, and give the fused set to the reranker.

*Strong answers also mention:* reciprocal rank fusion as a common fusion method, and that real query mixes always contain both kinds.

### Tier 2 — Reason

**Q 6.4 — Why does a change of embedding model force a full reindex?**

**Answer.** Similarity search compares the query vector to the stored vectors in one shared space.
Different embedding models define different spaces, and distances across two spaces have no meaning.
A query embedded with the new model and scored against old vectors returns noise, and gives no warning.
So you must re-embed and reindex the corpus before the query path changes model.

*Strong answers also mention:* running the old and new indexes side by side during the migration, and comparing recall on the same query set.

**Q 6.5 — When does agentic search beat one-shot RAG, and what does it cost?**

**Answer.** It wins when the data is already searchable in place, changes faster than you can re-ingest, or needs iterative narrowing.
A coding agent that greps a live repository needs no pipeline and never reads a stale chunk.
It can also recover from a bad first query, which one-shot RAG cannot do.
The cost is turns: each search round is a full model call, so latency and tokens grow with depth.
One-shot RAG moves its cost into the ingest pipeline; agentic search pays at query time.

*Strong answers also mention:* the hybrid pattern — RAG for the first broad pass, agentic tools to verify and refine.

**Q 6.6 — When does long context beat retrieval entirely?**

**Answer.** When the corpus fits in the window with room to work, and the queries reuse the same corpus.
Putting everything in removes recall failures, because the model sees every passage.
Prompt caching makes repeated queries over the same corpus affordable, because the cached prefix costs far less than input price.
Retrieval wins again when the corpus outgrows the window, when little is relevant for each query, or when latency budgets rule out huge prompts.

*Strong answers also mention:* long context still has attention limits — being in the window is necessary, not sufficient ([Chapter 3](ch03.md)).

### Tier 3 — Design & Debug

**Q 6.7 — Users report the RAG assistant answers confidently but wrongly about a policy updated last week. Walk your diagnosis.**

**Answer.** Read one failing transcript before you change anything.
Check the injected chunks first: is the updated policy text in the context at all?
If the old text is there, the index is stale; check the re-ingest triggers and the index timestamps against the source (Trace 14 failure modes).
If no relevant chunk is there, it is a recall miss; run the query against the index by hand and inspect the top k.
If the right chunk is present but ignored, check its rank at injection and what sits above it.
Each branch has a different fix: re-ingest, chunking or hybrid tuning, or rerank and injection order.

*Strong answers also mention:* adding the failing query to a gold set, so that the fix is measured and not asserted.

**Q 6.8 — Design retrieval for an agent over a large internal wiki that serves both exact lookups and broad questions.**

**Answer.** The corpus outgrows the window, so retrieval is required, and the query mix decides the shape.
Ingest: chunk on heading boundaries, keep the section and timestamp metadata, and trigger re-ingest on every wiki edit.
Query time: hybrid search, where keyword search carries the exact lookups and vector search carries the broad questions, then a reranker over the fused set.
Give the agent a search tool over the same index, so that it can query again when the first injection is not enough.
Define recall@k on a gold query set drawn from both query types before you tune anything.

*Strong answers also mention:* citations built from chunk metadata so users can verify, and index freshness monitored as an operational metric.

## Common mistakes & red flags

- **"We added RAG, so hallucinations are solved."** Retrieval misses, and the model then answers fluently from its weights. Verify grounding for each answer; do not assume it.
- **"Bigger chunks give the model more context."** They blur the embedding and dilute the injection. The chunk is the unit of finding, so keep it findable and let the metadata carry the surroundings.
- **"Vector search understands the query, keywords are legacy."** Embeddings blur exact identifiers. Hybrid search is the production default, not a fallback.
- **"We tested retrieval by trying a few queries."** That measures nothing. Recall needs a gold query set and a repeatable test; the method comes later in this book.
- **"The index is built, so retrieval is done."** Ingest is an operated pipeline. Without re-ingest and deletes, the index drifts away from the truth and gives no warning.
- **"Reranking is optional polish."** Injection order and cutoff decide what the model sees. A right answer at rank 40 is a wrong answer.
- **"Always retrieve — context is expensive."** If the corpus fits and the queries repeat, long context plus caching is simpler and misses nothing.
