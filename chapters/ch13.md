# Chapter 13 — Architecture Judgment & Org Adoption

## Why this chapter

This chapter uses the mechanisms from Chapters 1–12 to make decisions at org scale.
The questions change: not how the loop works, but which loop forty teams run.
Who may change that loop, and how do you know that a change helped?
The mental model: every org-scale question reduces to two tests —
where your differentiation lives, and what an exit costs.
This chapter runs above [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): it decides how many loops an org runs, and under what gates.

## Concepts

### Build vs buy: where differentiation lives

Buy the harness, and build the evals.
The harness (the runtime that owns the loop, context assembly, and gating) is a commodity that vendors improve every month.
Your loop, retry logic, and compaction policy do not make your product better than a competitor's.
A harness that you build adds a maintenance cost that grows every year.

Your differentiation lives in three places:

- your domain tools — the actions that only your systems can take;
- your eval suite — the record of what "good" means for your tasks ([Chapter 10](ch10.md));
- your data.

The rule: build what holds your judgment; buy what holds everyone's.
For observability, buy the pipes, because tracing is standardized.
Build the agent-specific views: transcripts, cost per solve, turn counts.
Build the evals, always.

### Framework selection: lock-in surface, not feature lists

Choose a framework by its lock-in surface, not by its feature list.
Teams compare frameworks with a feature matrix, which is the wrong instrument.
Features converge within quarters.

The lock-in surface is the set of long-lived artifacts in the framework's private format:
prompts, tool schemas, eval datasets, transcripts, state, and telemetry.
Each one raises the escape cost — the work needed to leave a framework that stalls, changes its license, or loses the market.

The defense is a neutral spine.
Keep the artifacts that outlive any framework in neutral formats:
tool definitions as plain JSON Schema, and transcripts in a standard telemetry shape.
Eval tasks are data files that any runner can load.
Frameworks become thin, replaceable adapters at the edges.
The measurable test: can you re-run last month's eval suite on a different stack in a week?

One more selection question sits below the framework choice: does this orchestration deserve a runtime at all?
A multi-step agent structure can run as a disposable script or on a durable runtime that checkpoints its state.
The durable runtime earns its cost in four cases:

1. The structure runs on a schedule.
2. A run must survive a crash and resume from its last good step.
3. A human must approve a step in the middle of a run.
4. An auditor will ask later what happened.

It is pure overhead for a structure that runs one time.
So decide by run frequency and by recovery need, not by how sophisticated the structure looks.

### Agents vs workflows: a per-decision choice

Choose between an agent and a workflow for each decision, not for the whole system.
[Chapter 1](ch01.md) fixed the definitions.
An agent is a model that calls tools in a loop and chooses its next step.
A workflow is a fixed pipeline where code chooses.
At org scale, teams make this an identity — "we build agents now".

For each step in a pipeline, write a short decision record.
It names who chooses the next step, what variance costs there, and what evidence supports the choice.
Where the path depends on what earlier steps find, the model chooses; that is what you pay it for.
Where the steps are known and variance is expensive — billing, deletion, any action that you cannot reverse — code chooses.
The record keeps the choice reviewable and reversible.

### Eval-gated rollout

No agent change ships without the eval suite.
[Trace 33](ch12.md#trace-33-what-happens-when-the-underlying-model-is-upgraded) showed one team that survived a model upgrade because it re-ran its suite.
At org scale this becomes a standing rule, and "change" means any change.
A prompt edit, a new tool, a model pin bump, and a harness upgrade each change behavior, so each is a release.

Trace 34 walks the pipeline: the suite gates the merge, and a canary cohort takes the change first.
Telemetry compares the cohort with the baseline, and only a healthy canary goes to the whole fleet.
The gate is the org's control point because it is mechanical: it scales to forty teams without forty review boards.

### Incident response for agentic systems

The transcript is the primary record for triage.
That is the decisive difference from a service incident.
It holds every decision, every tool result, and every gate, in order, with token counts and spans ([Chapter 12](ch12.md)).
An org that cannot pull a transcript in minutes cannot triage at all.

Prompt injection ([Trace 29](ch11.md#trace-29-what-happens-when-a-prompt-injection-arrives-in-tool-output)) is the common case.
Containment revokes a capability; it does not repair a prompt.
You cannot change how the model reads instructions during the incident.
You can revoke what the attacker needs: the tool, the egress path, or the write path ([Trace 30](ch11.md#trace-30-what-happens-when-an-agent-tries-to-exfiltrate-data)).
The root cause names the surface that carried untrusted text into the context.
The incident closes only when the reproducing case joins the guardrail regression suite.

### Skilling a team

The levels in this book are a growth path, not a hiring filter.

- **Builders (L1):** can narrate the loop and build a working agent.
- **Operators (L2):** can debug transcripts, run evals, and productionize an agent.
- **Architects (L3):** can commit to the positions that this chapter practices.

Grow operators by making transcript reading a habit.
One real transcript for each engineer each week teaches more than a slide deck.
The transcript is where every mechanism from Chapters 1–12 becomes visible.

Teams also need operating rules.

- Delegate self-contained work with a complete brief.
- Review the plan before the diff ([Chapter 8](ch08.md)).
- Never let an unverified "done" close a task.
- Write the rules where the harness loads them, not in a wiki that nobody reads.

### Measuring ROI

Measure the cost per solve against the engineer-hours that the agent saved.
Define the task classes, and measure the solve rate on them ([Chapter 10](ch10.md)).
Divide the spend by the solves, and compare that with the human-time cost of the same outcomes.
Track rework, because a "solve" that a human redoes is spend, not value.

Adoption metrics hide this result.

- **Sessions started** measures curiosity.
- **Tokens consumed** measures spend.
- **Active users** measures habit.

None of these numbers separates an agent that saves an hour from one that costs an hour.
The tie-breaker: would the team pay for it from its own budget?

One boundary note: agent product and UI design is out of scope for this book.

## Traces

### Trace 34: What happens when an agent change ships across an organization

A team edits the system prompt of a support agent that forty teams share.

1. **User** lands the change behind a version pin.
   - Prompts, tools, and model pins all count as releases.
2. **CI** runs the full eval suite against the pinned change ([Trace 27](ch10.md#trace-27-what-happens-when-an-eval-suite-runs)).
3. **CI** blocks the merge if any gated metric regresses.
   - The gate is mechanical: no reviewer judgment, no exceptions path.
4. **CI** publishes a passing change to a canary cohort — a small share of live sessions.
5. **Obs** compares canary telemetry with the baseline: solve rate, turns per task, cost per solve, guardrail hits.
6. **Obs** alerts on any canary regression that the offline suite missed.
7. **CI** rolls a healthy change forward cohort by cohort, or rolls back to the prior pin in one step.
8. **User** adds any case that the canary caught to the suite, so the gate catches its class next time.

```mermaid

  CH[Agent change] --> EG{Eval gate}
  EG -->|regression| BL[Merge blocked]
  EG -->|pass| CN[Canary cohort]
  CN --> TW[Telemetry watch]
  TW --> HG{Health gate}
  HG -->|healthy| FR[Fleet rollout]
  HG -->|regression| RB[Rollback to pin]
  RB --> RC[Case joins suite]
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef resource fill:#BE123C,stroke:#9F1239,color:#fff
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef leader fill:#0F766E,stroke:#115E59,color:#fff

  class BL,CN,TW,RB,RC process
  class FR leader
```

*Figure 13.1 — two gates stand between a change and the fleet; both are mechanical, and rollback feeds the suite.*

**Where this can fail**

- **Symptom:** a regression ships despite the gate.
    - **Cause:** the change class is not in the suite — prompt edits gated, tool edits not.
    - **Where to look:** which paths trigger the suite in the CI config.
- **Symptom:** the canary is healthy; the fleet degrades.
    - **Cause:** the cohort is not representative — one team's traffic, one task class.
    - **Where to look:** the cohort definition against the fleet task mix.
- **Symptom:** every change passes, and quality still drifts.
    - **Cause:** the suite is stale, because nobody feeds failures back.
    - **Where to look:** the date of the last case added to the suite.
- **Symptom:** teams bypass the gate under deadline.
    - **Cause:** the gate is slow or flaky, so exceptions became routine.
    - **Where to look:** the suite runtime and the exception log.

### Trace 35: What happens when a prompt-injection incident is triaged

An alert fires: a documentation agent posts outbound requests that it never made before.

1. **Obs** raises the alert on an anomalous tool-call pattern — a guardrail hit or an egress spike ([Trace 29](ch11.md#trace-29-what-happens-when-a-prompt-injection-arrives-in-tool-output)).
2. **User** (the on-call engineer) pulls the affected transcripts from Obs.
3. **User** finds the injected instruction inside a fetched page in a tool result, not typed by a person.
4. **User** adds a deny rule that revokes the egress capability across the fleet.
   - Containment comes first, and it revokes a capability ([Trace 30](ch11.md#trace-30-what-happens-when-an-agent-tries-to-exfiltrate-data)).
5. **Guard** enforces the rule on every live session, and the exfiltration path closes.
6. **User** stops the affected sessions, so none keeps the injected text in its context.
7. **User** traces the root cause through Obs: which tool carried the untrusted text, and why the gate passed it.
8. **User** writes the reproducing case into the guardrail regression suite.
9. **CI** runs the suite; the case fails on the old config and passes on the fix.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant Guard
  participant Obs
  participant CI
  Obs->>User: alert anomalous tool calls
  User->>Obs: pull session transcripts
  Obs-->>User: transcripts with spans
  User->>Guard: add deny rule
  Guard-->>Harness: block capability fleet wide
  User->>Harness: kill affected sessions
  User->>Obs: trace injected source
  Obs-->>User: tool result carried payload
  User->>CI: add regression case
  CI-->>User: guardrail suite gates class
```

*Figure 13.2 — containment (steps 4–6) comes before root cause (7–8); the incident closes only when CI gates its class.*

**Where this can fail**

- **Symptom:** nobody can find the injected text.
    - **Cause:** transcripts are truncated, or tool results were not logged.
    - **Where to look:** the telemetry config for tool-result retention.
- **Symptom:** the same injection returns a month later.
    - **Cause:** the fix repaired a prompt; nobody added a regression case.
    - **Where to look:** the guardrail suite for the incident's case.
- **Symptom:** the alert never fired; a customer reported the problem.
    - **Cause:** there is no anomaly baseline for tool-call patterns.
    - **Where to look:** what Obs alerts on, against what it records.

## Scenario: The platform team's grand harness

A central platform team proposes a two-year program: a bespoke harness and a custom eval store.
All forty product teams must adopt one framework, chosen this quarter from a feature matrix.
Release gates are deferred to phase three, "once teams are onboarded".
Success will be reported monthly as sessions started per team.
The team argues that central control now prevents fragmentation later.

**Critique.**
The plan inverts build vs buy.
The harness and the eval store are commodities, and the org's judgment lives in the eval content, which the plan never mentions.
The mandate optimizes a feature matrix that will be obsolete before onboarding ends.
The durable decision is the neutral spine — the transcript, tool-schema, and eval formats — and the plan standardizes none of them.
Gates in phase three mean two years of ungated changes, so the riskiest window is the least protected.
Sessions started counts curiosity and rewards waste.
What is right: central plumbing is worth owning, and fragmentation is a real problem.
The spine solves it for less than a mandate costs.

Ask next:

- Which formats must every team share, so evals and transcripts stay portable?
- What is the escape cost when the framework loses the market?
- Which change classes does the gate cover in phase one, not phase three?

## Questions

### Tier 2 — Reason

**Q 13.1 — Why is the eval gate a better org-level control point than mandatory human review of agent changes?**

**Answer.** The gate is mechanical: the same bar for every change, across forty teams.
A human who reviews a prompt diff cannot predict behavior: a one-line edit can shift tool choice across thousands of sessions.
The suite runs the change against real task classes and measures the shift ([Trace 27](ch10.md#trace-27-what-happens-when-an-eval-suite-runs)).
Review still matters for intent and design; the gate owns behavior.

*Strong answers also mention:* the gate is only as good as the suite is fresh — the Trace 34 failure mode where every change passes while quality drifts.

**Q 13.2 — Leadership reports agent adoption as "sessions started, up 40%". What does this measure, and what do you report instead?**

**Answer.** It measures curiosity and habit, not value.
A session counts the same whether the agent saved an hour or wasted one.
A team that fights a bad tool generates more sessions, not fewer.
Report the cost per solve against the engineer-hours saved on defined task classes:
solve rate, human-minutes per solve, and rework rate.
Those numbers separate outcome from activity.

*Strong answers also mention:* the willing-to-pay test — a metric that needs a mandate to look good is not evidence.

**Q 13.3 — What is a framework's lock-in surface, and why does it matter more than its feature list?**

**Answer.** The lock-in surface is the set of your long-lived artifacts in the framework's private format:
prompts, tool schemas, eval data, transcripts, and telemetry.
Features converge within quarters, but every artifact in a private format raises the escape cost, and that cost compounds.
The concrete test: can you re-run last month's eval suite on a different stack in a week?
A neutral spine keeps the answer yes.

*Strong answers also mention:* frameworks as thin adapters at the edge, owned by one team, so a swap touches adapters, not artifacts.

### Tier 3 — Design & Debug

**Q 13.4 — Org agent spend doubled in a quarter while total solves stayed flat. Walk your diagnosis.**

**Answer.** Read the telemetry before you theorize.
The cost per solve doubled, so find where the extra tokens go.
Segment by team and task class first: one team's runaway use case looks like org-wide drift in an aggregate.
Input tokens per turn point at context bloat or a broken cache prefix ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).
Turns per task point at retry storms from swallowed tool errors ([Trace 10](ch04.md#trace-10-what-happens-when-a-tool-call-fails)).
Sessions per solve point at humans who re-run failed tasks — a quality problem that arrives as cost.
Check the release record: whatever shipped near the change is the first suspect.
Fix the largest class, then measure the cost per solve again.

*Strong answers also mention:* adding the cost per solve to the canary health gate, so the next regression is caught in the cohort, not in the bill.

**Q 13.5 — Design the rollout when the provider retires the model your forty teams pin. You have eight weeks.**

**Answer.** This is [Trace 33](ch12.md#trace-33-what-happens-when-the-underlying-model-is-upgraded) across the fleet, so run it as forty gated releases, not one switch.
Week one: freeze the baseline.
Every suite runs against the old pin and records solve rate, turns, and cost per solve.
Then run every suite against the new model, with no other change.

Triage the teams into three categories:

- **Green:** ships now; canary first, as in Trace 34; their telemetry improves the plan for the rest.
- **Yellow:** prompt or tool fixes needed; fix against their suite, because the suite defines done.
- **Red:** behavior shifts that need redesign; get platform-team attention and, if needed, a temporary shim.

Hold both pins live until the last fleet is healthy, so rollback stays one cheap step.

*Strong answers also mention:* teams without a suite cannot even be triaged; the migration is what forces them to build one.

### Tier 4 — Judge

**Q 13.6 — Your platform team wants to build a bespoke harness "tuned to our stack". Build or buy? Commit.**

**Answer.** Buy the harness, and spend the freed headcount on evals and domain tools.

- **Assumptions:** a commodity harness covers the loop, the gating, and the context management that your teams need.
  Your differentiation lives in tools, evals, and data.
- **Kill-criteria:** a hard requirement that no harness meets after a genuine spike, a regulatory isolation model for example.
  The second: vendor terms that make the escape cost worse than the build cost.
- **Strongest counter-position:** a bespoke harness builds deep competence, and internal integration has real value.
  But it proves too much.
  Adapters and evals on a commodity loop build the same competence for less.
  Deep integration is what tools and MCP servers are for ([Chapter 4](ch04.md)).
- **Decision:** buy; revisit only if a kill-criterion fires; measure the platform team on suite coverage, not harness features.

*Strong answers also mention:* the Tier-4 bar in [Appendix C](appendices.md#appendix-c--answer-quality-rubric) — the decision is owned, the counter-position is steelmanned, and the exit condition is named first.

**Q 13.7 — Mandate one agent framework for all forty teams, or let every team choose? Commit.**

**Answer.** Neither: mandate the spine, and free the framework.
Standardize the tool-schema, transcript, and eval formats; let teams pick any framework that emits them.

- **Assumptions:** the artifacts, not the framework, are what the org must share,
  and framework churn makes any single bet risky.
- **Kill-criteria:** spine compliance above a quarter of a team's integration effort means the spine is too thick.
  Three or more frameworks that fragment hiring and on-call mean a shortlist of two.
- **Strongest counter-position:** a mandate concentrates expertise and gives one team's fixes to every team for free.
  Those economies are real.
  But a mandate buys them by maximizing the lock-in surface while the framework market is least settled.
  The spine captures most of the sharing benefit for a fraction of the escape cost.
- **Decision:** spine now; shortlist if fragmentation appears; no mandate without a kill-criterion firing.

*Strong answers also mention:* the spine is testable — CI can verify that artifacts parse, which makes compliance a gate, not a memo.

**Q 13.8 — After the Trace 35 incident, security proposes a human approval on every tool call fleet-wide. Accept, reject, or counter? Commit.**

**Answer.** Reject the blanket rule, and counter with capability-tiered gating.
Blanket approval destroys the economics, and approval fatigue makes reviewers approve without reading.
A gate that always approves is worse than no gate, because the org believes it works.
Tier by blast radius ([Chapter 11](ch11.md)).
Reads are auto-approved, and reversible writes are gated by rules and hooks.
Irreversible or egress-bearing actions are always gated by a human.

- **Assumptions:** the lesson of the incident is that egress needed a gate, not that every call did.
  The regression suite now covers that class (Trace 35).
- **Kill-criteria:** a second injection-class incident that slips the tiers means tighten them.
  Approval volume beyond what on-call can review means the tiering is wrong, not the reviewers.
- **Strongest counter-position:** after a real incident the risk budget is spent, and over-gating earns trust that you can relax later.
  That is politically true, but the training to approve without reading is permanent.
- **Decision:** tiered gating, measured by guardrail-hit and approval-fatigue metrics, reviewed quarterly.

*Strong answers also mention:* the approval-fatigue rate is itself a gated metric — a human gate that approves 99% of requests shows the tiers are wrong.

## Common mistakes & red flags

- **"We're building our own harness so we control the stack."** You control a maintenance cost; differentiation lives in tools, evals, and data.
- **"We compared frameworks on features and picked the winner."** Features converge; the escape cost compounds. The durable question is the lock-in surface; the answer is a neutral spine.
- **"Adoption is up 40%."** Sessions, tokens, and active users measure activity and spend, not value. A metric that cannot separate a saved hour from a wasted one tells you nothing.
- **"Prompt edits don't need the release process."** A one-line prompt change shifts fleet behavior like a code deploy. Every artifact that changes behavior ships through the Trace 34 gate.
- **"We handled the injection incident — we fixed the prompt."** A prompt repair is not containment. Contain by revoking the capability; a prompt patch without a gated regression test returns the same incident later.
- **"The eval gate slows teams down, so we allow exceptions."** A gate with a routine exceptions path is not a gate. Fix the suite's speed and flakiness instead.
