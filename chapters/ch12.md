# Chapter 12 — Production Ops, Cost & Latency

## Why this chapter

[Chapter 10](ch10.md) measured [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) offline; this chapter measures it in production.
Production runs a fleet of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loops against real users, real outages, and a real bill.
The mental model: the replayable transcript is the unit of debugging, and the solve is the unit of cost.
Every operational question reduces to one of those two units.

## Concepts

### Deployment shapes

Three shapes cover most production agents, and each has its own latency, cost, and risk envelope.

An **interactive copilot** has a human waiting.
Latency matters most here: the first token must arrive fast, so streaming ([Trace 5](ch02.md#trace-5-what-happens-when-a-response-streams)) is mandatory.
The human reads each answer, which contains the risk; the session pays the cost in the foreground.

A **background job** has nobody waiting.
Latency below hours does not matter, so its volume routes through the Batch API at 0.5× ([Chapter 2](ch02.md)).
Verify steps contain the risk, because nobody reads the intermediate output.

A **CI agent** runs unattended on a trigger ([Trace 23](ch08.md#trace-23-what-happens-when-a-ci-agent-handles-a-pull-request)).
The pipeline sets its latency budget.
Its risk envelope is the widest, because no human is in the loop.
So it carries the tightest permissions and the hardest budgets.

Name the shape before you tune anything: a copilot optimization on a batch job improves a latency that nobody waits on.

### Observability: spans and transcripts

A production agent emits two records: a span tree and sampled transcripts.
A trace, in the telemetry sense, is a tree of spans — timed, attributed records of work.
For an agent the tree is one root span per session, one child per turn, and one grandchild per tool call.
Each span carries the facts that the loop already knows: model id, input and output tokens, cache reads and writes, stop reason, latency, and prompt version.

Metrics aggregate spans, and they tell you *that* something regressed.
Only the replayable transcript — the exact rendered requests and responses — tells you *why*.
The transcript is the unit of debugging (Trace 32).
Store full transcripts for a sample of the traffic: whole sessions, never isolated spans, because a turn without its session is unreadable.
Always keep the flagged sessions: errors, failovers, and complaints.

### Failure handling

Every hop gets a timeout: the model call, each tool, and the session itself.
When a timeout fires, the harness classifies the failure on two axes: transient or permanent, and idempotent or not ([Chapter 4](ch04.md)).
A model call that executed no tool is idempotent, so a retry re-runs sampling only.
A turn whose tool already ran is not idempotent.
A retry there repeats the duplicate-invoice bug from [Trace 10](ch04.md#trace-10-what-happens-when-a-tool-call-fails), so the harness surfaces "state unknown" instead.

Retries that pass the gate still need backoff with jitter, a per-session retry budget, and a circuit breaker.
A provider outage must not become a retry storm.
When the budget is spent, the harness routes the call to a fallback model.
The fallback is a cheaper or older tier, tested in advance against the same prompt and tools.
The last resort is graceful degradation: a reduced answer that says it is reduced, instead of an error page.
The harness flags every degraded or failed-over response, so quality metrics can segment on the flag (Trace 31).

### Cost engineering

Input tokens dominate agent spend, and the input grows with the square of the turn count.
The API is stateless, so every turn resends the whole history ([Chapter 2](ch02.md)).
Turn *n* therefore pays for the *n−1* turns before it.

Prompt caching reduces that cost.
The API re-reads the stable prefix and the prior history at ~0.1× the input price, and processes only the new suffix in full ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).
Cache writes cost 1.25×–2×, so the gain depends on the hit rate — watch it as a first-class production metric.

The other levers, in order of leverage:

- **Fewer turns.** Turn count drives the quadratic term; the turn-count diagnosis in [Chapter 1](ch01.md) is also a cost tool.
- **Model tiering per step.** Route mechanical steps to a cheap tier, and judgment to a capable one ([Chapter 2](ch02.md)).
- **Batch for offline work.** Anything nobody waits for costs 0.5×.
- **Budgets per session.** A token and turn budget stops doomed sessions before they reach the cap.

### Latency anatomy

Turn count dominates a session's latency.
The session latency is a sum over turns: time-to-first-token, plus generation time, plus tool execution time.
Generation time is the output token count divided by the tokens per second.
TTFT grows with the uncached input length, and a cached prefix cuts it, so caching is also a latency lever.
Tokens per second is roughly fixed for each model tier.
Each extra loop iteration pays a full TTFT plus a full generation.

So the ranking is stable: fewer turns first, shorter context second, model choice third.
Streaming improves perceived latency only; the total latency is unchanged.

Turn count decides correctness as well as latency, because reliability multiplies.
A step that works 95 times in 100 finishes a twenty-step task about a third of the time.
[Appendix A](appendices.md#appendix-a--quick-reference-tables) holds that table. It is why a shorter loop beats a better prompt.

### Prompts and configs are deploy artifacts

The prompt text, the tool list, the model id, and the budgets decide a production agent's behavior as much as the code does.
Treat that bundle as one versioned config artifact: review each change, stamp the version on every span, and roll back like code.
Every prompt deploy changes the cache prefix, so the hit rate falls and the cost rises until the new prefix warms ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).

### Staged model upgrades

Pin the exact model id; never serve a provider alias.
An alias lets the provider change what your fleet runs, with no deploy from you.
An upgrade is then a staged rollout: the eval gate first ([Trace 27](ch10.md#trace-27-what-happens-when-an-eval-suite-runs)), then a canary cohort, then the fleet.
Keep the old pin deployable for rollback.
Prompts are tuned to a model, so an upgrade is also a prompt re-evaluation (Trace 33).

Judge an upgrade on two frontiers.
The intelligence frontier is the most capable model available; the efficiency frontier is the cheapest model above your quality bar.
Routine fleet work prices on the efficiency frontier, and that frontier moves faster.
So a gate that declines an upgrade is a normal outcome, not a failed test:
the candidate lost on cost per solve at equal quality, and the eval proved it before the fleet paid for it.

### The cost model of an agent fleet (L3)

The fleet's KPI is **cost per solve**: the cost per session divided by the solve rate.
The division is the point.
A quality regression raises cost per solve with no change in spend, because failed sessions consume a full budget and solve nothing.
Quality is therefore a cost lever, and the cheapest sessions to remove are the doomed ones.

The numerator has two dominant levers, both already in this chapter.
Cache hit rate scales the quadratic input term by up to ~0.1×, and turn count is that term.
Tier mix and batch share follow.
Rank task classes by total spend, not by per-session cost: a cheap task at huge volume outweighs a rare expensive one.
Re-measure cost per solve after each change.

### In other stacks

- **OTel-style tracing:** map LLM work onto standard trace semantics — one span per model call and one per tool call, with model, token-usage, and latency attributes. Agent traces then join your existing service traces.
- **Gateways and routers:** a proxy layer in front of the providers. It owns routing, fallback, API keys, rate limits, and budgets — one enforcement point for the Trace 31 policies.
- **Hosted eval-and-monitor platforms:** transcript capture, online scoring, and dataset building from flagged sessions, sold as a product — the Trace 32 loop, managed.
- **All stacks:** the pattern is the same for every vendor — a span tree to locate, a replayable transcript to explain, and a per-solve cost to decide.

## Traces

### Trace 31: What happens when a production request fails over

A copilot turn is running, and the primary model call returns nothing.

1. **Harness** sends the turn's model call with a deadline; no stream event arrives in time.
2. **Harness** cancels the request when the timeout fires.
3. **Harness** classifies the failure: it is transient, and the step is idempotent ([Chapter 4](ch04.md)).
   - This call executed no tool, so a retry re-runs sampling only; a turn whose tool already ran must surface "state unknown" instead ([Trace 10](ch04.md#trace-10-what-happens-when-a-tool-call-fails)).
4. **Harness** retries the primary with backoff and jitter, inside a per-session retry budget.
5. **LLM** times out again; the budget is spent, and the circuit for the primary opens.
6. **Harness** routes the call to the fallback model, a cheaper tier that is tested in advance.
7. **LLM** answers within the deadline on the fallback tier.
8. **Harness** returns the answer marked degraded; the user sees a caveat, not an error page.
9. **Obs** records the failover on the turn span: timeout, retry count, fallback model id, degraded flag.
10. **Obs** segments the quality dashboards by the flag, so fallback answers stay out of the baseline numbers.

**Where this can fail**

- **Symptom:** a side effect ran twice.
    - **Cause:** the harness retried a turn whose tool had already executed.
    - **Where to look:** the executor logs — two tool executions for one model call.
- **Symptom:** a provider outage gets worse as you retry.
    - **Cause:** no jitter and no circuit breaker, so every client retries at the same moment.
    - **Where to look:** your request rate against the provider error rate.
- **Symptom:** quality drops for days and nobody notices.
    - **Cause:** fallback answers carry no flag, so they mix into the baseline metrics.
    - **Where to look:** the share of traffic per model id.
- **Symptom:** the fallback path fails the first time it fires.
    - **Cause:** nobody exercised it, so the prompt or the tool schema does not fit the fallback tier.
    - **Where to look:** the failover drill results and the fallback call logs.

### Trace 32: What happens when a bad session is traced

A user reports yesterday's answer as wrong; the ticket carries a session id.

1. **User** (here, the operator) opens the ticket, which carries the session id that the client stamps on every response.
2. **Obs** returns the session's span tree: one root span, a span per turn, a span per tool call.
3. **User** scans the span attributes and finds the anomaly: the answer goes wrong at turn 7.
4. **Obs** serves the sampled full transcript: the exact rendered requests and responses, byte for byte.
5. **User** reads backward from turn 7 and finds the poison in turn 6.
   - The poison is a tool result that carries an error page formatted like data.
6. **Harness** replays the stored transcript up to turn 6 against the pinned model.
7. **LLM** reproduces the wrong answer from the poisoned context; the failure is now repeatable.
8. **User** classifies it in the failure taxonomy as "tool error surfaced as success".
   - The class, not this one prompt, decides where the fix goes: into the tool executor.
9. **User** adds the transcript as an eval case, so the class stays fixed ([Chapter 10](ch10.md)).
10. **CI** runs the new case in every future eval gate, including the upgrade gate of Trace 33.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Obs
  participant Harness
  participant LLM
  participant CI
  User->>Obs: query session id
  Obs-->>User: span tree per turn
  User->>Obs: fetch full transcript
  Obs-->>User: replayable transcript
  User->>Harness: replay to turn six
  Harness->>LLM: resend rendered context
  LLM-->>Harness: same wrong answer
  Harness-->>User: reproduction confirmed
  User->>CI: add eval case
```

*Figure 12.2 — the metrics locate the turn; only the replayable transcript can name the poison.*

**Where this can fail**

- **Symptom:** the session cannot be found.
    - **Cause:** the session id never reached the client, or the spans are not keyed by it.
    - **Where to look:** the response metadata and the span attributes.
- **Symptom:** spans exist but the transcript is gone.
    - **Cause:** metrics-only telemetry, or sampling that dropped the session.
    - **Where to look:** the sampling policy — sample whole sessions, and keep the flagged ones.
- **Symptom:** the replay produces a different answer.
    - **Cause:** the store kept parsed messages instead of the rendered request, or the model id changed.
    - **Where to look:** the stored request bytes against the model id on the span.
- **Symptom:** the same failure returns next month.
    - **Cause:** the fix patched this session's prompt instead of the failure class.
    - **Where to look:** the taxonomy entry, and whether an eval case guards the class.

> You classify twenty production transcripts into a failure taxonomy and compute per-solve cost from their usage records.

### Trace 33: What happens when the underlying model is upgraded

The provider ships a new model generation; your fleet serves a pinned id.

1. **Harness** serves every session from an exact pinned model id; a provider alias never decides what runs.
2. **User** declares the candidate id in config beside the pin; nothing serves it yet.
3. **CI** runs the eval suite against the candidate: the same tasks and graders that scored the pinned baseline ([Trace 27](ch10.md#trace-27-what-happens-when-an-eval-suite-runs)).
4. **CI** issues the gate verdict by comparing candidate scores to the baseline, not to an absolute bar.
   - Prompts are tuned to a model; a regression here often means the prompt needs re-tuning for the candidate, not that the candidate is worse.
5. **Harness** routes a canary cohort — a small share of sessions — to the candidate id.
6. **Obs** watches the online metrics per cohort: solve rate, turns per session, per-solve cost, degraded flags.
7. **User** waits for enough sessions to separate signal from noise, then compares the cohorts.
8. **Harness** rolls the fleet to the candidate, or rolls the canary back to the pin; either direction is one config change.
9. **User** keeps the old pin deployable until the candidate survives a full traffic cycle, because some regressions appear only weekly.

  D -->|fail| H[Stay on pin]

  E --> F{Online metrics hold}

*Figure 12.3 — two gates again: the offline eval earns the canary, the online metrics earn the fleet.*

**Where this can fail**

- **Symptom:** the fleet's behavior shifts overnight with no deploy.
    - **Cause:** an alias, not a pin — the provider upgraded for you.
    - **Where to look:** the model id on spans, plotted by day.
- **Symptom:** the gate passed but the canary regresses.
    - **Cause:** the eval suite drifted from the production task distribution.
    - **Where to look:** flagged canary sessions against the suite's task coverage ([Chapter 10](ch10.md)).
- **Symptom:** quality held, but the bill grew after rollout.
    - **Cause:** the gate scored correctness only; the candidate takes more turns per solve.
    - **Where to look:** per-solve cost per cohort during the canary.
- **Symptom:** the rollback itself fails.
    - **Cause:** prompts or configs already migrated to candidate-only behavior.
    - **Where to look:** the config diff between the pin and the candidate.

## Questions

### Tier 1 — Explain

**Q 12.1 — Why does an agent session's input cost grow roughly with the square of its turn count?**

**Answer.** The API is stateless, so every turn resends the entire history ([Chapter 2](ch02.md)).
Turn *n* therefore pays input for all *n−1* turns before it.
The sum over a whole session grows with the square of the turn count.
Prompt caching reduces that growth: the API re-reads the prefix and the prior history at ~0.1×, and processes only the new suffix in full ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).
That makes cache hit rate and turn count the two dominant cost levers.

*Strong answers also mention:* cache writes cost 1.25×–2×, so a changing prefix makes caching a net loss.

**Q 12.2 — What telemetry does a production agent emit, and what is the unit of debugging?**

**Answer.** It emits a span tree per session: a root span, a span per turn, and a span per tool call.
Each span carries the attributes that the loop already knows: model id, token counts, cache reads and writes, stop reason, latency, and prompt version.
It also stores sampled full transcripts: the exact rendered requests and responses.
Metrics locate a regression, but only the replayable transcript explains it.
The transcript is therefore the unit of debugging.
Sample whole sessions, never isolated spans, and keep the flagged ones.

*Strong answers also mention:* stamping prompt version and model id on every span, so any regression is attributable to a deploy.

**Q 12.3 — Which quantities compose an agent's latency, and which usually dominates?**

**Answer.** Turn count usually dominates, because each extra turn pays a full TTFT plus a full generation.
Each turn costs time-to-first-token, plus generation time, plus tool execution time.
Generation time is the output token count divided by the tokens per second.
A session's latency is the sum of those costs across the turns.
Hence the ranking:

1. Fewer turns.
2. Shorter context (a cached prefix cuts TTFT).
3. A faster model.

*Strong answers also mention:* streaming improves perceived latency only; the total is unchanged.

**Q 12.4 — Why treat prompts as deploy artifacts?**

**Answer.** The prompt text, the tool list, the model id, and the budgets decide behavior as much as the code does.
An unversioned prompt edit is an unattributable regression: nothing links the quality change to the change that caused it.
So version the bundle, stamp the version on every span, and roll back like code.
Every prompt deploy also changes the cache prefix, so expect a lower hit rate and a higher cost until it warms ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).

*Strong answers also mention:* prompt changes go through the same eval gate as model changes ([Chapter 10](ch10.md)).

### Tier 2 — Reason

**Q 12.5 — When may the harness auto-retry a failed production step, and what must surround the retry?**

**Answer.** Only when the failure is transient and the step is idempotent ([Chapter 4](ch04.md)).
A model call that executed no tool is idempotent, so a retry re-runs sampling.
A turn whose tool already ran is not: a timeout proves nothing about server state, so the harness surfaces "state unknown" instead.
Legal retries still need backoff with jitter, a per-session retry budget, and a circuit breaker, so an outage does not become a retry storm.

*Strong answers also mention:* idempotency keys make side-effecting steps safely retryable at the server ([Trace 10](ch04.md#trace-10-what-happens-when-a-tool-call-fails)).

**Q 12.6 — Why watch tail latency per shape instead of average latency?**

**Answer.** A session's latency is a sum over many turns, so the distribution has a heavy tail: one slow turn delays the whole session.
An average hides that tail, and the tail is what users experience: the p99 copilot session produces the complaint.
Watch p95 and p99 for each deployment shape.
A copilot p99 of one minute is a product bug; the same number in a batch job is acceptable.
Tails also set the timeouts: a deadline below the legitimate tail creates failovers that were never needed (Trace 31).

*Strong answers also mention:* per-turn tails compound with turn count, so turn reduction improves tails faster than averages.

**Q 12.7 — After a deploy, cache hit rate falls and cost jumps, yet nothing about caching changed. What happened?**

**Answer.** The deploy changed the rendered prefix.
The cache is a byte-exact prefix match ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).
So a new prompt version, a reordered tool list, or dynamic content early in the prompt invalidates every stored entry.
Every session then pays cache writes at 1.25×–2× with no reads, until the new prefix warms.
Watch the hit-rate curve: a clean prompt deploy falls once and recovers; a new per-request invalidator never recovers.
Compare two rendered requests byte by byte to find it ([Chapter 2](ch02.md)).

*Strong answers also mention:* stamping prompt version on spans makes the dip attributable to the exact deploy within minutes.

### Tier 3 — Design & Debug

**Q 12.8 — Per-solve cost doubled while traffic stayed flat. Walk your diagnosis.**

**Answer.** Decompose the KPI first: cost per solve = cost per session ÷ solve rate.
Check the denominator before the bill: a quality regression halves the solve rate and doubles cost per solve, with no change in spend.
If the solve rate held, split cost per session by task class and by deployment shape.
Then split the class that grew into its factors: turns per session, tokens per turn, cache read ratio, and model tier mix.
Match the break point to a deploy: the prompt version and the model id on each span date it exactly.
Fix the largest factor — commonly a cache invalidator (Q 12.7) or a turn-count regression — and re-measure the same classes.

*Strong answers also mention:* session budgets that stop doomed runs early, and checking whether a floating alias silently changed the model (Trace 33).

**Q 12.9 — Design the rollout of a new model generation across a copilot, a batch fleet, and a CI agent.**

**Answer.** Pin all three fleets to exact model ids; a provider alias never decides what runs.
Gate once per fleet, not once overall: each shape has its own eval suite and its own bar ([Trace 27](ch10.md#trace-27-what-happens-when-an-eval-suite-runs)).
Prompts may need re-tuning per shape before the gate is fair.
Then canary in risk order.

1. The batch fleet, because verify steps contain bad output and nobody waits.
2. The copilot, watched by the degraded-flag dashboards.
3. The CI agent, because nobody supervises it.

Hold each canary for a full traffic cycle, and gate on per-solve cost as well as on correctness.
A better model that takes more turns is a regression.
Keep the old pin deployable everywhere until the last fleet survives.

*Strong answers also mention:* adding recent flagged transcripts (Trace 32) to the suite before gating, so the gate reflects today's traffic, not last quarter's.

## Common mistakes & red flags

- **"We retry everything; retries are free."** A timeout on a step whose tool already ran proves nothing about state; a retry duplicates the side effect ([Chapter 4](ch04.md)). Retry only transient failures of idempotent steps.
- **"Average latency looks fine."** Users experience the tail, and agent sessions sum many turns, so the tails compound. Watch p95 and p99 per deployment shape.
- **"We track cost per request."** The KPI is cost per solve. Failed sessions keep per-request cost flat while the bill climbs; the solve rate in the denominator is how quality changes cost.
- **"We log errors, so we can debug."** An error line without its session explains nothing. The unit of debugging is the replayable transcript, sampled as whole sessions.
- **"We always run the provider's latest model."** An alias is a fleet-wide deploy that you did not schedule and did not gate. Pin, eval, canary, then roll (Trace 33).
- **"The prompt is just text; edit it in place."** A prompt edit is a deploy: version it, stamp spans with it, and expect the cache misses ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)). Unversioned edits make regressions unattributable.
- **"The fallback will work when we need it."** An untested failover path fails exactly when it fires. Drill it: test the fallback tier against the real prompt and tools before an outage does.
