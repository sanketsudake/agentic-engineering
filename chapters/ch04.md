# Chapter 4 — Tool Design & MCP

## Why this chapter

Tools are the only way an agent changes anything outside the model.
This chapter zooms into steps 4–6 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): the model emits a call, the harness executes it, and the result comes back as context.
The mental model: a tool is a schema plus an executor.
The schema is a prompt that the model reads; the executor is production code that you own.
Most agent failures happen on this boundary: vague descriptions, unbounded results, swallowed errors, and duplicated side effects.
MCP standardizes the boundary, so tools can run outside your process.
Level emphasis: [L1]–[L3]; the (L3) section is optional on first read.

## Concepts

**Tool schemas and descriptions are prompts.** A tool is declared as `{name, description, input_schema}`, where the schema is JSON Schema.
The harness sends these definitions in the context every turn.
The model reads them to decide when to call a tool, which tool to call, and which arguments to send.
No other channel informs that decision.
A description must therefore say when to use the tool, and when not to use it, not only what it does.
Each parameter needs its own description, because a vague schema produces wrong calls.

Give every tool description the same review that you give a prompt.
[Chapter 1](ch01.md) shows the effect: adding a tool changes model behavior even when the model never calls it.

**Schema strictness.** `strict: true` makes the provider return inputs that always match the schema.
The provider uses constrained decoding, which blocks any token that would break the schema.
Strictness needs `additionalProperties: false` and a `required` list.
Strictness removes failures of shape, not failures of meaning: a well-formed path can still point at nothing.

**The call-and-result shape.** The model returns `tool_use` content blocks and stops with `stop_reason: "tool_use"`.
One assistant message can carry several `tool_use` blocks, which are parallel calls.
The harness executes every call and replies with one `tool_result` block for each call.
Each result block carries the matching `tool_use_id`, and all of them travel in one user message.
A failed tool returns a `tool_result` with `is_error: true`; the harness never drops a result.

> **Lab 2 — Define and dispatch tools.** `labs/lab02-define-tools/` · [L1] · ~30 min · offline.
> You write the schemas and a dispatcher that turns every failure into text the model can read.

**Execution end to end.** The harness owns a pipeline between the model's block and the next turn: parse, validate, gate, dispatch, capture, truncate, append.
Trace 9 walks this pipeline step by step.
Every stage can corrupt what the model reads next, so every stage is a debugging checkpoint.

**Errors, idempotency, retries.** The model can only fix what it can see.
A tool error must come back as text in the `tool_result`, marked `is_error: true`.
An idempotent tool leaves the same state when it runs twice, so a retry is safe.
Reading a file is idempotent; sending an invoice is not.
The harness retries a transient failure only when the tool is idempotent, and every other failure goes to the model as an error result.
Trace 10 walks the failure path, and the worst case in it: silent success.

**Tool-result budgets.** A tool result becomes context that the model carries for the rest of the session ([Chapter 3](ch03.md)).
The harness therefore caps each result at a per-tool budget.
It adds an explicit marker to the cut text: "truncated: showing 10,000 of 91,000 chars".
It also offers a way to read the rest, such as an offset or a narrower query.
Always mark a truncation: the model must know that it read one part of the result.

**Sandboxing mechanics.** Two layers contain a tool.
The permission gate runs before dispatch, and decides allow, deny, or ask for each call.
The blast radius limits what the executor can touch when the gate is wrong: a container, a read-only mount, no network, and scoped credentials.
Which policy fits which deployment is a judgment question, and that layer comes later in this book.
This chapter covers only the machinery.

**Tool classes.** Four classes of tool are common.
Search tools are read-only and cheap to retry; their risk is the size of the result.
Code execution tools, such as a shell or an interpreter, give the most breadth and the largest blast radius.
Computer use tools take screenshots and send clicks; they are slow, and every action needs a gate.
External API tools carry side effects; idempotency and authentication are their design problems.

**MCP: what it standardizes.** The Model Context Protocol (MCP) is an open protocol that puts tools behind a standard client-server interface, so one server can serve any harness.
It standardizes three server primitives: tools (`tools/list`, `tools/call`), resources (`resources/list`, `resources/read`), and prompts (`prompts/list`, `prompts/get`).
It also standardizes two transports: stdio for local subprocess servers, and Streamable HTTP for remote servers.
Tool results return `content[]` blocks, an optional `structuredContent` object that the server validates against an `outputSchema`, and `isError: true` for execution errors.
Note the spelling: MCP uses `isError` on its results, and the provider API uses `is_error` on `tool_result` blocks.
HTTP transports authenticate with OAuth 2.1; stdio servers use environment credentials.

The current revision (2026-07-28) is stateless, and has no handshake.
Every request carries the protocol version, the client info, and the client capabilities in `params._meta`.
The server accepts or rejects each request on its own.
Servers must implement `server/discover`, an RPC that returns the supported versions, the capabilities, and the server info; the client chooses whether to call it.
Trace 11 follows this stateless flow.

**The legacy handshake.** Revisions up to 2025-11-25 start with a stateful handshake.
The client sends `initialize` with its version and its capabilities.
The server answers with its own version and capabilities.
The client then confirms with `notifications/initialized`.
Many deployed servers still use this handshake.
The spec therefore defines a compatibility matrix between the legacy revisions and the current one, and most clients support both eras.

### Tool-surface design: bash breadth versus dedicated tools (L3)

The working rule is: use one broad tool for exploration inside a strong sandbox, and dedicated tools for side effects that need a gate.
One `bash` tool covers everything that a shell can do.
A dedicated tool instead gives a typed schema, a narrow gate, and a result that the harness can cap.

Breadth is cheap to build and hard to gate, because the permission gate must then read arbitrary shell text.
Dedicated tools reverse these costs: each one is easy to gate and easy to budget.
They also cost more, because you must predict what the agent needs, and every definition spends context tokens each turn.
Description quality then decides whether the model picks the right tool.

### In other stacks

- **OpenAI Agents SDK:** tools are decorated Python functions attached to an agent; `Runner.run()` owns the execute-and-append loop, with an enforced `max_turns` limit.
- **OpenAI Agents SDK:** guardrails validate input and output at the loop boundary, so the gate is a first-class primitive.
- **LangGraph:** tool execution is a graph node you wire yourself; the call-tools-then-loop edge is explicit, so retry and truncation policy live in your node code.
- **Both:** the schema-is-a-prompt rule holds in every stack; the model sees only the name, description, and schema your code declares.

## Traces

### Trace 9: What happens when a tool call executes end to end

The model asks to run the test suite: one `tool_use` block, name `run_tests`, input `{"path": "tests/"}`.

1. **LLM** emits the `tool_use` block — id, name, input — and stops with `stop_reason: "tool_use"`.
2. **Harness** parses the block and looks the name up in its tool registry.
   - An unknown name becomes an error result, not a crash; the model sometimes invents a tool name.
3. **Harness** validates the input against the schema: missing, unknown, or mistyped arguments.
4. **Guard** checks the call against permission rules: allow, deny, or ask the user.
5. **Tools** dispatches: the executor function runs with the validated input.
6. **Env** does the work — the process runs, the file changes, the API responds.
7. **Tools** captures everything as text: stdout, stderr, exit code, return value, or exception.
8. **Harness** truncates the captured text to the result budget, with an explicit marker.
9. **Harness** appends a `tool_result` block with the matching `tool_use_id` and resends the context.
10. **LLM** reads the result as ordinary input tokens and plans the next step.

```mermaid
sequenceDiagram
  autonumber
  participant LLM
  participant Harness
  participant Guard
  participant Tools
  participant Env
  LLM-->>Harness: tool_use block
  Harness->>Harness: parse and validate
  Harness->>Guard: check permission rules
  Guard-->>Harness: allow
  Harness->>Tools: dispatch validated call
  Tools->>Env: execute action
  Env-->>Tools: raw output
  Tools-->>Harness: captured text
  Harness->>Harness: truncate to budget
  Harness->>LLM: append tool_result
```

*Figure 4.1 — every stage between the model's call and its next turn belongs to the harness.*

**Where this can fail**

- **Symptom:** the model calls a tool that does not exist. **Cause:** the model invented the name, often after a description that implies extra capability. **Where to look:** the tool definitions and the unknown-tool error result.
- **Symptom:** the harness rejects a call that looks correct. **Cause:** the input does not match the schema: a string where the schema wants an integer, or a forbidden argument. **Where to look:** the validation error text in the transcript.
- **Symptom:** the agent stops in the middle of a task. **Cause:** the gate waits for a human answer that nobody gave. **Where to look:** the harness's pending-approval state.
- **Symptom:** the next request to the model is very large. **Cause:** step 8 did not run, or the result budget is far too high. **Where to look:** the token counts for each message.
- **Symptom:** the provider rejects the follow-up request. **Cause:** parallel calls answered across several messages, or one result missing. **Where to look:** the message structure — one user message must carry all results.

### Trace 10: What happens when a tool call fails

The agent calls `send_invoice`; the network drops the response after five seconds.

1. **Tools** runs the executor; the HTTP call times out and raises an exception.
2. **Tools** catches the exception, because the loop must survive any tool failure.
3. **Tools** converts it to plain text: exception type, message, and any partial output.
4. **Harness** marks the result `is_error: true`, so the model can read the failure.
5. **Harness** consults its retry policy: retry only a transient failure of an idempotent tool.
   - `send_invoice` is not idempotent, and a timeout does not say whether the server created the invoice.
6. **Harness** therefore surfaces the failure: it appends the error result and resends the context.
7. **LLM** reads the error and adapts: it lists the invoices to check the state before it sends again.
8. **Harness** counts consecutive failures; repeated identical errors trigger a stop or an escalation.

```mermaid

  B --> C[Result marked is_error]
  C --> D{Transient and idempotent}
  D -->|yes| E[Harness retries with backoff]
  D -->|no| F[Error appended to context]
  E -->|still failing| F
  F --> G[Model reads and adapts]
  classDef process fill:#38bdf8,stroke:#0369a1,color:#fff
  classDef resource fill:#fb7185,stroke:#be123c,color:#fff
  classDef lease fill:#f59e0b,stroke:#b45309,color:#fff
  classDef leader fill:#10b981,stroke:#047857,color:#fff

  class E leader

```

*Figure 4.2 — the retry gate: only transient failures of idempotent tools bypass the model.*

The worst bug class here is silent success.
An executor catches an exception and returns an empty string or the word "done".
The model reads that result as success, reports the task complete, and the failure reaches production.
Every step above exists to stop this: a failure must become text that the model reads.

**Where this can fail**

- **Symptom:** the model claims success but nothing changed. **Cause:** a swallowed error — the executor returned empty text or "ok". **Where to look:** the raw tool result in the transcript against the executor logs.
- **Symptom:** the same invoice or email went out twice. **Cause:** the harness retried a tool that is not idempotent after a timeout. **Where to look:** the executor logs — two attempts for one model call.
- **Symptom:** the model repeats the same failing call without end. **Cause:** the error text has no detail that the model can act on, such as the single word "error". **Where to look:** the error strings in the transcript.
- **Symptom:** one bad call stops the whole loop. **Cause:** an executor exception escaped the dispatcher's catch. **Where to look:** the harness stack trace.

### Trace 11: What happens when the agent calls an MCP server

The harness is configured with a remote MCP server that exposes a `search_docs` tool (current revision, 2026-07-28).

1. **Harness** can call `server/discover` first: supported versions, capabilities, server info. Servers must implement it; clients choose whether to call it.
2. **Harness** sends `tools/list`; like every request, it carries the protocol version, client info, and capabilities in `params._meta`.
   - This revision has no handshake, so each request stands alone. A rejected version returns error -32022 with the versions that the server supports.
3. **MCP** returns the tool definitions, plus caching hints (`ttlMs`, `cacheScope`) that say how long the list stays valid.
4. **Harness** merges the MCP tools into the model's tool list, next to the local tools.
5. **LLM** emits a `tool_use` block that names the MCP tool; it cannot tell MCP tools from local ones.
6. **Harness** routes the call to the server: `tools/call` with the tool name and arguments.
7. **MCP** executes and returns `content[]` blocks, optional `structuredContent`, and `resultType: "complete"`.
   - A failure inside the tool sets `isError: true` in the result, so the model reads it, like `is_error` in Trace 10. A protocol error, such as an unknown tool or a malformed request, returns a JSON-RPC error to the harness instead.
8. **Harness** appends the content as an ordinary `tool_result` and resends the context.

```mermaid
sequenceDiagram
  autonumber
  participant LLM
  participant Harness
  participant MCP
  opt discovery
    Harness->>MCP: server discover
    MCP-->>Harness: versions and capabilities
  end
  Harness->>MCP: tools list
  MCP-->>Harness: tool defs plus cache hints
  Harness->>LLM: definitions in context
  LLM-->>Harness: tool_use for MCP tool
  Harness->>MCP: tools call with arguments
  MCP-->>Harness: content blocks plus isError
  Harness->>LLM: append tool_result
  Note over Harness,MCP: every request carries version metadata
```

*Figure 4.3 — the stateless flow: no handshake; version and identity travel with each request.*

**Where this can fail**

- **Symptom:** the server rejects every request with error -32022. **Cause:** the client and the server share no protocol revision. **Where to look:** the list of supported versions in the error; `server/discover`.
- **Symptom:** the model calls a tool that the server no longer has. **Cause:** the harness kept the `tools/list` result past its `ttlMs`. **Where to look:** the cache hints against the age of the harness cache.
- **Symptom:** the harness logs a JSON-RPC error, but the model saw nothing. **Cause:** the harness treated a protocol error as a tool error and appended nothing. **Where to look:** the harness MCP logs against the transcript.
- **Symptom:** the server works locally over stdio and fails after deployment over HTTP. **Cause:** authentication — HTTP transports require OAuth 2.1, and stdio ran on environment credentials. **Where to look:** 401 responses and the protected-resource metadata.
- **Symptom:** an older server returns an error on the first request. **Cause:** it expects the legacy `initialize` handshake. **Where to look:** the server's supported revisions and the compatibility matrix.

## Code-reading exercises

The loop shape is correct in all three snippets, so the bugs are elsewhere.
Each snippet builds on the Lab 3 loop.
Read each snippet for what the model will see in its context, not for syntax.

### Exercise 1 — The generous result

```python
def read_logs(path: str, pattern: str = "") -> str:
    """Return matching lines from a log file."""
    lines = open(path).read().splitlines()
    if pattern:
        lines = [l for l in lines if pattern in l]
    return "\n".join(lines)

def run_agent(model, tools, user_msg, max_turns=8):
    transcript = [{"role": "user", "content": user_msg}]
    for _ in range(max_turns):
        resp = model.complete(transcript, tools)
        transcript.append({"role": "assistant", "content": resp.text,
                           "tool_calls": [{"id": c.id, "name": c.name,
                                           "input": c.input}
                                          for c in resp.tool_calls]})
        if not resp.tool_calls:
            return resp.text
        for call in resp.tool_calls:
            fn = tools[call.name]
            try:
                content = str(fn(**call.input))
            except Exception as exc:
                content = f"error: {exc}"
            transcript.append({"role": "tool", "tool_call_id": call.id,
                               "content": content})
    return ""
```

**What's wrong?**

Two bugs.
(1) The code sets no result budget: `read_logs` with an empty pattern returns the whole file.
A 200 MB log becomes one tool message, because Trace 9 step 8 never happens.
Every later turn pays for those tokens again, and the earlier content is now a small part of the context.
One result can also overflow the window; the next response then stops with `model_context_window_exceeded`.
(2) `tools[call.name]` sits outside the `try` block.
A tool name that the model invented raises `KeyError` and stops the loop.
The model never sees an error that it could correct (Trace 9 step 2).

**Fix.**
Cap every result before you append it.
Cut at a per-tool character budget, add an explicit truncation marker, and tell the model how to read more.
A narrower `pattern` or an offset parameter gives that path.
Move the lookup into the error path: use `fn = tools.get(call.name)` and return "error: unknown tool".
Lab 2's dispatcher does both.

### Exercise 2 — The helpful retry

```python
import requests

API = "https://billing.internal"

def send_invoice(customer_id: str, amount_cents: int) -> str:
    """Create and send an invoice. Returns the invoice id."""
    resp = requests.post(f"{API}/invoices",
                         json={"customer": customer_id,
                               "amount_cents": amount_cents},
                         timeout=5)
    resp.raise_for_status()
    return resp.json()["invoice_id"]

def dispatch(call, tools, attempts=3):
    """Run one tool call; retry to smooth over flaky networks."""
    fn = tools.get(call.name)
    if fn is None:
        return f"error: unknown tool {call.name}"
    for _ in range(attempts):
        try:
            return str(fn(**call.input))
        except requests.Timeout:
            continue  # transient - try again
        except Exception as exc:
            return f"error: {exc}"
    return "error: timed out after 3 attempts"
```

**What's wrong?**

One bug, and an expensive one.
The dispatcher retries every tool after a timeout, but a timeout does not prove failure.
It proves only that no response arrived.
The server may have committed the POST before the response was lost.

`send_invoice` is not idempotent, so this loop can bill a customer three times, and the transcript still shows one clean call.
The retry policy must be per tool, not global (Trace 10 step 5).
"Safe to run twice" is a property of the tool, not a property of the network.

**Fix.**
Mark each tool as idempotent or not idempotent at registration.
The dispatcher then retries a timeout only for an idempotent tool.
For a tool with side effects, return the timeout as an error result that says "state unknown — verify before retrying".
Also give the model a tool that can check the state, such as `list_invoices`.
Better still, make the tool idempotent: send an idempotency key with the POST, so the server ignores a duplicate retry.

### Exercise 3 — The quiet failure

```python
import logging

log = logging.getLogger("agent")

def dispatch(call, tools):
    fn = tools.get(call.name)
    if fn is None:
        return ""
    try:
        result = fn(**call.input)
    except Exception:
        log.warning("tool %s failed", call.name)
        result = None
    return str(result or "")

def handle_calls(resp, tools, transcript):
    for call in resp.tool_calls:
        content = dispatch(call, tools)
        transcript.append({"role": "tool",
                           "tool_call_id": call.id,
                           "content": content or "done"})
```

**What's wrong?**

Three bugs, and all of one class: the model reads success where no success happened.
(1) The code logs the exception for the operator and hides it from the model.
`result = None` becomes `""`, and `handle_calls` rewrites `""` to "done".
The model then reports the task complete.
This is the silent-success bug from Trace 10, and it is the hardest one to find, because the transcript looks healthy.

(2) An unknown tool also returns `""`, which becomes "done", so an invented call reads as a completed action.
(3) `str(result or "")` deletes a correct result that is falsy: a tool that returns `0` or `False` also reads as "done".
The log line does not help the model, which can only use what its context contains.

**Fix.**
Turn every failure into text: return the exception type and the message ("error: FileNotFoundError: ..."), and mark the result `is_error: true` where the API supports it.
An unknown tool returns an explicit error string.
Remove the `or ""` fallback, because `str(result)` keeps `0` and `False`.
Keep the log as telemetry, not as the error channel, because the transcript is what the model reads.

## Questions

### Tier 1 — Explain

**Q 4.1 — Why do we say a tool schema is a prompt?**

**Answer.** The harness sends the tool definitions into the context every turn.
The model reads the name, the description, and the parameter schema to decide when to call and how to call.
No other channel informs that decision, so a wrong description produces wrong calls, exactly like a wrong instruction.
That is why a description gets the same review as a prompt.
It is also why adding a tool changes behavior even when the model never calls it ([Chapter 1](ch01.md)).

*Strong answers also mention:* per-parameter descriptions and "when NOT to use this" guidance are the highest-leverage lines.

**Q 4.2 — Walk the path from the model emitting a tool call to the model seeing the result.**

**Answer.** Parse, validate, gate, dispatch, capture, truncate, append (Trace 9).
The harness parses the `tool_use` block and validates the input against the schema.
A permission gate allows, denies, or asks.
The executor runs, and the harness captures the output, the errors, and the exit code as text.
The harness truncates that text to a budget.
It then appends a `tool_result` with the matching `tool_use_id` and resends the whole context.
The model reads the result as ordinary input tokens.

*Strong answers also mention:* each stage is a debugging checkpoint; the transcript shows exactly what the model saw.

**Q 4.3 — What does MCP standardize, and what does it not?**

**Answer.** MCP standardizes the interface between the harness (the client) and the tool provider (the server).
The standard covers three server primitives — tools, resources, and prompts — plus two transports, stdio and Streamable HTTP.
It also covers discovery and the result format: `content[]`, `structuredContent`, and `isError`.
MCP does not standardize what a tool does, how you sandbox it, how you budget its result, or which model runs.
Those stay harness decisions.

*Strong answers also mention:* the current revision (2026-07-28) is stateless; the version and the capabilities travel with each request, and `server/discover` replaces the legacy handshake.

**Q 4.4 — How does a failed tool call reach the model?**

**Answer.** As text, in a `tool_result` block with `is_error: true`, matched to the call by `tool_use_id`.
The executor catches the exception and converts it to a readable message, and the harness never drops it.
The model can only correct what it can see, so an error that reaches only a log file produces repeated retries or an invented success.
The matching MCP flag is `isError` on the tool result.

*Strong answers also mention:* error text quality matters — "error" teaches nothing; "file not found: app.log; directory contains app.log.1" teaches the fix.

### Tier 2 — Reason

**Q 4.5 — When should the harness retry a failed tool call, and when should it surface the error?**

**Answer.** Retry only when two conditions hold: the failure is transient (timeout, rate limit, connection reset) and the tool is idempotent.
Reading a file twice is safe; sending an invoice twice is a billing incident.
A timeout on a tool that is not idempotent says nothing about the server state, so a retry can duplicate the action.
Every other failure goes to the model as an error result, and the model can then check the state and choose the next step.
Cap the number of retries, add backoff, and stop or escalate after repeated identical failures.

*Strong answers also mention:* idempotency keys make side-effecting tools safely retryable at the server.

**Q 4.6 — Why cap tool results, and how do you pick the cap?**

**Answer.** A result becomes context that the model carries in every later turn ([Chapter 3](ch03.md)).
An unbounded result pushes out earlier content and can overflow the window.
Cap each result, mark the truncation explicitly, and give a path to the rest: an offset, pagination, or a narrower query.
Pick the cap from the window budget down.
The results share the window with the system prompt, the history, and the tool definitions, and the later turns still need space.
A silent truncation is worse than a small cap: the model must know that it read one part of the result.

*Strong answers also mention:* per-tool budgets; a failing test's output earns more space than a search result list.

**Q 4.7 — The model emits three tool calls in one assistant message. What must the harness do, and what breaks if it splits them?**

**Answer.** Execute all three calls and return all three `tool_result` blocks in one user message, each one matched by `tool_use_id`.
The API requires an answer to every `tool_use` block in the previous assistant message before the conversation continues.
A harness that splits the results across messages, or drops one result, makes the follow-up request invalid.
Parallel calls also raise an execution question: run them at the same time only when the tools share no state.

*Strong answers also mention:* a failed member of the batch still returns a result — `is_error: true`, never dropped.

**Q 4.8 — Your harness caches an MCP server's tool list. What can go stale, and what does the spec give you?**

**Answer.** The tool set and every schema can change on the server.
An old cache makes the model call tools that the server removed, or send arguments in an old shape.
List results carry caching hints — `ttlMs` and `cacheScope` — that say how long and how widely the list stays valid; honor them.
The current spec is stateless, so there is no session to invalidate.
Refresh the list when the TTL expires, and when a protocol error reports an unknown tool.
Discovery stays cheap, because `tools/list` is one request.

*Strong answers also mention:* a changed tool list also changes the model's behavior, and it invalidates any prompt-cache prefix that contains the definitions ([Chapter 2](ch02.md)).

### Tier 3 — Design & Debug

**Q 4.9 — A support agent occasionally sends the same refund twice. Walk your diagnosis and fix.**

**Answer.** Read the transcript around a duplicated refund first.
Two mechanisms can produce it.
The harness retried a `send_refund` call that timed out; the executor logs then show two attempts for one model call.
Or the model called again after an error that was in fact a success; the transcript then shows two `tool_use` blocks.
The first is a retry-policy bug: the tool is not idempotent, so a timeout must surface, not start a retry (Trace 10; Exercise 2).
The second is an error-quality bug: the timeout text reported failure, so the model sent the refund again.

Fix both ends: an idempotency key on the refund API makes any retry safe, and the timeout text must say "state unknown — verify first".
Back that text with a `get_refund_status` tool.

*Strong answers also mention:* an eval that replays the timeout and asserts exactly one refund; evals come later in this book.

**Q 4.10 — Design the tool surface for an agent that investigates production incidents but must never change anything.**

**Answer.** Start from the blast radius, not from convenience.
Read-only credentials at the infrastructure layer stop every tool from changing state, even when the model tries.
Prefer dedicated read tools — query logs, fetch metrics, describe deploys — over one bash tool.
A typed schema is easy to gate, and its result is easy to cap.
If exploration needs breadth, add bash inside a sandbox with a read-only mount and no production credentials (the L3 trade in Concepts).
Put the boundary cases, such as a tool that runs a command inside a pod, behind ask rules.
Cap every result, because logs and metrics are the common cause of a context flood, and offer pagination parameters instead of larger caps.

*Strong answers also mention:* the deny-by-default gate is mechanical; the choice of what belongs on the allow list is a judgment question that comes later in this book.

## Common mistakes & red flags

- **"The description barely matters; the model will work it out."** The description is all that the model reads before it calls. A vague description is the most common cause of a wrong tool choice.
- **"We validate inputs, so tool use is safe."** Validation checks the shape of the input, not its consequence. A destructive command that matches the schema still needs a gate and a blast-radius boundary.
- **"Errors are handled — we log them."** Logs go to operators; the model reads only its context. An error that never becomes a `tool_result` is a silent success (Exercise 3).
- **"Timeouts are transient; retry them."** A timeout means that the state is unknown. A retry of a tool that is not idempotent duplicates the side effect (Exercise 2).
- **"Return everything; more context helps the model."** Unbounded results push out what mattered and can overflow the window. Cap, mark, and paginate (Exercise 1).
- **"MCP makes our tools good."** MCP standardizes the interface, not the quality. A vague description or an unbounded result is just as bad over any protocol.
- **"`is_error` and `isError` are the same field."** Same idea, different layers: `is_error` on provider `tool_result` blocks, `isError` on MCP results. A confusion between the layers hides where a failure was dropped.
