# Chapter 9 — Multi-Agent Orchestration

## Why this chapter

[Chapter 8](ch08.md) delegated one subtask to one subagent; this chapter runs many [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loops at once.
Nothing new happens inside any single loop.
The new part is the coordination layer: who decomposes the work, what crosses each boundary, and who merges the results.
The mental model: agents never share understanding, only artifacts — a brief in, a report or a file out.
Track what crosses each boundary and you can debug any topology; assume shared state and you ship silent conflicts.

## Concepts

### Orchestrator–worker

One agent — the orchestrator — owns the goal.
It decomposes the task into independent subtasks, writes a brief for each, and spawns N workers in parallel.
Each worker runs its own [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop in its own context window.
The orchestrator collects the reports, reconciles them, and synthesizes the answer.

[Trace 22](ch08.md#trace-22-what-happens-when-work-is-delegated-to-a-subagent) ([Chapter 8](ch08.md)) covered one delegation: brief out, report back, contexts isolated.
Orchestration repeats it N times and adds two jobs: decomposition before the fan-out, reconciliation after it.
Both run in the orchestrator's context window, which must hold the plan, N briefs, and N reports at once (Trace 24).

### Handoffs are not delegation

Engineers call two different primitives "multi-agent", and confusing them causes design errors.

Delegation keeps ownership.
The parent spawns a worker, waits for its report, and keeps talking to the user.
The worker never meets the user.

A handoff transfers ownership of the conversation.
The harness makes the target agent the active one:
its instructions, tools, and permissions now face the user.
The first agent stops, and no report flows back.

The engineering question in a handoff is what moves:
the full conversation, a filtered view, or a summary.
The receiving agent never gets what the harness drops.
The user sees the gap as repeated questions (Trace 25).

### Topologies: star, pipeline, peer

A topology is the shape of who talks to whom; three shapes are common.

- **Star:** an orchestrator in the center; workers talk only to it.
- **Pipeline:** each agent's output artifact is the next agent's input.
- **Peer:** any agent messages any other.

Most systems use the star, for mechanical reasons.
One context holds the whole plan, so one agent can find gaps and contradictions.
Every message has one reader, so the cost grows linearly with N, and debugging means one orchestrator transcript plus N worker ones.

Use a pipeline when the task has real stages: research, then draft, then edit.
A pipeline also compounds errors: each stage treats the artifact before it as truth, so an error in stage one arrives at the end larger and more confident.
A peer topology is rarely worth its cost: the message count grows toward N², and no context holds the goal state.

Topology is one axis, and node lifetime is another.

- An *ephemeral* node exists for one step: it starts from a brief, returns a report, and keeps nothing.
  Every worker in Trace 24 is ephemeral.
- A *resident* node owns a domain across many runs — the agent for migrations, or the agent for security review.
  It keeps that domain's context, so it does not learn the domain again for each task.
  Resident nodes pay for that saving with a memory cost: stored domain knowledge goes stale, and stale facts read as current ([Chapter 5](ch05.md)).

### Two structures: roles and work

A multi-agent system carries two structures, and they change at different rates.
Keep them apart, because only one of them is safe to change during a run.

The **role structure** names the long-lived parts: which agent owns which domain, which tools it holds, and which permissions it carries.
It answers who.
You change it by deploy, with review.

The **work structure** is the task shape for one run: which subtask exists now, which one waits, and which ones have merged.
It answers what, right now.
The orchestrator reshapes it as evidence arrives: it splits a subtask that grew, drops one the results made unnecessary, or adds one for a gap.

Let the model reshape the work structure freely, because every shape it can reach stays inside the permissions that the role structure already granted.
Never let the model change the role structure.
An agent that grants itself a tool has removed the boundary that the design depended on.
The governance rules for that boundary come later in this book.

### The verifier is a separate node

One agent produces the result, and a second agent tries to break it.
The author cannot judge its own work: the context that produced the result also holds every reason to accept it.
So the verifier gets a fresh context, the artifact, and the acceptance criteria — never the author's reasoning.

Three shapes are common.

- **Adversarial:** N verifiers each try to refute the same claim, and the claim survives only if most of them fail.
- **Multi-perspective:** each verifier checks one property, such as correctness, safety, or whether the result reproduces.
- **Judge panel:** verifiers score parallel candidates, and the best one wins.

A verifier without written acceptance criteria approves everything, so it costs tokens and adds no safety.
Write the criteria before you add the node; the method for calibrating them comes later in this book.

Give the author-verifier loop a numeric cap, and define what happens at the cap:
escalate to a human, or return the best candidate with a warning attached.
A loop that ends silently at the cap hides its failure.
For a high-stakes check, use a verifier from a different model family:
two models that share training data can share a blind spot, and a fresh context does not remove it.

### Shared artifacts and conflict

Agents coordinate through artifacts, and the filesystem is the usual medium.
It is durable, you can inspect it, git versions it, and every agent has tools for it.
An artifact also outlives any context window.

The filesystem has no locks that the agents respect.
A reads, B reads, A writes, then B writes: B's write erases A's edit, and no error appears.
Both transcripts show success, and this is the lost update — the defining failure of shared artifacts (Trace 26).

Three defenses answer it, strongest first.

1. Give each agent a disjoint set of files, decided at planning time.
2. Give each agent its own worktree, with an explicit merge step ([Chapter 8](ch08.md)).
3. Add a staleness check: the harness rejects a write if the file changed after that agent's read.

### Context isolation between agents

Every worker starts with a fresh context window: its brief and its own instructions, nothing else.
[Chapter 3](ch03.md) carries the full argument; here it scales to N workers.
A constraint that decomposition leaves out is missing from every worker's brief, so it is not one bug but N.

The isolation also cuts the audit trail: the orchestrator cannot inspect reasoning that it never saw, so it can only judge the reports.
So each brief must fix the report shape, and each report must carry evidence: file paths, test output, and line numbers.

### Agent-to-agent protocols

When agents belong to different teams or vendors, the brief-and-report boundary needs a wire format, and the standards for it are still new.
The common pattern has three parts:

1. A discovery document that states what the remote agent can do.
2. A task lifecycle: submitted, working, done, failed.
3. A message envelope that carries identity and task references.

Treat these as patterns: the names and the specifications still change.

Two things do not change.

- A remote agent is an external service, so it needs timeouts, retries, and idempotent calls.
- Its messages are untrusted input, and the defenses against injected instructions come later in this book.

### When one agent beats N (L3)

The default answer to "how many agents?" is one, because the costs of many agents are structural.

- Every worker pays again for the system prompt and the tool definitions.
- Every coordination turn — decompose, brief, collect, reconcile — is pure overhead.
- Every boundary loses information, because a brief is smaller than the context that wrote it.

Fan out only when one of three conditions is true.

1. The subtasks are independent and context-heavy, so isolation gives N clean windows.
2. Wall-clock time matters, and the subtasks can truly run in parallel.
3. The workers need different privileges, tools, or models — a cheap searcher beside a sandboxed executor.

If no condition is true, one agent with good tools is better: one context that you can audit, and no coordination cost.
[Chapter 1](ch01.md) flagged "we need multi-agent for this"; it usually means a missing tool, not a missing agent.

### In other stacks

- **OpenAI Agents SDK:** a handoff is a first-class primitive: an agent declares its targets, and the transfer happens inside the loop.
- **LangGraph:** a multi-agent system is one graph: each agent is a node or a subgraph, and the topology is the edges you wired.
- **Claude Code:** subagents ([Chapter 8](ch08.md)) give you star delegation; there is no handoff to the user, because the parent answers.

## Traces

### Trace 24: What happens when an orchestrator fans work out

You ask one agent to audit a large codebase for a deprecated API, and it fans the work out.
The Sub lane below stands for all N workers; each runs the same steps in a fresh context.

1. **User** sends the goal to the orchestrator.
2. **LLM** decomposes the codebase into disjoint areas, one subtask for each.
3. **LLM** writes one brief for each subtask: scope, constraints, and the exact report shape.
4. **Harness** spawns N workers in parallel, each with a fresh context that holds one brief.
5. **Sub** runs its own [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop against its slice of the environment.
6. **Sub** returns one final report. Its intermediate reads stay in its own window.
7. **Harness** appends each report to the orchestrator's context as a tool result.
8. **LLM** reconciles: coverage against the plan, reports against each other.
   - A contradiction triggers a re-brief, never an average.
9. **LLM** re-briefs a worker for any gap, then waits for the patch report.
10. **LLM** synthesizes the merged answer and returns it.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  participant Sub
  participant Env
  User->>Harness: goal
  Harness->>LLM: assembled context
  LLM-->>Harness: briefs for N subtasks
  Harness->>Sub: spawn with one brief
  Sub->>Env: work own slice
  Env-->>Sub: raw results
  Sub-->>Harness: one final report
  Harness->>LLM: all reports
  LLM-->>Harness: reconcile and synthesize
  Harness-->>User: merged answer
```

*Figure 9.1 — the orchestrator pays for decomposition and reconciliation; the workers' raw work never enters its window.*

**Where this can fail**

- **Symptom:** two workers audited the same files, and a third area got none.
    - **Cause:** the decomposition was not disjoint and left a gap.
    - **Where to look:** the briefs' scope lines against the plan.
- **Symptom:** the reports arrive in formats that do not match, so the merge needs manual work.
    - **Cause:** no brief fixed a report shape.
    - **Where to look:** the brief text.
- **Symptom:** the final answer contradicts one worker's correct report.
    - **Cause:** reconciliation dropped a minority finding.
    - **Where to look:** the merge turn, against each worker report.

### Trace 25: What happens when one agent hands off to another

A support agent triages a billing question and hands the conversation to a billing specialist.
The Sub lane here is the specialist: a peer that takes over, not a worker that reports back.

1. **User** describes the problem to the triage agent.
2. **LLM** (triage) asks questions and gathers facts: account, symptom, urgency.
3. **LLM** decides that the case needs the specialist, and emits a handoff call.
4. **Harness** validates the target against the list of allowed handoffs.
5. **Harness** swaps the active agent: the specialist's instructions, tools, and permissions replace triage's.
6. **Harness** builds the specialist's context from the handoff payload: the full conversation, a filtered view, or a summary.
   - Anything the payload drops, such as triage's tool results, is gone: no agent holds it.
7. **Sub** (specialist) reads the payload and continues the conversation with the user.
8. **User** now talks to the specialist; triage takes no more turns and owes no report.
9. **Sub** resolves the case, or hands off again; ownership moves the same way.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  participant Sub
  User->>Harness: billing question
  Harness->>LLM: triage context
  LLM-->>Harness: handoff call
  Harness->>Sub: payload plus new tools
  Sub-->>Harness: reply as new owner
  Harness-->>User: specialist answer
  User->>Harness: follow-up question
  Harness->>Sub: routed to specialist
```

*Figure 9.2 — after step 3 the LLM lane goes quiet: ownership moved, and nothing ever flows back to triage.*

**Where this can fail**

- **Symptom:** the specialist asks again for answers that the user already gave.
    - **Cause:** the payload was a summary that dropped them.
    - **Where to look:** the handoff payload against the triage transcript.
- **Symptom:** the specialist takes actions that triage was forbidden to take.
    - **Cause:** the swap gave more tools, with no gate.
    - **Where to look:** both agents' tool and permission settings.
- **Symptom:** two agents hand the conversation back and forth without end.
    - **Cause:** each agent's instructions match the other's cases, and no limit stops the handoffs.
    - **Where to look:** the transcript, for repeated transfer calls.
- **Symptom:** the answer carries triage's persona with the specialist's content.
    - **Cause:** the harness kept the old system prompt after the swap.
    - **Where to look:** the specialist's first turn.

### Trace 26: What happens when two agents write the same artifact

Two parallel agents each fix a different bug; both fixes touch the same config file.

1. **Sub** (agent A) reads the file and plans its edit.
2. **Sub** (agent B) reads the same file seconds later; both hold the same snapshot.
3. **Sub** (A) writes its edit, and the file on disk changes.
4. **Sub** (B) writes its edit, computed from the snapshot that is now stale.
5. **Env** stores B's version. A's edit is gone, and no step failed.
   - This is the lost update: both agents report success, and both transcripts look correct.
6. **Harness** with a staleness check instead rejects B's write, because the file changed after B's read.
7. **Sub** (B) re-reads the file, applies its edit again, and writes; both edits survive.
8. **Harness** with worktree isolation prevents the race: A and B write separate copies on their own branches.
9. **User** (or an integrator agent) merges the branches; the overlap appears as conflict text, not silent loss.

```mermaid
flowchart TD
  F[Two writers one file] --> Q{Shared working copy}
  Q -->|yes| I[Interleaved reads and writes]
  I --> D{Staleness check}
  D -->|absent| L[Silent lost update]
  D -->|present| R[Write rejected]
  R --> RR[Re-read and re-apply]
  Q -->|no worktrees| W[Each edits own copy]
  W --> G[Merge gate]
  G --> C[Conflict visible as text]
  classDef process fill:#0369A1,stroke:#075985,color:#fff
  classDef lease fill:#D97706,stroke:#B45309,color:#fff
  classDef resource fill:#BE123C,stroke:#9F1239,color:#fff
  class Q,I,R,RR,W,C process
  class D,G lease
  class F,L resource
```

*Figure 9.3 — the lost update is the dangerous branch: every step succeeds and the artifact is still wrong.*

**Where this can fail**

- **Symptom:** the file matches only one agent's report.
    - **Cause:** a lost update in a shared working copy.
    - **Where to look:** the write timestamps in both agents' tool logs.
- **Symptom:** one agent writes the same file again and again.
    - **Cause:** another agent writes continuously, so the staleness check rejects every attempt.
    - **Where to look:** the rejection count and the other agent's write rate.
- **Symptom:** the agents used worktrees, but the merge is too large to review.
    - **Cause:** the decomposition gave both agents the same file area, so a planning error surfaces late.
    - **Where to look:** the plan's ownership map against the diff overlap.

## Questions

### Tier 1 — Explain

**Q 9.1 — What is the difference between delegating to a subagent and handing off to another agent?**

**Answer.** Delegation keeps ownership: the parent spawns a worker, waits, and receives a report; the user never meets the worker.
A handoff transfers ownership: the target agent's instructions and tools become active, it answers the user directly, and nothing flows back.

*Strong answers also mention:* only a handoff raises the payload question of what moves and what is lost; delegation's interface is the brief-and-report pair ([Trace 22](ch08.md#trace-22-what-happens-when-work-is-delegated-to-a-subagent)).

**Q 9.2 — What two jobs does an orchestrator do that its workers never see?**

**Answer.** Decomposition comes before the fan-out: the orchestrator splits the goal into disjoint subtasks and writes a brief for each.
Reconciliation comes after: it checks coverage, resolves contradictions, and synthesizes the reports.
Both jobs run in the orchestrator's context window, which holds the plan, N briefs, and N reports; that window is the scarce resource.

*Strong answers also mention:* a brief that sets a size limit for its report keeps the merge step inside that window.

**Q 9.3 — In a handoff, what determines what the receiving agent knows?**

**Answer.** The payload that the harness passes at the swap: the full conversation, a filtered view, or a summary.
Anything the payload drops is gone, because the sender stops and no agent holds it.
The user sees a drop as a repeated question or a forgotten preference.

*Strong answers also mention:* facts that lived only in the sender's tool results never entered the conversation text, so even a full-history payload misses them.

### Tier 2 — Reason

**Q 9.4 — A fan-out to five workers cost six times a single run and finished no sooner. Was it a mistake?**

**Answer.** Not always: the cost multiple is structural, because each worker pays again for the system prompt and the tool definitions.
The fan-out was worth it if isolation carried the run: raw output that would have overflowed one window, or workers with different privileges.
The unchanged wall time is the signal to follow: check the spawn timestamps, because serial spawning loses the parallelism that you paid for.
If no condition held, one agent with good tools was the right design.

*Strong answers also mention:* run the task again with one agent — the fan-out must beat that baseline, not zero.

**Q 9.5 — Two workers return contradictory conclusions. What does the orchestrator do — and what must it not do?**

**Answer.** It must not average the two conclusions, and it must not pick the more confident tone, because confidence costs the model nothing.
It reconciles against evidence: the reports carry file paths and outputs, so it checks the claims, or re-briefs one worker to test the contradiction.
It also inspects the decomposition, because a contradiction often means that two scopes overlap or that one brief was ambiguous.

*Strong answers also mention:* this is why a brief fixes a report shape with evidence fields; you can only trust a conclusion-only report, never reconcile it.

**Q 9.6 — Why is the filesystem a good coordination medium between agents, and where does it stop being one?**

**Answer.** It is durable, you can inspect it, git versions it, and every agent has tools for it; artifacts outlive any context window.
It stops at concurrent writes: the agents respect no locks, so two writers on one file produce a silent lost update (Trace 26).
The discipline is disjoint ownership, worktrees with an explicit merge, and staleness checks at write time.

*Strong answers also mention:* the discipline covers scratch files and plans too: any shared artifact has the two-writer problem.

### Tier 3 — Design & Debug

**Q 9.7 — Design the orchestration that finds every use of a deprecated auth library in a two-million-line monorepo and plans the migration.**

**Answer.** Use a star topology with read-only workers.
Decompose by directory into disjoint slices, each sized to fit a worker's window, and verify that they cover the repository tree before you spawn.
Each brief fixes the scope paths, the call patterns to find, and a report schema: file, line, call form, migration difficulty.
The workers only read, so no write conflict is possible; the orchestrator alone writes the plan.
Reconcile mechanically: compare the reported files against the repository listing, re-brief for any gap, and cap each report so N reports fit the merge window.

*Strong answers also mention:* verify coverage by counting — a worker that read nothing and one that missed every use return the same empty report.

**Q 9.8 — A three-stage pipeline — research, draft, edit — produces confident, wrong output. Walk your diagnosis.**

**Answer.** A pipeline compounds errors: each stage treats the artifact before it as truth, so the last transcript tells you the least.
Read the artifacts between the stages, not the final output, and find the first one that is wrong; that stage owns the bug.
Then ask why the wrong artifact left that stage; usually the next stage had no gate to reject it.
Fix it with a check at each boundary — a schema, an eval, or a grader — so a wrong artifact stops the pipeline.

*Strong answers also mention:* a stage boundary with no gate is the multi-agent form of a swallowed tool error ([Trace 10](ch04.md#trace-10-what-happens-when-a-tool-call-fails)).

## Common mistakes & red flags

- **"We need multi-agent for this."** [Chapter 1](ch01.md) flagged it; this chapter gave the full argument. N agents multiply the cost, add coordination turns, and lose information at every boundary. If none of the three conditions holds, the team is missing a tool, not an agent.
- **"The agents talk to each other."** They exchange text, not understanding. Every message is paid for twice: one context writes it, another reads it. Each hop loses detail.
- **"More workers means faster."** The merge runs serially, and the reconciliation work grows with N. The limit is the orchestrator's window, not the spawn count.
- **"Both agents edit the file; git will sort it out."** Inside one checkout there is no git boundary, so the second write silently erases the first (Trace 26). Worktrees make a conflict visible; a shared copy hides it.
- **"Add a manager agent above the managers."** Each level writes new briefs and new summaries, so every hop loses detail. Keep the topology flat until one orchestrator's window cannot hold the plan.
