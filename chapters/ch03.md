# Chapter 3 — Context Engineering

## Why this chapter

The context window holds everything the model can read for one turn.
The harness decides what goes into it.
This chapter zooms into steps 2 and 6 of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task): the harness assembles the context, and the tool results come back into it.
The mental model: context is a budget, not a bag.
Every token that you place competes with every token that you may need later.
If you count the tokens in each segment, you can explain most bugs in cost, in latency, and in agent memory before you start a debugger.

## Concepts

**Context engineering.** Context engineering is the practice of deciding what enters the context window each turn.
It replaces "prompt engineering" as the general term for this work.
The prompt is one segment of the window; context engineering covers all of the segments.
The unit of work is the turn, because the harness builds the window again every turn (Trace 7).

**Anatomy of the window.** An agent turn carries six segments, in this order:

- **System prompt** — the identity of the agent and the standing rules.
- **Tool definitions** — every tool schema and every tool description.
- **Memory and instructions** — project files and stored facts.
- **History** — every prior message and every tool result.
- **Injected content** — retrieved documents, hook output, and reminders.
- **Current turn** — the newest user message or tool result.

The six segments exist only in the harness.
The model receives one flat sequence of tokens.
Nothing in that sequence marks where the instructions end and the data starts.
This flat structure is why prompt injection works: text that the agent read as data can act as an instruction.
It is also why the order of the segments matters.

**Per-turn assembly.** The provider API keeps no state between calls.
The harness builds the full request again, with all six segments, and sends all of it every turn.
A session of 40 turns sends 40 requests, and each request is larger than the one before it.
Input tokens therefore make most of the cost of an agent, and prompt caching exists to reduce that cost.

**Budgets and token math.** Treat the window as a budget, and count the tokens in each segment.
Tool results and tool definitions use most of that budget.
Tool results collect in the history.
Fifty tool calls that each return 2,000 tokens add 100,000 tokens to every later request.
Tool definitions have a constant size, but that size is large: thirty detailed schemas cost thousands of tokens before the agent does any work.

Count the harness overhead as its own line.
The harness injects its system prompt, its tool schemas, and its skill descriptions on every turn, whether the turn uses them or not.
In a loaded session the words that the user typed are a small fraction of the payload; the rest is overhead that you chose.
Measure that overhead once per configuration, rank the schemas by size, and remove the tools that the task does not need — a removed tool costs nothing on any turn.

The system prompt and the user messages are usually the smallest segments.
Measure each segment with the token-counting endpoint of the provider.
Each model counts tokens differently.
A segment that you cannot measure is a segment that you cannot control.

**Stability ordering.** Prompt caching matches a prefix of the request.
One changed byte makes the cache invalid from that byte to the end of the request ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).
So put the stable content first and the volatile content last.
Providers place the tool definitions first, then the system prompt, then the messages.
The large front part of the request therefore repeats at a low price on every turn, until something changes it.

A timestamp in the system prompt changes it.
A new order for the tool list changes it too, and the harness reports no error.
Check the cache fields in the usage data of each response.
Zero cache reads across repeated turns means that something in the prefix changes every turn.

**Compaction and summarization.** Compaction keeps a long session inside the window limit.
When the history comes close to that limit, the harness replaces the old turns with a summary and keeps the recent turns word for word (Trace 8).
Some providers run compaction on the server as a beta feature.
Most harnesses write their own.
Treat compaction as a harness pattern, not as a product feature.

The question to ask is not whether the harness compacts.
The question is what survives the compaction.
The task, the decisions, and the current state must survive.
The harness can drop everything else, and it reports no error when it does.

**Context rot and poisoning.** Context only accumulates, and nothing in the window expires.
A fact that was true at turn 3, such as the contents of a file, stays in the window after turn 30 changed that fact.
The model gives the old fact the same weight as the new one.
Context rot is the name for this problem: old facts stay in the window and steer later decisions.

Context poisoning is the attack form of the same problem.
Text inside a web page or a tool result reads as an instruction, because the token sequence is flat.
Detection and gating come later in this book.
This chapter shows that the exposure exists.

**Just-in-time loading.** Three strategies manage content loading:

- **Pre-loading** puts every possibly useful item in the window at the start.
- **Just-in-time loading** gives the model a pointer and a tool that fetches the content when the model needs it.
- **Progressive disclosure** is the compromise that scales: the window always carries the one-line description, and the harness loads the body on use.

A skill, which is a folder of instructions that the agent loads on demand, works exactly this way.
Use just-in-time loading when the content is large, rare, or volatile.
Pre-load only the content that every turn needs.

### Sub-context isolation across subagents (L3)

A subagent is a second agent that the parent agent starts for one task, and it runs in a fresh context window.
Only the text that the parent writes into the task prompt goes into that window.
Only the final report of the subagent comes back.
Everything between those two points is lost to both sides: the files that the subagent read, the failed attempts, and the intermediate reasoning.

That loss is the benefit.
A search that reads forty files costs the parent one paragraph of context.
The loss also has a cost.
A parent that writes an incomplete task prompt gets a confident answer to the wrong question, and it cannot audit reasoning that it never saw.
Design the boundary as you design an API: the task prompt is the request schema, and the report is the response schema.

### In other stacks

- **LangGraph:** context is an explicit state object. Nodes read and write typed channels, so the code that you wrote decides what the model sees, not the defaults of a harness.
- **LangGraph:** checkpointers store that state between runs. A thread that resumes brings its old context back, and you must still trim it.
- **OpenAI Agents SDK:** sessions store the history and apply strategies that trim or summarize it. This is the compaction pattern with another name.
- **Everywhere:** every framework has the same budget problem. A new name for the window does not make the window larger.

## Traces

### Trace 7: What happens when the context for a turn is assembled

You send a follow-up message deep in a long session.

1. **User** sends the message.
2. **Harness** starts a fresh request, because the provider kept nothing from the last call.
3. **Harness** places the stable prefix: the tool definitions first, then the system prompt.
4. **Mem** returns the instruction files and the stored facts, which the harness places after the system prompt.
5. **Harness** appends the full history, oldest first: every message, tool call, and tool result.
6. **Harness** injects the content for this turn: hook output, retrieved documents, and reminders.
7. **Harness** appends the new user message last, at the volatile end of the request.
8. **Harness** trims every segment whose token count is over the budget for that segment.
   - One common rule caps each tool result and marks the cut with a truncation notice.
9. **Harness** posts the request, which the LLM reads as one flat token sequence.
10. **LLM** returns the output; the harness discards this assembly and builds a new one next turn.

```mermaid
  autonumber
  participant User
  participant Harness
  participant Mem
  participant LLM
  User->>Harness: new message
  Harness->>Harness: place stable prefix
  Harness->>Mem: load instructions
  Mem-->>Harness: files and facts
  Harness->>Harness: append history and injections
  Harness->>Harness: budget check per segment
  Harness->>LLM: one flat token sequence
  LLM-->>Harness: output
  Harness-->>User: reply
```

*Figure 3.1 — assembly is total: everything the model sees this turn was rebuilt from scratch this turn.*

**Where this can fail**

- **Symptom:** cost grows every turn even when the messages are short.
    - **Cause:** the harness resends the full history every turn, so the input tokens add up.
    - **Where to look:** the input token count for each turn.
- **Symptom:** cache reads are zero on every turn.
    - **Cause:** one volatile byte sits in the stable prefix, such as a timestamp or a new order for the tool list.
    - **Where to look:** the cache fields in the usage data, and a diff of two requests that follow each other.
- **Symptom:** the model ignores a rule that the system prompt states.
    - **Cause:** the rule sits behind 100,000 tokens of tool results, so the attention of the model spreads across all of them.
    - **Where to look:** the place where the rule sits in the assembled request.
- **Symptom:** the model follows instructions that nobody wrote.
    - **Cause:** injected content, such as a fetched page or a tool result, reads as an instruction in the flat sequence.
    - **Where to look:** the injected content in the transcript.
- **Symptom:** the model missed detail that a tool did return.
    - **Cause:** the cap on that segment truncated the tool result.
    - **Where to look:** the truncation markers in the transcript.

### Trace 8: What happens when the context window fills

A long refactoring session approaches the model's window limit mid-task.

1. **Harness** compares the total token count after each turn to a threshold below the hard limit.
2. **Harness** passes the threshold and schedules compaction before the next model call.
3. **Harness** selects the survivors: the task statement, the decisions, the current state, and the open questions.
4. **LLM** writes a summary of the old turns from a separate summarization prompt.
   - Some providers run this step on the server as a beta feature. The pattern is the same.
5. **Harness** replaces the old turns with the summary and keeps the most recent turns word for word.
6. **Harness** accepts one side effect: the cached prefix changed, so the next call writes the cache again.
7. **LLM** continues the task from the summary and the recent turns.
8. **LLM** needs a fact that did not survive, such as a file path, and cannot read it anywhere.
9. **LLM** re-derives that fact: it reads the files again and runs the commands again.
   - In the worst case the model does not re-derive the fact. It guesses, and it states the guess with confidence.

```mermaid
flowchart TD
  A[Turn ends] --> B{Over threshold}
  B -->|no| C[Resend history verbatim]
  B -->|yes| D[Select survivors]
  D --> E[Summarize old turns]
  E --> F[Swap summary into history]
  F --> G[Cache prefix invalidated]
  F --> H[Unselected facts drop silently]
  H --> I[Model re-derives or guesses]
```

*Figure 3.2 — compaction trades tokens for facts: everything not selected drops with no error raised.*

**Where this can fail**

- **Symptom:** the agent repeats work that it already finished.
    - **Cause:** compaction dropped the evidence that the step already ran.
    - **Where to look:** the transcript around the compaction point, and the summary next to the original turns.
- **Symptom:** the agent states something false about earlier work.
    - **Cause:** the model guessed a dropped fact instead of reading it again.
    - **Where to look:** the summary text next to the original turns.
- **Symptom:** cost rises sharply just after compaction.
    - **Cause:** the prefix changed, so cache reads dropped to zero for one rewrite.
    - **Where to look:** the cache read count and the cache write count around the compaction turn.
- **Symptom:** the session still stops with a context-exceeded error.
    - **Cause:** there is no threshold, or one tool result is larger than the remaining headroom.
    - **Where to look:** the stop reason and the size of the last tool result.
- **Symptom:** compaction repeats, because the window fills again at once.
    - **Cause:** the survivors hold bulky raw content instead of references to that content.
    - **Where to look:** the token count of the summary itself.

## Questions

### Tier 1 — Explain

**Q 3.1 — Name the six segments of an agent's context window.**

**Answer.** System prompt, tool definitions, memory and instructions, history, injected content, and the current turn.
The boundaries between them exist only in the harness.
The model receives one flat token sequence, and it cannot separate instructions from data by position alone.

*Strong answers also mention:* providers place tool definitions first, then the system prompt, then the messages — that fixed order defines the cacheable prefix.

**Q 3.2 — Why does the harness resend the entire context every turn?**

**Answer.** The provider API keeps no state between calls, so nothing stays on the server between requests.
The model can use only the tokens that the current request carries.
So the harness builds all six segments again and sends them again, and the request grows every turn.
Prompt caching makes the repeated prefix cheap, but it does not make the prefix free or optional.

*Strong answers also mention:* input tokens therefore make most of the cost of an agent, so per-turn token counts are the first telemetry to read.

**Q 3.3 — Which segments dominate token spend in an agent session, and why?**

**Answer.** Token spend is ranked by segment:

1. **Tool results** collect in the history and go out again every turn: fifty results of 2,000 tokens each is 100,000 tokens for each request.
2. **Tool definitions** have a constant size, but that size is large, because every schema and every description goes in every call.
3. **System prompt and user messages** are usually small parts of the total.

*Strong answers also mention:* truncate each tool result in the executor, before the result enters the history at all.

**Q 3.4 — What is the difference between pre-loading and just-in-time loading?**

**Answer.** Three strategies exist:

- **Pre-loading** places content in the context at the start, before the model asks for it.
- **Just-in-time loading** gives the model a pointer and a tool, and the model fetches the content when it needs the content.
- **Progressive disclosure** combines the two: the window always carries a one-line description, and the harness loads the body on use.

Skills use exactly this pattern.

*Strong answers also mention:* the trade — pre-loading spends tokens on content that the model may never use; just-in-time loading spends a turn and a tool call.

### Tier 2 — Reason

**Q 3.5 — Cache reads dropped to zero after a "harmless" deploy. What do you look for?**

**Answer.** Take a byte-level diff of two requests that follow each other, from front to back.
Caching matches a prefix, and the first changed byte makes everything after it invalid.
Common causes: a timestamp or a dynamic value in the system prompt, a new order or new wording for the tool list, or a changed model.
Confirm the cause with the usage fields: cache reads return once you fix the byte that changes.

*Strong answers also mention:* stability ordering as the design fix — volatile content belongs at the back of the request ([Trace 6](ch02.md#trace-6-what-happens-when-a-prompt-cache-hits--and-misses)).

**Q 3.6 — Why can an agent confidently act on a stale fact from thirty turns ago?**

**Answer.** Context does not expire; every turn stays in the window until compaction removes it.
The model gives a file listing from turn 3 the same weight as one from turn 30, because recency is weak evidence, not a rule.
Nothing marks the old fact as replaced unless the harness or a later tool result says so.
The fix is hygiene: read the state again before you act on it, or inject an explicit marker that says the state changed.

*Strong answers also mention:* context rot grows with session length, so long sessions need a habit of re-verification or a restart policy.

**Q 3.7 — Your harness compacts at a threshold. What must the summary preserve, and what may drop?**

**Answer.** Must survive:

- the task statement
- the constraints
- the decisions and the reasons for them
- the current state
- the open questions

May drop:

- raw tool results
- exploration that led nowhere
- file contents that the agent can read again

The test is one question: can the model continue the task from the summary and the recent turns without a guess?
Preserve the references — file paths and command names — so the agent can recover dropped content cheaply.

*Strong answers also mention:* replay compacted sessions in an eval suite, to catch summaries that lose the task.

### Tier 3 — Design & Debug

**Q 3.8 — An agent performs well for 20 turns, then quality degrades sharply. Walk your diagnosis.**

**Answer.** Get the transcript and the token counts for each turn first.
Look for a compaction event near the point where quality drops: degradation at compaction means that the summary dropped facts the task needs.
If there was no compaction, check the total size.
Degradation with a large intact window means that the attention of the model spreads across 100,000 tokens of results.
Then check for context rot: old facts that later turns contradicted, and that still steer the late decisions.
Fix the confirmed cause in this order: better selection of survivors, then tighter truncation of tool results, then prompts that force re-verification.

*Strong answers also mention:* reproduce the drop on a fixed task suite, so that the fix is measurable and not anecdotal.

**Q 3.9 — Design the context budget for an agent with 30 tools and long tool results.**

**Answer.** Set a cap for each segment and measure against those caps every turn.
Cut the tool definitions first: pre-load the few tools that every turn needs, and expose the rest through just-in-time discovery.
Cap each tool result in the executor; store the full result outside the context and return a path plus an excerpt.
Set the compaction threshold with headroom for the largest single tool result that you allow.
Raise an alert when a segment hits its cap, and when cache reads fall to zero, because both faults report no error.

*Strong answers also mention:* the token-counting endpoint gives model-specific measurement, and tokenizers differ across model generations.

**Q 3.10 — When would you restart a session instead of compacting it?**

**Answer.** Restart when the state lives outside the conversation: the plan, the notes, and the code sit in files, not in the history.
A restart assembles the context again from durable artifacts and gives you a clean window with no context rot.
Compaction keeps the nuance of the conversation, but it carries context rot forward and it risks a summary that loses facts.
Prefer a restart at a natural boundary, such as a finished subtask or a written plan; prefer compaction in the middle of a task.

*Strong answers also mention:* a subagent applies the same idea in parallel, because it also starts from a fresh window.

## Common mistakes & red flags

- **"The prompt is fine, we tested it."** The prompt is one segment. The model reads it behind the tool definitions, the memory, and 100,000 tokens of history — so test the assembled context, not the prompt alone.
- **"We'll just use a bigger window."** A bigger window raises the ceiling, but it does not improve attention; cost and context rot grow with what you put in the window.
- **"Compaction is lossless — it's a summary."** The selection is the loss. Everything that the harness does not select drops with no error, and the model later guesses it or derives it again.
- **"Caching is automatic; it will save us."** Caching matches a byte-exact prefix. One volatile byte at the front sets it to zero, and nothing raises an error — so watch the usage fields.
- **"The model forgot."** A model never forgets what is in the window. The harness dropped it, truncated it, or compacted it — find which one, in the transcript.
- **"Add it to the system prompt."** This default answer to every gap in behavior makes the stable prefix larger; most content belongs in a just-in-time load or in memory.
