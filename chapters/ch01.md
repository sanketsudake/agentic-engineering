# Chapter 1 — The Agent Loop: Big Picture

## Why this chapter

After this chapter you can describe an agent run from the first request to the final answer.
Every agentic system is one loop with four parts: a model, a harness, tools, and a context window.
An engineer who can describe that loop can predict where an agent fails.
This chapter builds the master trace, Trace 2, that every later chapter examines in more detail.
The mental model is this: the model proposes an action, and the harness decides what happens next.
The harness owns everything that the model cannot do.
Level emphasis: [L1]–[L2]; no (L3) sections in this chapter.

## Concepts

**Agent.** An agent is a model that calls tools in a loop to reach a goal.
This book uses that definition everywhere.
A workflow is a fixed pipeline that may call models; the model does not choose the next step.
This difference decides most architecture questions later in this book.

**Harness.** The harness (the runtime that owns the loop, context assembly, and gating) is not the model.
It builds the prompt, validates tool calls, executes them, and decides when to stop.
Claude Code, an SDK executor, and a server-side runner are all harnesses.

**Context.** The context window is the model's only working memory for a turn.
The harness places every fact that the model uses in this turn into that window.
The model reads nothing else.

**Tools.** A tool is a schema plus an executor.
The model emits a tool call, and the harness runs it.
The harness then appends the tool result to the context.

### In other stacks

- **OpenAI Agents SDK:** the harness role is the `Runner`; tools are decorated functions; the loop is `Runner.run()`.
- **OpenAI Agents SDK:** handoffs make the transfer between agents a built-in primitive.
- **LangGraph:** the loop is an explicit state graph; you wire nodes and edges yourself.
- **LangGraph:** state persists through checkpointers, so a "turn" is a graph step, not a chat turn.

## Traces

### Trace 1: What happens when you send one message to a model

You send "What is 2+2?" to a model API with no tools.

1. **User** sends a request with a system prompt and one message.
2. **Harness** serializes the request and posts it to the provider API.
3. **LLM** tokenizes the full context into input tokens.
4. **LLM** samples output tokens one at a time, and each token depends on all the earlier tokens.
5. **LLM** stops at an end token, a stop sequence, or the output limit.
6. **Harness** receives the response with a stop reason and token counts.
7. **User** sees the text.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  User->>Harness: send message
  Harness->>LLM: POST full context
  LLM->>LLM: tokenize and sample
  LLM-->>Harness: text plus stop reason
  Harness-->>User: final text
```

*Figure 1.1 — the synchronous core: one request, one sampled response, no state on the provider side.*

**Where this can fail**

- **Symptom:** the response stops in the middle of a sentence. **Cause:** the response reached the output token limit. **Where to look:** the stop reason and the output token count.
- **Symptom:** the same prompt gives different answers. **Cause:** the sampling temperature is above zero. **Where to look:** the request parameters.
- **Symptom:** the first word is slow, the rest is fast. **Cause:** a long input; the time to the first token grows with the input size. **Where to look:** the input token count.

### Trace 2: What happens when a user request becomes a finished task

You ask the agent to fix a failing test.
This is the master trace; later chapters each examine one segment of it.

1. **User** sends the request.
2. **Harness** assembles the context: the system prompt, memory, history, and tool definitions.
3. **LLM** generates a response that is a tool call, not an answer.
4. **Harness** validates the call and checks it against permission rules.
5. **Tools** execute the call in the environment.
6. **Harness** appends the tool result to the context.
7. **LLM** repeats steps 3–6 until it has the information that it needs.
8. **LLM** emits final text.
9. **Harness** finishes the turn: it writes memory, runs hooks, and records telemetry.
10. **User** sees the answer.

```mermaid
sequenceDiagram
  autonumber
  participant User
  participant Harness
  participant LLM
  participant Tools
  participant Env
  User->>Harness: request
  Harness->>LLM: assembled context
  LLM-->>Harness: tool call
  Harness->>Tools: validated call
  Tools->>Env: act
  Env-->>Tools: result
  Tools-->>Harness: tool result
  Harness->>LLM: context plus result
  LLM-->>Harness: final text
  Harness-->>User: answer
```

*Figure 1.2 — the anchor diagram: every arrow into the LLM is context the harness chose to send.*

**Where this can fail**

- **Symptom:** the loop never ends. **Cause:** the harness has no turn limit, and the model continues to call tools. **Where to look:** the turn count in the transcript.
- **Symptom:** the agent does not use a fact from an earlier turn. **Cause:** the context overflowed, and the harness dropped the early turns. **Where to look:** the token counts for each turn.
- **Symptom:** the model reports that a tool succeeded, but nothing changed. **Cause:** the harness dropped the tool error before it reached the context. **Where to look:** the raw tool result in the transcript.
- **Symptom:** the same action ran two times. **Cause:** the tool is not idempotent (a repeated call repeats the effect), and the harness retried it after a timeout. **Where to look:** the logs of the tool executor.

## Questions

### Tier 1 — Explain

**Q 1.1 — What is the difference between an agent and a workflow?**

**Answer.** An agent is a model that calls tools in a loop and chooses its own next step.
A workflow is a fixed pipeline where the code chooses the steps, and the code may call models inside them.
The test is one question: who decides what happens next, the model or your code?

*Strong answers also mention:* most production systems use both, and you make the choice for each decision, not for the whole system.

**Q 1.2 — Name the responsibilities the harness owns that the model cannot.**

**Answer.** The harness owns context assembly, tool execution, permission gating, stop conditions, memory, and telemetry.
The model only maps the context to output tokens.
Every action that keeps state or changes the world belongs to the harness.

*Strong answers also mention:* this is why "the agent did X" almost always means "the harness permitted X".

**Q 1.3 — Why does the model see a tool result as text in the next turn?**

**Answer.** The API keeps no state between calls.
The harness appends the tool result to the message list and sends the whole context again.
The model executes nothing; it reads what the harness placed in the context.

*Strong answers also mention:* this is why the harness must budget and truncate every tool result.

### Tier 2 — Reason

**Q 1.4 — A team says "the model keeps looping". What harness settings do you check first, and why?**

**Answer.** Check the maximum turn limit and the stop conditions first, because the loop belongs to the harness, not the model.
Check next how the harness reports tool errors: a model calls a tool again when it never sees the failure text.
Check the context last: compaction can remove the evidence that a step already ran.

*Strong answers also mention:* a turn limit only stops the damage; the real fix is usually in the tool results.

**Q 1.5 — Why does adding a tool change model behavior even when the tool is never called?**

**Answer.** Tool definitions live in the context window.
They use tokens, and they change which text the model attends to.
A large or unclear schema can also make the model emit the wrong call.

*Strong answers also mention:* a tool description is a prompt, and it needs the same review as a prompt.

**Q 1.6 — When does a workflow beat an agent?**

**Answer.** A workflow wins when you know the steps, when variance is expensive, and when no decision at run time needs the model.
A fixed pipeline costs less, runs faster, and is easy to test.
Use an agent only where the path depends on what the earlier steps find.

*Strong answers also mention:* start with a workflow, and make a step agentic only where the model must choose the next action.

### Tier 3 — Design & Debug

**Q 1.7 — An agent completes a task correctly but takes 40 loop turns. Walk your diagnosis.**

**Answer.** Read the transcript before you change any setting.
Count the wasted turns in three classes: the agent reads an unchanged file again, it retries a failing call, or it derives a known fact again.
A repeated read points at missing context or missing memory.
A retry points at a tool error that never reached the context.
A repeated derivation points at what compaction removed.
Fix the largest class first, then measure the turn count again on the same task.

*Strong answers also mention:* a task suite that records the turn count for each run, so you can prove that the fix works.

**Q 1.8 — Design the stop conditions for an unattended agent run.**

**Answer.** Use four limits together: a maximum turn count, a time budget, a token budget, and a detector for no progress.
Each limit guards a different failure: an endless loop, a hang, a cost overrun, and repeated work that makes no progress.
On every stop, write the transcript and return a state that the operator can resume.
Always report the reason for the stop.

*Strong answers also mention:* a stop condition only limits the damage; send an alert with the count of how often each one triggers.

## Common mistakes & red flags

- **"The model executed the command."** The harness executed it; the model emitted text. This difference decides where you put every control.
- **"We need multiple agents for this."** For most tasks, one agent with good tools is better than several agents that must coordinate.
- **"The agent has memory."** It has a context window that the harness fills. Memory that persists between runs is a harness feature.
- **"Tool errors are handled."** Ask where they are handled. If the model never sees the error text, it retries the call or reports a success that never happened.
- **"We set temperature to zero, so it is deterministic."** Providers do not promise identical output for identical input, and tool results still change between runs.
