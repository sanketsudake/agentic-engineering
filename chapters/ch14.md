# Chapter 14 — Lineage, Frontier & Capstones

## Why this chapter

An architect holds two timelines at once:
where agentic systems came from, and where the current bets point.
The mental model: the loop was always the destination,
and every lineage stage attacks the same bottleneck — what enters the context window, and who decides.
Read the past that way and the frontier is the next five attacks on the same constraint.
This chapter closes the book: the lineage, five judged bets, two capstones.
Level emphasis: [L3]; the whole chapter targets architect judgment.

## Concepts

### The lineage, briefly

Each stage shipped real products, then hit a constraint that forced the next stage.
The constraint is always context: one window is the model's working memory, and something must fill it well.

**Chatbots.** A model plus a replayed message history.
Added: conversational state — resend the transcript and the model appears to remember.
Constraint: the model knows only its training data;
users ask about their own documents, and pasting by hand does not scale.

**RAG apps.** A retrieval pipeline (Chapter 6) injects relevant chunks into the context at question time.
Added: fresh, private knowledge — the first automated answer to "what should be in the window".
Constraint: retrieval is one-shot and read-only;
it guesses relevance before the model speaks, cannot re-query a miss, and cannot act on what it finds.

**Tool use.** The model emits a structured call; the caller executes it and returns the result as context (Trace 9).
Added: the model chooses the next step — deciding moved from pipeline code into the model.
Constraint: one call per request is a workflow wearing a costume;
real tasks need the call–result cycle repeated.

**Agents.** The loop: model proposes, caller executes, result returns, repeat until done (Trace 2).
Added: multi-step autonomy — the model assembles much of its own context, one tool result at a time.
Constraint: a raw loop fails in production —
context overflows, errors get swallowed, dangerous calls go ungated, nothing persists, nothing says stop.

**Harnesses.** The runtime that owns the loop: context assembly, gating (Trace 18), memory, compaction, hooks, subagents.
Added: every failure the raw loop exposed became a harness feature.
This is where the field stands: the loop is settled; the harness is where systems differ.

The through-line: chatbots replayed context, RAG injected it, tool use let the model request it, agents let the model build it, harnesses made the building governable.
Each stage survives as a component of the next — RAG is now a tool the agent calls (Trace 16), not a rival architecture.

### The frontier, with judgment

Five bets, each stated the same way: the state of the pattern, the judgment this book commits to, and when it matters to you.
These are hedged positions, not predictions.

**1. Computer use — GUI agents.**
State: models drive a screen from screenshots and complete short, constrained flows; long flows stay brittle because per-action errors compound and every screenshot is expensive context.
Judgment: bet on GUI agents as the fallback interface, never the primary one.
An API beats pixels wherever one exists — structured results are verifiable, cheap, and gateable; the durable niche is software with no other interface.
It matters to you when a task's only interface is a screen: budget heavy verification and short leashes, and trust no accuracy claim until measured on your own flows.

**2. Long-horizon autonomy.**
State: agents complete hours-long tasks in supervised settings; reliability decays with horizon as errors compound and context degrades.
Judgment: the bottleneck is verification, not model capability.
Autonomy lengthens where checkable milestones exist — tests, CI, typed schemas — and stalls where "done" needs a human.
Bet on checkpointed autonomy: long runs decomposed into harness-verifiable segments (Chapter 10).
It matters to you when you design unattended runs: invest in milestones and layered stop conditions (Q 1.8), not a longer leash.

**3. Self-improving agents.**
State: agents can edit their own memory files, skills, and instructions; the mechanics are ordinary file writes.
Judgment: split the bet by review.
Unreviewed self-modification compounds errors and lets a prompt injection persist across sessions (Chapter 11).
Reviewed self-modification is automated harness maintenance, and likely wins: the agent proposes; an eval suite and a human gate it, like code.
It matters to you when maintaining many agent configurations costs more than reviewing agent-drafted upkeep.

**4. Agent-to-agent ecosystems.**
State: multi-agent works inside one trust boundary (Chapter 9); cross-organization protocols exist on paper, and adoption is thin — trust, billing, and liability stay unresolved.
Judgment: the hard part is the trust boundary, not the protocol.
Another organization's agent is an untrusted tool whose output lands in your context — an inbox for injections.
Bet on cross-org agent traffic growing along existing API-contract lines, with authentication and audit, before any open marketplace.
It matters to you when a partner offers an agent endpoint: gate it like an untrusted server, allowlist what it sees, and never let its output trigger ungated actions.

**5. Small local models in the loop.**
State: small models run on-device and handle classification, routing, and summarization; they stay weak at long-horizon tool use.
Judgment: the economics decide.
The cost equation — cost per task ≈ turns × average context tokens × token price (Chapter 12) — is linear in what reaches the priced model, so route cheap, latency-sensitive, or private steps locally and keep judgment steps frontier.
Bet on hybrid loops; be skeptical of local-only agents for open-ended work.
It matters to you when cost or privacy makes sending every token off-device untenable — the router then becomes a harness component you eval like any other.

## Capstones

Both capstones grade against the Appendix C Tier-4 row:
assumptions, kill-criteria, the strongest counter-position, then a decision someone owns.

### Capstone: The agent platform for a 200-engineer organization

**Prompt.** Design the agent platform for a 200-engineer product organization as a one-page plan:
harness choice, eval infrastructure, permission policy, rollout gates, team skilling.
Commit to positions; every bet carries a kill-criterion.

**Model artifact.**

> **Bets (3).**
> 1. One shared, managed harness — org settings, permission policy, memory conventions — not per-team stacks. Assumption: consistency compounds faster than per-team optimization.
> 2. Config ships like code: prompts, permission rules, and skills merge only through an eval suite of ~30 real tasks tracking success rate, turns, and cost per task.
> 3. Skilling by transcript review: one real transcript per team per week; engineers level up on diagnosis (Appendix C), not prompt folklore.
>
> **Kill-criteria.**
> 1. Over 30% of teams on unmanaged forks after two quarters — standardization failed; govern outcomes, not the stack.
> 2. Zero real regressions caught in a quarter while the suite costs more than one incident's cleanup — shrink to the ten highest-signal tasks.
> 3. Median turns and intervention rate flat after eight weeks of reviews — switch to paired debugging.
>
> **Non-goals.** No custom harness build; no cross-org agent endpoints this year; no fine-tuning (Appendix D).
>
> **Milestones (90 days).**
> Day 30: managed settings and permission policy live for two pilot teams; baseline eval suite green; cost and turn dashboards up.
> Day 60: rollout gate wired into CI; half of teams on; first config change shipped through the gate.
> Day 90: all teams on; per-team cost, turn, and intervention metrics reviewed monthly; first kill-criterion formally evaluated.
>
> **Risks.** Shadow usage (make the paved road faster, not mandatory); the eval suite ossifying (rotate tasks quarterly); a policy so tight teams route around it (measure ask-rate; loosen the noisiest rules).

**What reviewers look for.**
A decision on the harness question, not a survey.
The strongest counter-position — per-team autonomy moves faster — stated fairly, answered with the consistency assumption plus the kill-criterion that would concede it.
Quantified gates: tokens, turns, dollars, dates — not adjectives.
Rollout tied to the eval suite, so "safe to ship" is measured.
Non-goals present: a plan without refusals is a wish list.

### Capstone: Redesign the coding agent

**Prompt.** You may keep only five tools and add one new harness mechanism.
Design the coding agent that results; justify every keep and cut against the traces of this book.

**Model answer.**
Keep: `read_file`, `edit_file`, `run_shell`, `search` (filename and content unified), and `spawn_subagent`.
Trace 2 shows the loop is read–act–verify: `read_file` and `search` cover discovery, `edit_file` the act, and `run_shell` the verification — tests, builds, and diffs are all shell.
`spawn_subagent` is the context-cost release valve: exploration burns tokens in an isolated window and returns only conclusions.
Cut everything else for two mechanical reasons.
Every schema is context on every turn (Q 1.5), and the cost equation — cost per task ≈ turns × average context tokens × token price — taxes each unused tool on every step.
And each tool touching untrusted content (a browser, a web fetch) widens the injection surface (Chapter 11) for marginal coding value; when a task needs the web, mount a gated external server.
A dedicated `write_file` loses to `edit_file`: Trace 9 makes a tool a schema plus an executor, and one edit schema covers creation as a degenerate case.
The new mechanism: a claim ledger in the harness.
Every success claim in the final answer must map to a tool-observed check — a passing test, a clean diff — or completion blocks, the way a permission rule blocks a dangerous call in Trace 18.
Kill-criterion: fewer than one real false-success blocked per hundred runs, and the ledger comes out.

**What reviewers look for.**
Cuts justified by mechanism — context cost, injection surface, schema overlap — not taste.
Keeps mapped to trace steps, covering Trace 2 end to end.
The counter-position argued: more tools means more capability; the reply is that capability unused per-turn is pure cost.
The new mechanism placed in the harness, not the model — it must bind even when the model is wrong.
An exit condition on the mechanism itself: willingness to delete one's own invention is the Tier-4 signal.

## Questions

### Tier 2 — Reason

**Q 14.1 — Why did RAG apps precede tool-using agents, if the loop was always the destination?**

**Answer.** Each stage attacks the context bottleneck with the machinery reliable at the time.
RAG needs only read-only context assembly: no structured output, no action risk, no error recovery.
Tool use needs the model to emit valid calls and recover when results surprise it, and the loop compounds any per-step unreliability.
So the read-only attack shipped first; deciding moved into the model only when models could carry it.

*Strong answers also mention:* the order was set by risk — acting is gated harder than reading, in history as in permission policy.

**Q 14.2 — Every lineage stage attacks one bottleneck. Name it, and show how two different stages attack it.**

**Answer.** The context window: what enters it each turn, and who decides.
RAG attacks it with pipeline code — retrieval guesses relevance once, before the model speaks.
Agents attack it by handing the decision to the model — each tool call requests the model's own next context.
Harnesses referee the same bottleneck: compaction, memory, and subagent isolation are policies about what stays in the window.

*Strong answers also mention:* this is why context engineering supersedes prompt engineering as the umbrella term.

**Q 14.3 — Why does GUI-agent reliability decay faster with task length than API-agent reliability?**

**Answer.** Three compounding mechanisms.
Per-step accuracy is lower — state is inferred from pixels, not read from structured results — and errors multiply across steps, so a small accuracy gap becomes a large completion gap.
Screenshots are token-heavy, so context pressure arrives sooner, degrading exactly when the task needs history most.
And there is no schema to verify against: a wrong click often looks like success, so errors surface late.

*Strong answers also mention:* verification is the binding constraint — an API returns a checkable result, a screen returns a picture of one.

### Tier 3 — Design & Debug

**Q 14.4 — Your team supervises every agent session and wants hours-long unattended runs. Design the rollout.**

**Answer.** Do not lengthen the leash; add gates and extend between them.
Decompose target tasks into segments ending at harness-verifiable milestones — tests pass, build green, diff judged (Chapter 10).
Wrap each run in layered stop conditions (Q 1.8), each persisting a resumable state.
Roll out by horizon: unattended for one segment, then two, gating each extension on the measured intervention and false-success rates of the previous stage.
Instrument first: if you cannot measure how often a supervised session needed a human, you cannot argue the next extension is safe.

*Strong answers also mention:* tasks that resist decomposition stay supervised — task shape, not confidence, sets the autonomy budget.

**Q 14.5 — An agent fleet has self-maintained memory files for six months. Turn counts and costs have crept up. Diagnose and fix.**

**Answer.** Read transcripts and the memory files first; creep points at accumulation, not a model change.
Expect unreviewed self-written memory to have grown monotonically — agents append but never prune — so every session pays more context and attends to stale entries, adding turns.
Check for the worse failure: injected or wrong content that persisted into memory and now steers every session (Chapter 11).
Fix the class: gate memory writes like config — an eval suite tracking turns and success rate, plus a size budget with forced consolidation.
Verify by replaying the task suite against pruned memory and comparing turns and cost.

*Strong answers also mention:* a memory-size and repeated-read metric in the standing suite, so creep alarms next time.

### Tier 4 — Judge

**Q 14.6 — A director says: "We will adopt agents when they are done improving." Argue the strongest version, then commit.**

**Answer.** Strongest version: early adopters pay integration costs twice — today's patterns get rebuilt, and waiting a cycle buys a better baseline for free.
It fails on one observation: the compounding asset is not the model but the organization — eval suites, permission policies, transcript literacy — and every capability jump so far has raised that layer's value, because stronger models get trusted with more, which demands more gating and measurement.
"Done improving" also never arrives; it is deferral dressed as prudence.
Commit: adopt now on low-blast-radius workflows, spend on the harness and eval layer, re-scope each model generation.
Kill-criterion: two successive upgrades forcing a rewrite of the eval and permission layer itself would prove the transfer assumption wrong.

*Strong answers also mention:* Trace 2 has been stable across model generations — the loop is the durable interface to bet on.

**Q 14.7 — Your CFO proposes cutting model spend by moving the coding agents to small local models. Commit to a position.**

**Answer.** No to replacement; yes to routing.
Assumption: spend concentrates in high-turn frontier sessions, so the lever is the cost equation — cut what reaches the priced model, not the model itself.
Local models hold up on classification and summarization, and degrade on exactly the long-horizon tool use that coding agents are; a local-only fleet trades visible spend for invisible cost — failed tasks, cleanup, re-runs.
The honest counter: for narrow, repetitive, verifiable steps, local is genuinely free and private — so route those locally, keep judgment steps frontier.
Kill-criteria: hybrid routing must cut cost per completed task 30% in a quarter, and any routed step that drops completion below baseline routes back.
Report cost per completed task to the CFO, never cost per token.

*Strong answers also mention:* the router becomes a harness component with its own evals — a misrouting bug looks exactly like a model regression.

## Common mistakes & red flags

- **"The next model makes harness work obsolete."** Every capability jump so far increased harness value: stronger models get trusted with more, which demands more gating, evals, and context discipline.
- **"We will adopt agents when they are done improving."** They will not be "done" on any planning horizon, and the compounding asset — evals, permissions, transcript literacy — accrues to your organization, not the provider.
- **"GUI agents mean we never need APIs again."** Pixels are the most expensive, least verifiable interface. GUI agents are the fallback for software with no better surface, not a reason to stop building surfaces.
- **"Self-improving agents are either magic or forbidden."** Reviewed self-modification is ordinary automation: the agent drafts; an eval suite and a human gate. The line is review, not self-editing.
- **"Agent-to-agent is just an integration problem."** The protocol is the easy part. An external agent is an untrusted tool whose output lands in your context; without trust, billing, and audit answers, a demo is not an architecture.
- **"Local models will make agents free."** Local-only agents on open-ended work trade token spend for failure cost. Judge by cost per completed task; route hybrid.
- **"Agents replaced RAG and workflows."** Each stage survives as a component of the next: retrieval is a tool, workflows are scaffolding. Choose per decision, not per era (Q 1.6).
