# Chapter 14 — Lineage, Frontier & Capstones

## Why this chapter

An architect holds two things at once:
where agentic systems came from, and where the current bets point.
The mental model: every lineage stage works on the same limit — what enters the context window, and who decides.
The loop was always the end point, and the frontier is the next five answers to that limit.
This chapter closes the book: the lineage, five judged bets, two capstones.
Level emphasis: [L3]; the whole chapter targets architect judgment.

## Concepts

### The lineage, briefly

Each stage shipped real products, then met a limit that forced the next stage.
The limit is always the context window, the model's working memory.

**Chatbots.** A model plus a message history that the caller resends on each turn.
Added: conversational state, so the model appears to remember.
Limit: the model knows only its training data.
Users ask about their own documents, and manual pasting does not scale.

**RAG apps.** A retrieval pipeline ([Chapter 6](ch06.md)) puts relevant chunks into the context at question time.
Added: fresh, private knowledge — the first automatic answer to what belongs in the window.
Limit: retrieval runs once for each question and only reads.
It guesses relevance before the model speaks, cannot query again after a miss, and cannot act on what it finds.

**Tool use.** The model emits a structured call, and the caller executes it and returns the tool result as context ([Trace 9](ch04.md#trace-9-what-happens-when-a-tool-call-executes-end-to-end)).
Added: the model chooses the next step, so deciding moved from pipeline code into the model.
Limit: one call for each request is still a fixed workflow, and real tasks repeat the cycle many times.

**Agents.** The loop: the model proposes a call, the caller executes it, the result returns, and the cycle repeats ([Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task)).
Added: autonomy across many steps, because the model assembles much of its own context, one tool result at a time.
Limit: a raw loop fails in production.
The context overflows, errors stay hidden, no gate stops a dangerous call, no state persists, and no rule says stop.

**Harnesses.** The runtime that owns the loop: context assembly, gating ([Trace 18](ch07.md#trace-18-what-happens-when-the-harness-gates-a-dangerous-action)), memory, compaction, hooks, and subagents.
Added: each failure that the raw loop exposed became a harness feature.
The field stands here: the loop is settled, and the harness is where systems differ.

The through-line: chatbots replayed the context, RAG filled it, and tool use let the model request it.
Agents let the model build the context, and harnesses made that building governable.
Each stage survives inside the next one: retrieval is now a tool that the agent calls ([Trace 16](ch06.md#trace-16-what-happens-when-the-agent-searches-instead)), not a rival architecture.

### The frontier, with judgment

Five bets follow, each with the pattern today, this book's judgment, and when the bet matters to you.
These are hedged positions, not predictions.

**1. Computer use — GUI agents.**
State: models drive a screen from screenshots and complete short, fixed flows.
Long flows stay unreliable: errors compound across actions, and each screenshot costs many context tokens.
Judgment: use a GUI agent as the fallback interface, never the primary one.
Prefer an API wherever one exists: a structured result is cheap to check and easy to gate.
It matters to you when a task has only a screen: verify every step, keep runs short, and measure accuracy claims on your own flows.

**2. Long-horizon autonomy.**
State: with a human who supervises, agents complete tasks that run for hours.
Reliability drops as a run gets longer, because errors compound and the context degrades.
Judgment: the limit is verification, not model capability, so bet on checkpointed autonomy.
Autonomy extends where the harness can check a milestone: a test, a CI run, a typed schema.
It stalls where only a human can judge completion, so split a long run into segments that the harness verifies ([Chapter 10](ch10.md)).
It matters to you when you design unattended runs: spend on milestones and stop conditions (Q 1.8), not on longer stretches.

**3. Self-improving agents.**
State: agents edit their own memory files, skills, and instructions with an ordinary file write.
Judgment: the answer depends on review.
Self-modification without review compounds errors, and it lets a prompt injection persist across sessions ([Chapter 11](ch11.md)).
Self-modification with review is automated harness maintenance, and it probably wins.
The agent proposes a change, and an eval suite and a human gate it, as with code.
It matters to you when maintaining many agent configurations costs more than reviewing the agent's drafts.

**4. Agent-to-agent ecosystems.**
State: multi-agent systems work inside one trust boundary ([Chapter 9](ch09.md)).
Protocols between organizations exist, but adoption stays thin, because trust, billing, and liability stay unresolved.
Judgment: the hard part is the trust boundary, not the protocol.
An agent from another organization is an untrusted tool whose output enters your context, so it can carry an injection.
Bet on traffic between organizations along existing API contracts, with authentication and audit, before any open marketplace.
It matters to you when a partner offers an agent endpoint: allowlist what it sees, and never let its output start an ungated action.

**5. Small local models in the loop.**
State: small models run on the local device and handle classification, routing, and summarization, but stay weak at tool use over long runs.
Judgment: the cost decides, so bet on hybrid loops and stay skeptical of local-only agents for open-ended work.
The cost equation — cost per task ≈ turns × average context tokens × token price ([Chapter 12](ch12.md)) — grows with every token that reaches the paid model.
So route the cheap, fast, or private steps locally, and keep judgment steps on a frontier model.
It matters to you when cost or privacy blocks sending every token off the device.

## Capstones

The [Appendix C](appendices.md#appendix-c--answer-quality-rubric) Tier-4 row grades both capstones:
assumptions, kill-criteria, the strongest counter-position, and a decision that someone owns.

### Capstone: The agent platform for a 200-engineer organization

**Prompt.** Write a one-page plan for the agent platform of a 200-engineer product organization:
harness choice, eval infrastructure, permission policy, rollout gates, and team training.
Commit to positions, and give every bet a kill-criterion.

**Model artifact.**

> **Bets (3).**
> 1. One shared, managed harness — org settings, permission policy, memory conventions — not a stack for each team. Assumption: consistency returns more than per-team tuning.
> 2. Configuration ships like code: prompts, permission rules, and skills merge only through an eval suite of ~30 real tasks tracking success rate, turns, and cost per task.
> 3. Training by transcript review: one real transcript for each team each week. Engineers learn diagnosis ([Appendix C](appendices.md#appendix-c--answer-quality-rubric)), not prompt habits that nobody measured.
>
> **Kill-criteria.**
> 1. More than 30% of teams run unmanaged forks after two quarters. Standardization failed: govern outcomes, not the stack.
> 2. The suite catches no real regression in a quarter and costs more than one incident's cleanup. Shrink to the ten highest-signal tasks.
> 3. Median turns and the intervention rate do not move after eight weeks of reviews. Switch to paired debugging.
>
> **Non-goals.** No custom harness. No agent endpoints for other organizations this year. No fine-tuning ([Appendix D](appendices.md#appendix-d--the-architects-lens)).
>
> **Milestones (90 days).**
> Day 30: managed settings and permission policy live for two pilot teams; baseline eval suite green; cost and turn dashboards up.
> Day 60: rollout gate in CI; half the teams on; first config change shipped through the gate.
> Day 90: all teams on; cost, turn, and intervention metrics reviewed monthly; first kill-criterion reviewed.
>
> **Risks.** Use outside the platform: make the supported path faster, not mandatory. A stale eval suite: rotate tasks quarterly. A policy teams avoid: measure the ask rate, and loosen the noisiest rules.

**What reviewers look for.**
A decision on the harness question, not a survey.
The strongest counter-position — each team moves faster with its own stack — answered with the consistency assumption and the kill-criterion that concedes it.
Gates with numbers — tokens, turns, money, dates — not adjectives.
A rollout tied to the eval suite, so a measurement decides what is safe to ship.
Non-goals present: a plan that refuses nothing is not a plan.

### Capstone: Redesign the coding agent

**Prompt.** Keep only five tools, and add one new harness mechanism.
Design the coding agent that results, and justify every keep and cut against this book's traces.

**Model answer.**
Keep `read_file`, `edit_file`, `run_shell`, `search` (filenames and content in one tool), and `spawn_subagent`.
[Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) shows that the loop is read, act, verify.
`read_file` and `search` read, `edit_file` acts, and `run_shell` verifies, because tests, builds, and diffs all run in a shell.
`spawn_subagent` controls context cost: the subagent explores in a separate window and returns only its conclusions.

Cut every other tool, for two reasons.
Every tool schema occupies context on every turn (Q 1.5), and the cost equation — cost per task ≈ turns × average context tokens × token price — charges you for each unused one.
Each tool that reads untrusted content, such as a browser, widens the injection surface ([Chapter 11](ch11.md)) for little coding value; when a task needs the web, mount a gated external server.
A separate `write_file` loses to `edit_file`: [Trace 9](ch04.md#trace-9-what-happens-when-a-tool-call-executes-end-to-end) defines a tool as a schema plus an executor, and one edit schema also covers file creation.

The new mechanism is a claim ledger in the harness.
Every success claim in the final answer must map to a check that a tool observed — a passing test, a clean diff.
If a claim has no such check, the harness blocks completion, the way a permission rule blocks a dangerous call in [Trace 18](ch07.md#trace-18-what-happens-when-the-harness-gates-a-dangerous-action).
Kill-criterion: if the ledger blocks fewer than one real false success in a hundred runs, remove it.

**What reviewers look for.**
Cuts justified by mechanism — context cost, injection surface, schema overlap — not taste.
Every kept tool mapped to a step of [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task), which the five cover end to end.
The counter-position argued: more tools give more capability; a capability no turn uses is pure cost.
The new mechanism placed in the harness, not the model, so it holds even when the model is wrong.
An exit condition on the mechanism itself: readiness to delete your own invention is the Tier-4 signal.

## Questions

### Tier 2 — Reason

**Q 14.1 — Why did RAG apps come before tool-using agents, if the loop was always the end point?**

**Answer.** Each stage works on the context limit with the machinery reliable at the time.
RAG needs only read-only context assembly: no structured output, no action risk, no error recovery.
Tool use needs the model to emit valid calls and to recover from an unexpected tool result, and the loop multiplies any unreliability in one step.
So the read-only approach shipped first, and deciding moved into the model only when models could carry it.

*Strong answers also mention:* the order followed risk — an action is gated harder than a read, in history as in permission policy.

**Q 14.2 — Every lineage stage works on one limit. Name it, and show how two stages work on it differently.**

**Answer.** The limit is the context window: what enters it on each turn, and who decides.
RAG answers with pipeline code: retrieval guesses relevance once, before the model speaks.
Agents answer by giving the decision to the model: each tool call requests the model's own next context.
Harnesses govern the same limit: compaction, memory, and subagent isolation are policies about what stays in the window.

*Strong answers also mention:* this is why context engineering replaces prompt engineering as the name for the practice.

**Q 14.3 — Why does GUI-agent reliability decay faster with task length than API-agent reliability?**

**Answer.** Three mechanisms compound.
Accuracy for each step is lower: the agent infers the state from pixels instead of reading a structured result.
Errors multiply across steps, so a small gap in accuracy becomes a large gap in completion.
Screenshots cost many tokens, so the context fills sooner, exactly when the task needs its history most.
There is also no schema to check against: a wrong click often looks like success, so the error appears late.

*Strong answers also mention:* verification is the binding limit — an API returns a checkable result, a screen a picture of one.

### Tier 3 — Design & Debug

**Q 14.4 — Your team supervises every agent session and wants hours-long unattended runs. Design the rollout.**

**Answer.** Add gates first, and extend the run between them.
Split the target tasks into segments that end at a milestone the harness verifies — a passing test, a green build, a judged diff ([Chapter 10](ch10.md)).
Wrap each run in layered stop conditions (Q 1.8), and make each one persist a resumable state.
Extend the unattended part one segment at a time, gated on the measured intervention rate of the previous stage.
Measure first: if you cannot count how often a supervised session needed a human, you cannot argue the next extension is safe.

*Strong answers also mention:* a task that you cannot split stays supervised — task shape, not confidence, sets the autonomy budget.

**Q 14.5 — An agent fleet has self-maintained memory files for six months. Turn counts and costs have crept up. Diagnose and fix.**

**Answer.** Read the transcripts and the memory files first: a slow rise points at accumulation, not a model change.
Memory that the agent wrote without review grows without limit: agents append entries and never remove them.
Every session then carries more context, reads stale entries, and needs more turns.
Check for the worse failure: wrong or injected content that reached memory and now steers every session ([Chapter 11](ch11.md)).
Fix the class: gate a memory write like a configuration change, with an eval suite on turns and success rate.
Add a size budget that forces consolidation, then replay the task suite against pruned memory and compare turns and cost.

*Strong answers also mention:* a metric for memory size and repeated reads in the standing suite, so the next rise alarms early.

### Tier 4 — Judge

**Q 14.6 — A director says: "We will adopt agents when they are done improving." Argue the strongest version, then commit.**

**Answer.** Strongest version: an early adopter pays the integration cost twice.
Today's patterns get rebuilt, and a team that waits one cycle gets a better baseline free.
One observation defeats it: the compounding asset is the organization — eval suites, permission policies, transcript reading — not the model.
Every capability jump so far raised that layer's value: teams trust a stronger model with more work, and more work demands more gating.
Commit: adopt now on workflows with a small blast radius, spend on the harness and eval layer, and re-scope at each model generation.
Kill-criterion: two upgrades in a row that force a rewrite of the eval and permission layer would break the transfer assumption.

*Strong answers also mention:* [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) has stayed stable across model generations, so the loop is the durable interface to bet on.

**Q 14.7 — Your CFO proposes cutting model spend by moving the coding agents to small local models. Commit to a position.**

**Answer.** No to replacement, yes to routing.
Assumption: the spend concentrates in frontier sessions with many turns, so cut what reaches the paid model, not the model itself.
Local models hold up on classification and summarization, and degrade on exactly the long-run tool use that a coding agent does.
A local-only fleet trades a visible spend for an invisible cost: failed tasks, cleanup, re-runs.
The honest counter-position: for narrow, repeated, checkable steps a local model is free and private, so route those steps locally and keep judgment steps frontier.
Kill-criteria: hybrid routing must cut cost per completed task 30% in one quarter, and any routed step that drops completion below baseline goes back.
Report cost per completed task to the CFO, never cost per token.

*Strong answers also mention:* the router becomes a harness component with its own evals, because a routing bug looks exactly like a model regression.

## Common mistakes & red flags

- **"The next model makes harness work obsolete."** Every capability jump so far raised harness value: teams trust a stronger model with more work, and more work demands more gating, evals, and context discipline.
- **"GUI agents mean we never need APIs again."** A screen is the most expensive interface and the hardest to check. A GUI agent is the fallback for software with no other interface, not a reason to stop building interfaces.
- **"We will adopt agents when they are done improving."** "Done" never arrives, and the compounding asset — evals, permissions, transcript reading — belongs to your organization, not the provider.
- **"Self-improving agents are either magic or forbidden."** Self-modification with review is ordinary automation: the agent drafts, and an eval suite and a human gate it. The line is review, not self-editing.
- **"Agent-to-agent is just an integration problem."** The protocol is the easy part. An external agent is an untrusted tool whose output enters your context, so answer trust, billing, and audit before you call a demo an architecture.
