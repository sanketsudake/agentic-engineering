# Chapter 10 — Evals

## Why this chapter

You cannot improve an agent that you cannot score.
This chapter measures [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task):
it turns "the agent seems better" into a number that you can defend.
Every prompt, tool, and model decision in Chapters 2–9 becomes a testable change.
The mental model: the eval is the spec.
If you cannot write a check for a behavior, you did not define it.
This chapter owns offline evaluation, the runs that you score before you ship.
Online telemetry from live traffic comes later in this book.

## Concepts

### Eval-driven development

An eval is a scored, repeatable test of agent behavior.
It has three parts: a set of tasks, a way to run the agent on them,
and graders that score each run.
Eval-driven development writes the eval before the prompt,
the way test-driven development writes the test before the code.
The loop has five steps:

1. Capture a failure as a task.
2. Run the eval and watch it fail.
3. Change the system.
4. Re-run the eval.
5. Keep the change, or revert it.

Writing the eval first forces one question:
what, exactly, does "better" mean here?
A change without an eval gives you no way to prove that it helped.
With an eval, every improvement is a score that moves,
and every regression names the tasks that broke.

### Datasets and task suites

A task is an input, a fixture environment to run it in, and a grading spec.
A task suite is the versioned collection of tasks.
Start with twenty real failures from your transcripts,
not a thousand synthetic tasks.
Real failures carry the distribution that the agent meets in production.
Synthetic tasks carry your assumption about that distribution,
and a model passes an assumed test more easily than a real one.
Grow the suite the same way: every production incident becomes a task before its fix merges.

Split the suite in two.
You run the dev set constantly and iterate against it.
You score the holdout rarely and never tune on it.
If you iterate on the holdout, it becomes a second dev set,
and your scores rise while the agent does not improve.

Guard against contamination: task content that leaks into what the agent reads.
A holdout task that sits in the repository that the agent searches is no longer held out.
Public benchmark tasks may sit in the training data of a model.
So prefer your own failures over a borrowed suite.

### Graders: three kinds

A grader maps one run to a score.
There are three kinds, in order of preference.

1. **Code graders** are deterministic checks:
   an exact match on an answer, a functional test on produced code,
   an assertion on the final environment state.
   They are cheap, fast, and free of bias.
   Use them for every behavior with a checkable outcome.
2. **LLM-as-judge** is a model that scores a run against a written rubric.
   Use it where code cannot check: the faithfulness of a summary, the tone, or whether the reasoning holds.
   A judge is itself a model call, so pin its prompt and its model.
   A change to the judge is a change to the metric (Trace 28).
3. **Human graders** are slow and expensive, and they are the calibration anchor.
   A small set of human-labeled runs defines ground truth.
   It is the only thing that tells you whether you can trust a judge.

### Outcome-level and transcript-level metrics

Outcome-level metrics score the end state.
Pass rate is the share of tasks that the agent solves.
Pass@k is the chance that at least one of k attempts solves the task.
An agent run is sampled, so one attempt for each task measures luck as much as ability.

Transcript-level metrics score the path that the run took:
turn counts, tool-error rates, token cost per solve, and wall-clock time.
Two runs can both pass while one takes 40 turns and ten times the tokens,
and outcome metrics alone hide that difference.
Transcript metrics warn you early: the tool-error rate usually rises before the pass rate falls.
Track both kinds, and gate on both.

### When the metric becomes the target

Every metric is a proxy for something that you cannot measure directly.
An agent that optimizes the proxy moves the proxy, and some of the paths that it finds work against the goal you meant.

A support team measured the share of tickets that the agent resolved.
The number rose for five months.
Then the renewal date arrived, and churn had doubled.
The agent had found three ways to resolve a ticket:

- close the conversation early;
- discourage the follow-up question;
- mark an abandoned ticket as resolved.

Each way raised the metric.
Each way lost a customer.

A better single number does not fix this, because the next proxy has its own shortcuts.
Three practices together do.

1. Pair each target metric with a guard metric that the same shortcut damages. Resolution rate pairs with the reopen rate and with customer retention.
2. Grade the process, not only the outcome (below).
3. Read a sample of passing runs by hand each cycle. A shortcut looks like success in every number you chose, so only a human reading finds the ones you did not choose.

### Judge calibration and bias

A judge carries systematic biases, and each bias has a cheap detector.

- **Position bias:** in a pairwise comparison, the judge favors one position. Run every comparison in both orders, and treat disagreement as noise.
- **Verbosity bias:** a longer answer scores higher whatever its content. Check the correlation between score and length across the suite.
- **Self-preference:** a judge favors output in the style of its own model family. Strip model names and formatting habits from what the judge reads.

Calibration is what makes a judge admissible.
Before you trust a judge, score its agreement with human labels on a labeled subset.
Publish that agreement number next to every metric that the judge produces.
A judge that agrees with humans 95% of the time is a measuring instrument;
a judge that you never checked reports an opinion.
A structured verdict that cites evidence raises agreement, and it makes each disagreement auditable.

### Regression gates

An eval suite that runs on demand measures the agent; one that runs in CI protects it.
The regression gate works in three steps:

1. Every change to a prompt, a tool, or the harness config triggers the suite.
2. The gate compares the new scores to a stored baseline.
3. A regression larger than the noise threshold blocks the merge.

The same gate guards a model upgrade.
A new model version is a change like any other,
so the suite runs against it before any traffic moves.

The noise threshold is what keeps the gate credible.
An agent run is stochastic, so measure the run-to-run variance of an unchanged baseline first.
Gate only on a delta that is larger than that variance.
Use several runs for each task, or a threshold with real headroom.
A gate that fires on noise gets bypassed, and a bypassed gate protects nothing.

### Grading the process, not only the outcome (L3)

Outcome grading rewards a lucky run, and it cannot separate a robust agent from a brittle one.
Trajectory grading scores the transcript against a process rubric.

- Did the agent bisect the failure instead of guessing?
- Did it run the tests before it declared the task done?
- Did it read the file before it edited the file?

A run that passes without verification is a defect that the outcome grader just certified.
It is the same gap that lets a CI agent pass by weakening a test ([Trace 23](ch08.md#trace-23-what-happens-when-a-ci-agent-handles-a-pull-request)).

Implement trajectory grading with both grader kinds.
Code checks read the transcript: they confirm that the verify command appears before the done claim,
and count redundant re-reads.
Judge rubric items read the trajectory for what a pattern check cannot catch.
One caution: grade for invariants, not for tactics.
"The agent verified the claim before it made the claim" is an invariant.
"The agent used bisection" is one strategy, and a rubric that demands a strategy locks the agent into it.

### In other stacks

- **Pytest-style runners:** each task is a test case and each grader is an assertion. The eval suite then runs under the test runner and CI wiring that the team already has.
- **Declarative task suites:** tasks live in YAML or JSON — input, fixtures, grading spec — separate from runner code. People who do not write code can then add tasks from real failures.
- **Hosted eval platforms:** dataset versioning, judge management, and baseline diffing arrive as a service. The cost is lock-in: your tasks and labels live inside the platform.
- **Trace-based evals:** graders run over the same telemetry spans that the production pipeline emits, so offline suites and online monitors share one grader library.
- **Framework hooks:** an agent framework exposes run traces and callback hooks, and that is where an eval harness attaches, whatever the stack.

## Traces

### Trace 27: What happens when an eval suite runs

You changed the system prompt; before the merge, CI runs the agent eval suite against the change.

1. **CI** starts the eval run on the candidate change, with the model, judge, and config pinned.
2. **Harness** loads the task suite: each task carries an input, a fixture environment, and a grading spec.
3. **Harness** starts one agent run for each task, each run in an isolated, freshly built environment.
   - Parallel runs must share nothing. A shared scratch directory lets one task's artifacts grade another task.
4. **LLM** works each task through its own [Trace 2](ch01.md#trace-2-what-happens-when-a-user-request-becomes-a-finished-task) loop until the loop stops.
5. **Harness** records a transcript and a final outcome artifact for every run.
6. **Harness** runs the code graders on each outcome: functional tests, exact matches, end-state assertions.
7. **Judge** scores the rubric items that code cannot check, one transcript at a time (Trace 28 zooms in).
8. **Harness** aggregates per-task scores into suite metrics: pass rate, pass@k, turn counts, cost per solve.
9. **Harness** loads the baseline: the stored metrics of the last accepted run.
10. **CI** applies the regression gate: a tracked metric that falls by more than the noise threshold blocks the merge.
11. **CI** posts the verdict with per-task diffs, so a red gate names the tasks that changed from pass to fail.

**Where this can fail**

- **Symptom:** scores swing between runs of the same commit.
    - **Cause:** sampling variance, from too few attempts per task.
    - **Where to look:** the run-to-run variance of an unchanged baseline, and the attempts per task.
- **Symptom:** the suite stays green while production regresses.
    - **Cause:** dataset drift, so the tasks no longer match real traffic.
    - **Where to look:** the dates on suite tasks against the newest production failures.
- **Symptom:** a task passes alone but fails inside the suite.
    - **Cause:** parallel runs that share environment state.
    - **Where to look:** the fixture paths in both transcripts.
- **Symptom:** the gate blocks a change that everyone agrees improves the agent.
    - **Cause:** a stale baseline, or a threshold tighter than the suite's own noise.
    - **Where to look:** which baseline run the gate compared against, and its variance.
- **Symptom:** the suite has passed at 100% for months.
    - **Cause:** the tasks are too easy, so the gate blocks nothing.
    - **Where to look:** the per-task score distribution; a healthy suite has headroom.

### Trace 28: What happens when an LLM judge grades a transcript

A code grader cannot decide whether a summary is faithful to its source, so a judge model scores it against a rubric.

1. **Harness** selects the task rubric: numbered criteria, each with anchors for a low score and a high score.
2. **Harness** strips identifying metadata from the transcript: model name, variant label, run order.
   - Any hint about which candidate produced the run invites self-preference.
3. **Harness** sends the judge prompt: the rubric, the transcript, and a required verdict schema.
4. **Judge** scores each criterion, with a citation to the transcript span that justifies the score.
5. **Judge** returns a structured verdict: per-criterion scores, quoted evidence, one overall grade.
6. **Harness** validates the verdict against the schema. A malformed verdict retries once, then counts as a grading error, never as a zero for the agent.
7. **Harness** sends the judge the calibration subset: transcripts that carry stored human labels.
8. **Env** returns the human labels from the label store for comparison.
9. **Harness** computes judge–human agreement. Below the bar the judge is invalid, and no agent score publishes from this run.
10. **Harness** aggregates the accepted verdicts into the suite metrics of Trace 27.

```mermaid
sequenceDiagram
  autonumber
  participant Harness
  participant Judge
  participant Env
  Harness->>Harness: strip run metadata
  Harness->>Judge: rubric plus transcript
  Judge-->>Harness: structured verdict
  Harness->>Harness: validate verdict schema
  Harness->>Judge: calibration transcripts
  Judge-->>Harness: calibration verdicts
  Harness->>Env: read human labels
  Env-->>Harness: labels
  Harness->>Harness: check agreement bar
  Harness->>Harness: publish or invalidate scores
```

*Figure 10.2 — the judge is graded too: no agent score publishes until the judge clears the agreement bar.*

**Where this can fail**

- **Symptom:** the pairwise winner changes when you swap the answer order.
    - **Cause:** position bias.
    - **Where to look:** run every comparison in both orders, and measure the disagreement rate.
- **Symptom:** longer transcripts score higher on every criterion.
    - **Cause:** verbosity bias.
    - **Where to look:** the correlation between score and transcript length across the suite.
- **Symptom:** the judge always prefers one candidate's answers, and humans do not agree.
    - **Cause:** self-preference, because that candidate's style matches the judge's model family.
    - **Where to look:** judge–human agreement for each candidate, and whether any metadata reached the judge.
- **Symptom:** scores drift week to week with no system change.
    - **Cause:** the judge prompt or model is not pinned.
    - **Where to look:** the judge config diff between the two runs.
- **Symptom:** high scores that rest on quotes that do not exist.
    - **Cause:** the rubric lets the judge score without verified evidence.
    - **Where to look:** the verdict's quoted spans, checked against the transcript text.

## Questions

### Tier 1 — Explain

**Q 10.1 — Why write the eval before the prompt change?**

**Answer.** The eval defines what "better" means before you start the work.
An eval written after the change measures whatever that change improved.
An eval written first is a spec: the change either moves the score, or it does not.
A regression elsewhere in the suite also appears in the same run.
Without an eval, nobody can prove that the prompt work helped.

*Strong answers also mention:* the parallel to test-driven development, and capturing each real failure as a task before you fix it.

**Q 10.2 — Name the three grader kinds and when each applies.**

**Answer.** Three kinds, in order of preference:

1. Code graders run deterministic checks on outcomes: exact match, functional tests, end-state assertions.
   Use them wherever an outcome is checkable.
2. LLM-as-judge is a model that scores a run against a written rubric,
   for the qualities that code cannot check: faithfulness, tone, and reasoning.
3. Human graders are slow and expensive, so they anchor rather than scale;
   a human-labeled set is the ground truth that calibrates the judge.

Prefer them in that order; fall back only when the cheaper kind cannot express the check.

*Strong answers also mention:* a judge is a pinned model call, so a change to the judge is a change to the metric.

**Q 10.3 — What is the difference between outcome-level and transcript-level metrics?**

**Answer.** Outcome-level metrics score the end state: pass rate, pass@k.
Transcript-level metrics score the path: turn counts, tool-error rates, token cost per solve.
Two runs can both pass while one of them costs ten times more.
Outcome metrics alone hide that difference in efficiency and robustness.
Transcript metrics also lead: the tool-error rate usually rises before the pass rate falls.

*Strong answers also mention:* gating on both, and trajectory grading as the L3 extension of path metrics.

**Q 10.4 — What does pass@k measure, and why does k matter for agents?**

**Answer.** Pass@k is the probability that at least one of k independent attempts solves the task.
An agent run is sampled, so a single attempt mixes ability with luck.
A wide gap between pass@1 and pass@8 means that the agent can solve the task, but not reliably.
That is a different problem from an agent that never solves it, and it needs a different fix.

*Strong answers also mention:* pass@1 is what a user experiences; pass@k describes capability, not product quality.

### Tier 2 — Reason

**Q 10.5 — Why do twenty real failures beat a thousand synthetic tasks as a starting dataset?**

**Answer.** Real failures come from the distribution that the agent meets in production.
Synthetic tasks come from your assumption about that distribution,
and the two differ exactly where your assumption is wrong.
Each of the twenty real tasks carries a documented, reproduced defect,
so every task that changes from fail to pass is a real fix.
A thousand synthetic tasks measure the same assumed difficulty a thousand times,
and public or generated tasks risk sitting in the model's training data.

*Strong answers also mention:* the suite grows by converting each production incident into a task before its fix merges.

**Q 10.6 — When can you trust an LLM judge's scores?**

**Answer.** Trust the scores when you have measured judge–human agreement and it is above your bar.
Calibration is empirical: run the judge on a human-labeled subset, compute the agreement, and publish the number with the metric.
A judge that reports its own confidence, or agrees with itself across reruns, proves consistency only, not correctness.
Then keep it trustworthy: pin the judge prompt and model, strip candidate metadata, and require evidence citations.
Re-calibrate whenever the judge, the rubric, or the task mix changes.

*Strong answers also mention:* checking bias detectors — order swaps for position bias, length correlation for verbosity.

**Q 10.7 — Why must a model upgrade pass the same regression gate as a prompt change?**

**Answer.** The suite scores the whole system, and the model is its largest single component.
An upgrade changes behavior across every task at once: the average usually rises, and something specific falls.
The gate finds the specific case: which tasks changed from pass to fail, and which transcript metrics moved.
The aggregate benchmark gains that the provider publishes say nothing about your twenty real failures.

*Strong answers also mention:* running the full suite, not a smoke subset, since upgrade regressions cluster in the tails.

### Tier 3 — Design & Debug

**Q 10.8 — Your suite's pass rate is flat, but production complaints are rising. Walk your diagnosis.**

**Answer.** The suite and production have diverged, so find where.

1. Check for dataset drift: sample the newest production failures and look for a suite task that resembles them.
   If none does, the suite tests last year's traffic.
2. Check for a missing metric: a suite that scores pass rate only never sees a complaint about cost, latency, or tone.
   Read the transcript-level metrics, and check whether a judge rubric covers the complaint.
3. Check for contamination: a suite that the agent can read, or a task that the model saw in training, holds scores up artificially.

Then convert the current complaints into tasks, watch them fail, and add the missing metric to the gate.

*Strong answers also mention:* a standing process that turns each incident into a task. Compare online telemetry against the suite's predictions to catch drift early.

**Q 10.9 — Design the regression gate for a team shipping agent changes daily.**

**Answer.** Start by measuring the noise: run the unchanged baseline several times, and record the variance of each metric.
The gate fires only on a delta larger than that variance.
Build two rings.

1. The first ring is a fast dev-set run on every pull request: minutes, code graders, and cached judges.
2. The second ring is the full suite, with the holdout and the calibration set.
   It runs on merge to main, and on any change to the model or judge.

Gate on pass rate, tool-error rate, and cost per solve: block on a regression, and warn on stagnation.
Update the baseline only when a gated run is accepted, never by hand.
Score the holdout on a schedule, not on every change, so nobody tunes against it.
Post per-task diffs on every red gate, because a gate that says only "worse" gets bypassed.

*Strong answers also mention:* an explicit bypass path, with a named approval and an automatic follow-up task. A team that cannot bypass the gate in an emergency deletes it instead.

**Q 10.10 — Your agent's headline metric improved every month for a year. What do you check before you believe it?**

**Answer.** Run these checks:

- Ask what the metric is a proxy for, and then look for the paths that raise it without delivering that thing.
- Read the passing transcripts by hand, because a shortcut satisfies every number that you chose.
- Check the guard metrics: the ones that a shortcut damages, such as a reopen rate, a revert rate, or retention.
  A target that rises while its guard metric also worsens is the signature.
- Check the suite itself: a task set that stopped changing while production changed will show a rising score against last year's traffic.
- Check who can edit the metric, the grader, and the baseline, because a gate that the agent or the team can move measures the mover.

Then state what would make you stop believing the number, and add that check to the gate.

*Strong answers also mention:* a metric that only rises is itself the warning, because a real measurement of a hard task moves in both directions.

## Common mistakes & red flags

- **"We eval on vibes — we can tell when it's better."** You can judge the case in front of you. The suite scores the nineteen cases that you are not looking at.
- **"The judge is a frontier model, so its scores are reliable."** Reliability is agreement with human labels, measured on your own tasks. An uncalibrated judge reports an opinion.
- **"The judge grades its own model's style."** Self-preference: the judge and the candidate share a model family, and the metadata reached the judge. Strip it, and calibrate for each candidate.
- **"100% pass rate — the agent is ready."** A suite that every run passes gates nothing. A healthy suite keeps headroom, so add harder real failures until the score can move.
- **"We ran the holdout a few times while tuning."** Then it is a dev set. A holdout stays a holdout only while you score it on a schedule, not on every iteration.
- **"One run per task keeps the suite cheap."** One sample of a stochastic process measures luck. Run each task several times, or the gate fires on noise.
- **"The task passed, so the behavior is fine."** The outcome grader cannot see the skipped verification or the weakened test. Grade the trajectory for invariants too.
